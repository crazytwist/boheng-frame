# 中枢能力划分与权威事实

> 面向实验室中枢的对外架构表述。回答两个问题：**由哪些能力组成**、**哪一条事实归谁**。
> 详细论证与代码核对过程见仓库 `doc/10-中枢能力划分与权威事实.md`。

---

## 一、结论

- 现有三域（设备、物料、流程）作为起步骨架成立，**不需要立刻大拆重构**。
- 但对外的目标架构应升级为 **5 个纵向能力域 + 2 个横向支撑层**。
- 权威按**事实**划分，不按系统划分。
- 当前最贵的缺口不是功能，是**外部关联没有统一模型**。

---

## 二、为什么是 5 纵 2 横

**判据：纵向域必须拥有独立的事实链，且可被单独替换。**

| 能力 | 独立事实链 | 定位 |
|---|---|---|
| 实验执行域 | 方法定义 → 执行实例 → 步骤执行 → 信号 | 纵向 |
| 设备域 | 设备 → 能力 → 命令 → 结果 | 纵向 |
| 样本与物料域 | 实例 → 落位 → 流水 | 纵向 |
| 资源与调度域 | 申请 → 租约 → 释放 | 纵向 |
| 数据与结果域 | L0 → L1 → L2 | 纵向 |
| **任务与集成** | 无（事实分散在外部单据与各域记录中） | **横向层** |
| **身份 · 审计 · 合规** | 无（是策略与记录，不产生事实） | **横向层** |

「任务与集成」排在入口位置，但它的性质是横向的。把它做成域，会重演
「流程域变万能域」的同一个错误——变成第二个什么都管一点的中间层。

---

## 三、三层权威

| 层次 | 归属 | 内容 | 外部可否改写 |
|---|---|---|---|
| 业务权威 | 外部系统（LIMS/MES）或平台 | 业务编号、业务要求、优先级、样本业务身份 | 业务字段可 |
| 执行权威 | 平台，唯一 | 分了哪台设备、走到哪步、出了什么异常、产出什么原始数据 | **不可** |
| 物理权威 | 平台，唯一 | 实物在哪、占哪个库位、被谁占用 | **不可** |

一句话：**外部系统可以「提出要求」和「接收结果」，不能「改写过程」。**

---

## 四、权威矩阵（摘要）

| 事实 | 载体 | 唯一写入者 | 现状 |
|---|---|---|---|
| 业务任务身份 | 外部单据 | 外部系统 | 平台内无载体 |
| 平台任务 ↔ 外部任务映射 | 待建关联表 | 关联层 | 散落 5 处 |
| 执行实例 | `flow_execution` | 实验执行域 | ✅ |
| 步骤执行 | `flow_step_execution` | 实验执行域 | ✅ |
| 设备命令 | `device_command` | 设备域 | ✅ |
| 原始数据 | `device_data_raw` | 数据域 | 缺设备时间 |
| 分析结论 | `device_analysis_result` | 数据域 | ✅ |
| 样本业务身份 | `wms_sample_info.external_id` | 外部系统 | 单串，无来源系统 |
| 样本执行状态 | `wms_sample_info.status` | 实验执行域 | **未声明** |
| 实物与占用 | `wms_material_instance` | 样本与物料域 | ✅ |
| 资源租约 | 待建 | 资源与调度域 | ❌ |
| 审计记录 | 待建 | 身份与合规层 | ❌ |

**最危险的一行是「样本执行状态」**：业务系统认为它是自己的字段，流程引擎认为它由执行驱动。
接入 LIMS 前必须写死为执行权威，否则第一天就会打架。

## 五、当前缺口的实测证据

### 5.1 外部关联散落五处、互不相认

| 表 | 关联字段 |
|---|---|
| `flow_execution` | `trigger_type` + `triggered_by` + `business_key`（自由串，可空） |
| `device_command` | `source_type` + `source_ref` + `attempt` |
| `device_measurement` | `experiment_ref` + `task_ref` |
| `device_analysis_result` | `source_system` |
| `wms_sample_info` | `external_id`（单串，无来源系统） |

无法回答「这份报告对应 LIMS 哪张单、是哪个系统下发的」。

### 5.2 时间权威缺失

`device_data_raw` 共 19 列，只有 `received_time`，**没有 `device_time`，没有 `clock_offset_ms`**。
仪器文件里自带的时间戳无法归一到平台时基；审计时只能回答「我们几点收到的」，
不能回答「几点测的」。

### 5.3 资源三者异构，暂时拆不出调度域

| 资源 | 可用性表达 |
|---|---|
| 库位 | `wms_slot_info.slot_status`（FREE/OCCUPIED/LOCKED/CHECKING） |
| 设备 | `device_info.status`（'ONLINE' 字符串）+ busy |
| 通道 / 人力 / 时间窗 | 不存在 |

此时拆出来的调度器只能调度设备，结果是一个「设备排队器」。
正确顺序是：先定义 `Resource` 抽象 → 给 slot/device 各挂适配器（不改原表）→ 再落 `ResourceLease`。

## 六、三层契约

| 层 | 面向 | 状态 |
|---|---|---|
| 能力契约 | 模块之间（`*-api`） | 已有，缺 `flow-api` |
| 集成契约 | 外部系统（版本化 API + 事件 + 幂等键） | ❌ 无 |
| 证据契约 | 审计、复算、对外出具（只读导出 + schema 版本） | ❌ 无 |

---

## 七、待决策（附推荐）

| 编号 | 决策 | 推荐结论 |
|---|---|---|
| D1 | 样本业务身份唯一性 | `(source_system, external_id)` 联合唯一，不要求全局唯一 |
| D2 | 任务撤回语义 | 拆成「撤回」与「终止」；已产生数据一律不删 |
| D3 | 时钟基准 | 平台 NTP 做记录时基，设备偏移换算业务时基；不设参考设备 |
| D4 | 数据留存期限 | L0 永久只归档；其余 ≥ 有效期后 1 年且不少于 3 年；审计不少于 10 年 |
| D5 | 审计追踪粒度 | 只对受控字段做字段级，其余记录级 |

推荐原则：**不把改造成本推给客户、不产生不可追溯的数据。**

## 八、落地顺序

| 序 | 动作 | 成本 |
|---|---|---|

| P2 | `device_data_raw` 补 `device_time` + `clock_offset_ms` + `time_quality` | 0.5 人日 |
| P3 | 资源统一抽象 + 适配层 | 5–8 人日 |
| P4 | `audit_log` + `signature`（最小形态） | 3–5 人日 |
| P5 | 证据契约：导出格式 + schema 版本 | 5 人日 |
