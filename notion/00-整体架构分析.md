# 整体架构分析（boheng-frame 实验自动化平台）

> 本篇统领全局，把「物料、样本、设备、流程」四块串起来。各块细节见 `01~04` 分篇。

---

## 一、四块一句话定位

| 域 | 模块 | 回答的问题 |
|---|---|---|
| 物料域 | `boheng-module-wms` | 东西是什么、装在哪、现在在哪 |
| 样本域 | `boheng-module-wms`(sample) + `wms-api` | 这次送检的业务样本是什么、谱系、走到哪 |
| 设备域 | `boheng-module-device` + `device-api` | 有什么设备、能下什么命令、结果怎么回 |
| 流程域 | `boheng-module-flow` | 流程怎么定义、怎么跑、怎么调度 |

**分层关系**：流程是「大脑」，物料/样本/设备是「手脚」。流程通过两个契约层（`wms-api`、`device-api`）驱动它们，绝不直接依赖实现模块。

---

## 二、模块依赖关系

```
                        ┌─────────────┐
                        │ boheng-flow │  流程编排（大脑）
                        └──────┬──────┘
                ┌──────────────┼──────────────┐
                ▼              ▼              ▼
        ┌──────────────┐ ┌──────────────┐
        │ wms-api 契约 │ │ device-api 契约 │   纯契约，零实现
        └──────┬───────┘ └──────┬───────┘
               ▲                ▲
        ┌──────┴───────┐ ┌──────┴───────┐
        │  boheng-wms  │ │ boheng-device│    实现模块
        └──────────────┘ └──────────────┘
```

关键约束：
- 契约层（`*-api`）**零 Spring/MyBatis/validation**，只有接口 + DTO，供消费方（flow）与实现方（wms/device）共同依赖，绝不反向。
- 流程模块只依赖契约层，所以「换设备实现」「换仓储实现」不影响流程编排。

## 三、端到端数据流（一次实验的完整生命周期）

```
1. 登记样本         flow 调 SampleApi.registerSample → wms_sample_info（业务对象，先于实物）
                        │
2. 生成实例（分装）  样本侧「生成实例」→ wms_material_instance.sample_id 挂样本（1 样本 : N 实例）
                        │
3. 定义流程         flow_step（能力）+ flow_node（编排 DAG）→ 发布（PUBLISHED）
                        │
4. 启动流程         engine.start 冻结定义 → 初始化节点行 → 推进
                        │
5. 节点执行         按 step_type 分发：
     device.command  → DeviceCommandApi.send（同步推设备）
     device.task     → FlowDeviceTaskService.enqueue（设备离线排队拉取）
     bean.invoke     → 调业务 Bean（可经 SampleApi 读实验参数/驱动状态）
     validate        → 调 FlowValidateAction 拿完整上下文判 pass/fail
                        │
6. 设备执行 + 回传   DeviceHttpService 下发 → 设备执行 → 回调/轮询 → L0 raw → codec 解析 → L1 测量
                        │
7. 结果落库/回写     L1 测量 → 流程节点输出写进上下文（node.{nodeId}.*）
                        │
8. 样本状态流转      流程动作 Bean 调 SampleApi.updateStatus 驱动八态
```

**两条正交的主线**贯穿始终：
- **样本状态（八态）** 由**流程引擎**驱动 —— 表达「业务走到哪」
- **实例状态（六态）** 由**物理操作**驱动 —— 表达「实物处于什么物理状态」

---

## 四、状态正交总览

| 对象 | 状态集合 | 驱动者 | 终态 |
|---|---|---|---|
| 样本 | REGISTERED/LOADED/IN_PROCESS/SPLIT/COMPLETED/ARCHIVED/REJECTED/LOST | 流程引擎 | ARCHIVED/REJECTED/LOST |
| 实例 | AVAILABLE/RESERVED/IN_USE/USED/EXPIRED/DISCARDED | 物理操作 | DISCARDED（含 USED/EXPIRED 过渡） |
| 槽位 | status(0/1) × slot_status(FREE/OCCUPIED/LOCKED/CHECKING) | 调度域 + 落位 | — |
| 命令 | ACQUIRED/SENT/WAITING/SUCCEEDED/FAILED/TIMED_OUT/CANCELLED | 设备域 | 终态 |
| 流程运行 | RUNNING/PENDING/SUCCESS/FAILED/CANCELLED | 流程引擎 | 终态 |

**核心设计**：样本状态和实例状态**不联动**——生成实例（分装）不改样本状态，「独立走流程」的载体是子样本而非实例。

## 六、关键决策清单（沉淀）

| 决策 | 结论 |
|---|---|
| 位置即实例 | 孔/格位也是实例，内容物 1:1 内联，无独立内容物表 |
| 两套位置 | slot（空间）vs parent_position_code（容器内），只有顶层实例落 slot |
| slot 不存占用方/锁 | 占用真相源 = material_instance.root_slot_id；锁归调度域 |
| 落位流水 | 上下架/转移/消耗都写 movement（只增不改），同事务 |
| 样本↔实例正交 | 样本八态由流程驱动，实例六态由物理驱动 |
| 分装 vs 拆分 | 分装 = 1样本:N实例；拆分 = 母样本→子样本谱系 |
| 唯一键 | 全程「普通索引 + Service 校验」或「生成列 + 唯一索引」兼容逻辑删除 |
| 契约隔离 | flow 只依赖 *-api，不依赖实现模块 |
| 数据依赖⊆拓扑依赖 | 参数映射发布期强制取直接前驱，运行时零竞态 |
| 决策与执行分离 | 控制流节点只产出 BRANCH，激活/裁剪归调度器 |

## 七、已闭环 vs 待办

### 已闭环（本轮验证通过）
- 样本三层模型 + 谱系五件套 + 八态状态机（含删除保护/流转约束/deriveType 一致性）
- 实例绑定 sample_id + 按样本反查 + 分装/拆分入口
- 流程引擎：定义/类型/运行五表 + CAS/DAG/分支/循环/子流程/FANOUT + 校验节点 + 定时启动
- 设备域：命令下发-回调-超时兜底 + 编解码 + 模拟 + 契约层

### 待办 / 缺口
1. **资源校验独立**：拟独立成「资源声明 + 检查/预留/释放」SPI（一期只做物料资源校验 check-only，占用/释放留二期），未实现。
2. **样本状态驱动者**：`updateStatus` 入口 + 状态机就位，但「谁在何时驱动」属业务编排，未硬编码。
3. **样本状态流转表待业务确认**（4 个待确认点，见《样本域》3.2）。
4. **实例表缺批次字段**：`batch_no/lot_no/received_at/opened_at/expired_at`（v1.4 原设计有，当前简化）。
5. **设备 DDL v4 目标 vs 代码一期子集**（幂等三键、忙闲预检、命令状态机等未落地）。
6. **「数据流等待态」**（参数依赖非直接前置的旁路分支）：经评估一期不做，靠「拓扑依赖 = 数据依赖」覆盖。
