# 虚拟资源与调度求解器设计备忘

> 状态：方向性设计，暂不实施。资源模型、调度模型和求解器必须联合设计，不应分别落地后再强行对接。

---

## 一、核心想法

建立一个独立的虚拟资源模块。“虚拟”不代表资源不真实，而是指资源模块不拥有设备、库位、人员等业务实体，只保存它们参与调度时所需的统一投影。

任何具有以下特征的业务对象都可以被注册成资源：

- 容量有限；
- 存在互斥使用；
- 需要抢占、续租、释放或过期回收；
- 存在能力、时间窗、位置、优先级或组合约束；
- 需要参与跨业务域的调度求解。

可注册对象包括但不限于：设备、机台、库位、机械臂、AGV、人员、通道、工装以及其他受限对象。

---

## 二、渐进式接入

业务数据默认继续使用原有逻辑。管理员可在前端通过“加入资源管理”动作，将指定业务对象注册为受管资源。

控制模式建议不使用单一布尔值，而是分为：

| 模式 | 含义 |
|---|---|
| `OFF` | 不受资源模块管理，保持原有业务逻辑 |
| `ADVISORY` | 资源模块返回校验和调度建议，但不强制拦截 |
| `ENFORCED` | 必须成功获得资源租约后才允许执行 |

推荐按 `OFF → ADVISORY → ENFORCED` 逐步上线，先观察候选筛选和评分结果，再开启强制管控。

前端只负责发起注册、停用或取消管理的管理动作，不能决定单次执行是否绕过资源校验。

---

## 三、模块边界

| 模块 | 职责 |
|---|---|
| device | 设备台账、能力、通信、命令和设备业务状态 |
| WMS | 库位、物料、容器、相容性和物理流水 |
| flow | DAG 执行、节点重试、取消和执行结果收口 |
| resource | 资源注册、容量、互斥组、租约、续租、释放、过期回收 |
| scheduler/solver | 跨域候选资源组合、约束求解、评分排序和分配方案 |

资源模块不成为业务实体的新主数据源。它使用 `owner_module + owner_type + owner_id` 弱引用原业务对象，仅保存调度所需投影。

---

## 四、统一执行入口

业务模块不应分散编写“先查是否已注册，再决定是否走资源模块”的逻辑。应由资源契约提供单一原子入口：

```text
acquire(request)
    ├─ NOT_MANAGED  对象未注册，业务按原逻辑执行
    ├─ ACQUIRED     已原子创建租约，允许执行
    ├─ BUSY         资源已被占用
    └─ REJECTED     资源停用或不满足约束
```

这避免了 `exists → acquire` 之间的并发窗口，也避免不同业务入口遗漏校验。

同时支持两类请求：

- 指定对象：对已选定的设备、库位等进行校验和抢占；
- 按需求选择：只提供能力和约束，由调度器返回具体资源组合。

---

## 五、为什么必须和调度、求解器整体考虑

资源模型决定求解器能看到什么，求解器的需求又决定资源模型必须表达什么。二者无法后置对接。

需要一起确定的内容包括：

1. **能力模型**：资源能做什么，能力是标签、类型还是带参数契约。
2. **容量模型**：独占、数量容量、分数容量和复合容量如何统一。
3. **互斥模型**：单资源互斥、资源组互斥、物理空间冲突如何表达。
4. **时间模型**：即时租约、未来预约、维护窗口和执行时长预估。
5. **约束分层**：硬约束必须满足，软约束用于评分和优化。
6. **组合分配**：一个任务可能同时需要设备、机械臂、库位、通道和人员。
7. **优化目标**：完成时间、设备利用率、路径、切换成本、能耗、优先级和公平性。
8. **动态事件**：设备离线、任务取消、执行超时和紧急插单如何重排。
9. **可解释性**：为什么选择某组资源，为什么拒绝或延迟任务。
10. **一致性**：求解结果只是建议，最终必须通过租约层原子落地。

## 六、求解与执行分离

```text
收集业务候选和资源快照
        ↓
求解器产生候选分配方案
        ↓
租约层对方案执行原子抢占
        ↓
抢占全部成功？
  ├─ 否：释放已抢资源，使用新快照重新求解
  └─ 是：固化 Allocation Plan，交给 Flow 执行
```

求解器不直接命令设备或修改库位；Flow 不能绕过租约使用受管资源。

---

## 七、初步核心对象

| 对象 | 作用 |
|---|---|
| `ResourceRegistration` | 把业务对象注册为受管资源 |
| `ResourceCapability` | 描述资源可提供的能力和参数 |
| `ResourceConstraint` | 描述容量、互斥、时间窗和兼容性约束 |
| `ResourceRequest` | 描述一次执行对资源的需求 |
| `AllocationPlan` | 记录求解器的选择、评分、快照和解释 |
| `ResourceLease` | 资源占用事实，包含持有者、容量、到期时间和 fencing token |

`ResourceLease` 是调度占用的唯一真相源。业务模块保留 ONLINE、MAINTENANCE、CHECKING 等业务状态，但“被谁占用到什么时候”最终应收敛到租约表。

---

## 八、生命周期与一致性约束

- 业务对象停用时，同步将资源标记为不可调度；
- 业务能力或属性变化时，更新资源投影；
- 删除业务对象前，检查有效租约；
- 取消资源管理前，确认不存在有效租约或未完成计划；
- 租约必须有到期时间，长任务通过心跳续租；
- 释放时校验持有者和 fencing token，防止旧任务释放新租约；
- `ENFORCED` 模式下资源模块不可用时应拒绝执行，不得静默绕过；
- 求解时的快照可能过期，只有原子获取租约成功才表示方案真正生效。

---

## 九、与现有实现的迁移关系

初期不直接删除现有占用逻辑：

```text
DeviceHttpService.invoke
        ↓
ResourceApi.acquire(device reference)
        ├─ NOT_MANAGED → 继续使用 device_info 的现有 CAS 锁
        ├─ ACQUIRED    → 使用 ResourceLease 执行命令
        └─ BUSY/REJECTED → 拒绝执行
```

当设备资源已稳定迁移到 `ENFORCED` 后，再删除 `device_info.current_command_id/lock_*` 等重复占用真相，避免长期双写。WMS 的 `LOCKED/CHECKING` 仍保留为业务状态，具体任务占用关系逐步迁移到租约。

## 十、建议演进路径

1. **建模阶段**：定义资源、需求、约束、租约和分配方案，不接入业务执行。
2. **建议阶段**：引入 `ADVISORY`，仅记录候选和评分结果，与实际选择对比。
3. **租约阶段**：先选一类资源（建议从设备开始）实现原子抢占、续租、释放和过期回收。
4. **组合阶段**：支持一次请求组合分配设备、机械臂、库位等多类资源。
5. **求解阶段**：在约束稳定后引入可替换求解器，从简单过滤+评分逐步演进到约束规划或全局优化。

---

## 十一、尚未决策的问题

实施前需要专门完成一次资源与调度建模，至少回答：

- 资源是只表示实体，还是允许虚拟资源组和组合资源；
- 组合租约如何保证全成或全败；
- 租约是仅支持现在占用，还是同时支持未来时间窗预约；
- 约束由资源模块解释，还是由各业务模块提供可执行的候选过滤器；
- 调度范围是单任务局部选择，还是多任务批量重排；
- 是否需要强制抢占，以及强制抢占后原持有任务如何补偿；
- 如何定义可解释的评分项、权重、硬约束失败原因和方案快照；
- 在单机、多实例和分布式部署下，租约的一致性边界分别是什么。

## 十二、Transport V1.0 实施计划

当前第一阶段不直接建设独立的 Scheduler 和 Resource 服务，而是先把运输场景做成独立的 `boheng-module-transport` 模块，使用本地分配和本地资源锁跑通完整闭环。模块边界通过 SPI 预留后续替换点。

实施顺序：

1. **模块骨架**：建立 `boheng-module-transport`，划分 api、request、planning、allocation、resource、runtime、handover、executor、event、recovery 包；接入主工程和 server。
2. **契约与状态**：定义 TransportRequest、TransportOrder、TransportItem、TransportStop、TransportOperation、Handover、Event 的 DTO、枚举和 API 契约。
3. **数据库与迁移**：落地 `transport_*` 表，支持多批次、多起点、多终点；建立状态索引、幂等键、版本号和事件流水。
4. **需求与执行单**：实现请求受理、幂等校验、需求拆解、Order/Item/Stop/Operation 创建及状态条件更新。
5. **本地分配**：实现 `AllocationService` 与 `LocalTransportAllocationService`，按在线状态、能力、载位、电量、距离和优先级选择执行器。
6. **本地资源锁**：实现 `ResourceLeaseService` 与 `LocalResourceLeaseService`，支持原子抢占、续租、过期回收、fencing token 和按 Stop/Operation 滑动释放。
7. **Device 适配**：通过 Device API 实现 `AgvTransportExecutor`，把 MOVE、DOCK、PICK、PLACE、开关门、扫码和状态查询转换为 Device 命令。
8. **WMS 交接**：通过 WMS API 完成源位、目标位和运输载位校验；实现双边证据确认后更新物料位置和移动流水。
9. **运行时状态机**：实现 Stop/Operation 推进、超时、重试、取消、暂停、恢复、部分成功和人工介入。
10. **事件与恢复**：实现 TransportEvent/Outbox、命令幂等、重启恢复、陈旧回调拒绝和资源泄漏检查。
11. **测试与仿真**：覆盖单批次、多批次、多起点多终点、资源冲突、开关门失败、交接不一致、AGV 失联、重复回调和服务重启。
12. **V1.0 验收**：确认物料全过程可追踪、未双边确认不改 WMS、本地资源不重复占用、失败可补偿，且未来接入 Scheduler/Resource 不需要重构 Transport 核心表。

### V1.0 明确不做

- 不建设独立 Scheduler 服务和复杂求解器；
- 不建设独立 Resource 服务，先使用本地锁实现；
- 不实现全局最优路线、复杂路权、动态多车重排和未来时间窗预约；
- 不把 AGV 设备档案、协议和厂商配置复制到 Transport。

### V1.0 当前执行基线

```text
Flow / WMS / 人工
        ↓
TransportRequest
        ↓
LocalTransportAllocationService
        ↓
LocalResourceLeaseService
        ↓
Transport Runtime
        ├── Device API：AGV、机械臂、门禁、机台
        └── WMS API：物料位置、槽位和移动流水
```

### 第一批代码交付物

- `boheng-module-transport` Maven 模块及主工程依赖；
- `TransportApi`、请求/结果 DTO、状态枚举和执行器/资源 SPI；
- V1.0 数据库设计脚本与模块说明文档；
- 本地分配与本地资源锁的最小可运行实现；
- 不依赖 Scheduler/Resource 的编译和单元测试基线。

## 十三、当前结论

虚拟资源方向保留，但暂不单独开发独立服务。当前优先执行 Transport V1.0：先完成运输模块、状态机、本地分配、本地锁、Device/WMS 交接闭环，再依据真实任务量和资源竞争数据演进 Scheduler、Resource 和求解器。
