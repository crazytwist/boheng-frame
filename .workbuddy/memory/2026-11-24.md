## flow 模块「节点完成判定」与「设备回调链路」诊断

### 结论：设备回调链路代码完整，但有 3 个断点
1. **`boheng.device.callback-base-url` 全仓库未配置** → 签发的回调地址恒为 `http://127.0.0.1:{port}/admin-api/device/callback/...`，真设备/预发必然收不到回调（`DevicePlatformUrl.callbackAdminBase()` 无配置时静默降级）。
2. **`FlowExecutionEngine.deadlineOf` 不给 `DEVICE_COMMAND_CALLBACK` 设 deadline**（只处理 TIMER / DEVICE_CALLBACK）→ 流程侧无一手超时，全靠设备域 `DeviceCommandSweeper`(1min) + `FlowExecutionSweeper`(20s) 兜底，最坏约 7 分钟才判失败。
3. **设备「受理即完成」时结果被丢**：`DeviceHttpService.invoke` L139-142 只要 `callback=true` 就无条件 `resp.setStatus(202)` + WAITING，响应体只进 `request_json.ack`，不解析。

### 另外发现（本轮新增证据）
- **节点超时是死参数**：`DeviceCommandStepType` L89 传 `req.setTimeoutMs(ctx.getTimeoutMs())`，但设备域从不读 `DeviceCommandSendReqDTO.timeoutMs`。真正生效的是 `device_action.callback_timeout_sec`（默认 300 / 上限 600）。两套超时并存。
- 完成判定现状：`settle` 只认布尔；`DeviceCommandServiceImpl.callbackFailure` L310 硬编码认 `status=FAILED/ERROR/FAIL` 或 `success=false`，其余一律成功。零测试覆盖（`FlowSignalDispatcherTest` 只测 deviceTaskSignal）。

### 架构判断：不是「设备侧减负」，是三条线切分
- 留在设备域：协议、令牌、报文、命令五态、codec、超时收尾（人工调试/其他系统也要用）
- 搬成数据（不是搬去节点）：`callbackFailure` 字段名 → `device_action.completion_rule`
- 搬到节点：`completeWhen` 断言、超时、重试、失败分支（随流程/工序变化）
- **不可搬**：`/device/callback/{commandNo}` 回调入口必须留设备域，设备不认「流程节点」；接缝只保留 `DeviceCommandCompletedEvent(commandId)`

依赖方向已核验：`flow → device-api` 单向，device 不 import flow。

## 已实施：判定单点化 + 节点级回调（决策：判定做在 flow）

### 决策
用户拍板：**完成判定单点化到 flow**，且**节点推动回调也做在节点层**（不绕设备域）。
最终形态：设备走命令（认 commandNo）、业务系统走节点（认 executionId+nodeId），两条通道并存不混用。

### A. 节点完成断言 completeWhen
- `flow_node.run_config` 新增键：`"completeWhen": "output.weight >= 0.95 && output.weight <= 1.05"`
- 作用域：`output.*`（本次产出）/ `params.*`（本次入参快照）/ `node.<id>.*`（上游）/ `input.*`
- 求值点：`FlowExecutionEngine.settle` 的 SUCCESS 之前；不成立 → 降级 `StepOutcome.failed`，复用已有重试 / FAIL_FAST / FAIL_SKIP；断言失败时仍落 output_data 便于排查
- 求值异常**按不通过处理**（变量名写错不能静默放行）
- 发布期校验：`FlowGraphChecker.checkPublish` 调 `ExpressionEvaluator.checkSyntaxStatic`（新增静态入口，避免第二套合法表达式判断）
- 新增 `FlowNodeDraft.completeWhen` + `FlowDraftAssembler` 解析
- 关键类：`RuntimeNode.runCompleteWhen()`

### B. 节点级外部回调 external.callback
- 新类型 `external.callback`（role=WAIT, completionMode=SIGNAL, retryable=false）
- 入口：`POST /app-api/flow/external-callback/{executionId}/{nodeId}?attempt=&token=`（@PermitAll + @TenantIgnore）
- 令牌：`FlowCallbackToken` 按 `sha256(secret:executionId:nodeId:attempt)[0..32]` **派生**，服务端可重算，不必下发、不落库
  - 配置键 `boheng.flow.callback-secret`（默认 boheng-flow-callback-secret，**生产必须改**）
  - 重试换 attempt 即换令牌 → 旧尝试的迟到回调打不进来
- 结算：`FlowSignalDispatcher.externalCallback`（先 TenantUtils.executeIgnore 查 tenantId 再 execute 进租户）/ `externalCallbackSignal`（令牌校验 + signal_id 幂等 + settle）
- 等待行定位用新 mapper 方法 `selectWaitingByNode`（因为 `selectLatestAttempt` 写死 iterationNo=0，循环内节点查不到）
- 超时：`deadlineOf` 把 EXTERNAL_CONFIRMATION 与 DEVICE_CALLBACK 并列按节点超时；Sweeper 加 `externalCallbackTimeout` 分支

### 顺手修掉的既有缺陷
1. **`RuntimeNode.runValue` 对 String 恒返回 null**：`JSONUtil.toBean("output.weight >= 0.95", String.class)` 把裸字符串当 JSON 解析 → null。
   影响面不止 completeWhen，**节点级 failureStrategy 覆盖一直是失效的**。已改为 String 直接 `.toString()`。
2. **flow 模块测试源集编译不过**：`spring-boot-starter-test` 在 boheng-dependencies 里排除了 mockito-core，模块又没补 mockito-inline。
   → `WaterRegisterTraceTest` / `FlowSignalDispatcherTest` 之前根本跑不起来。已在 flow/pom.xml 补 mockito-inline。

## 第二轮：把「判定单点化」补成可用的闭环

上一轮后端逻辑通了，但用户拿不到、对方回调不进来。这一轮补的是可达性。

### A. runConfig 打通全链路（原来只有 DO 层有）
- 病根：`FlowNodeDO.runConfig` 存在，但 **VO 和接口全没暴露**，前端 grep `runConfig` 0 命中 → 节点级超时/重试/断言只能改库
- `FlowRelationUpdateReqVO` +4 字段：`timeoutSec` / `maxAttempts` / `failureStrategy` / `completeWhen`
- **合并语义**（关键约定）：`null` = 这次不动这个键（别把已有断言抹掉）；`0`/空串 = 清掉覆盖回落步骤表
  - 实现 `FlowRelationServiceImpl.mergeRunConfig`，合并进 runConfig JSON 而不是整串覆盖
  - `timeoutSec` 对外秒、落库毫秒（与 flow_step.timeout_ms 同单位）
  - 断言在保存时就 `ExpressionEvaluator.checkSyntaxStatic` 校验（发布期也会拦，但那时用户已离开节点）
- `FlowRelationRespVO` 回带：`runConfig`(原串) + `overrideTimeoutSec`/`overrideMaxAttempts`(仅覆盖值) + `failureStrategy`/`completeWhen`(生效值)
  → 前端才能区分「继承」与「已覆盖」
- `FlowNodeRespVO` 也补 `completeWhen`（定义详情页展示）

### B. 前端运行配置面板
- 新建共享组件 `web/src/components/flow/NodeRunConfigForm.vue`（超时/重试/失败策略/完成断言，每项带 tooltip 说清语义）
- 接入两处（避免实现分叉）：`views/flow/designer/index.vue`（画布抽屉）+ `views/flow/relation/index.vue`（节点编排对话框）
- `el-collapse` 默认收起，已有覆盖时自动展开 + 「已覆盖」角标
- 提交时留空统一送 `0`/`''` 而非 `undefined` —— 否则后端分不清「不改」和「恢复继承」

### C. external.callback 能力目录种子

### D. ★ 补掉真缺口：回调地址从来没交给对方
- 令牌改成派生式后，只保留了**校验**、忘了**下发** → 对方知道路径也永远过不了校验，表现为回调恒 409、节点恒超时
- 新增 `FlowCallbackUrl`：`{base}/app-api/flow/external-callback/{executionId}/{nodeId}?attempt=&token=`
  - 配置键 `boheng.flow.callback-base-url`（注意与设备域的 `boheng.device.callback-base-url` 是**两个键**，前缀 /admin-api vs /app-api）
- `StepOutcome.waitingWithOutput(...)`：等待类节点也能带产出
- `ExternalCallbackStepType.execute` 产出 `{callbackUrl, attempt, counterparty, expiresInMs}`
- `FlowExecutionEngine.settle` 的 WAITING 分支：把产出写 `output_data` + 写上下文（等待期间上游就能转发地址）
