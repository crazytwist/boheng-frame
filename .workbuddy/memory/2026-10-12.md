## 流程引擎两个新能力（校验节点 + 定时启动）

用户需求两条：1）节点执行前要有校验，校验用 JavaBean 做成单独节点，判断需基于**完整上下文**；2）步骤执行可配置按定时任务触发，参照系统 JobHandler 体系。已确认决策：校验不通过走 **fail 出口**（复用分支机制）；定时粒度是**定时启动流程**（JobHandler 按 cron 触发新流程实例，非流程内部 timer.wait）。

### 1. validate 校验节点（boheng-module-flow）
- 常量：`FlowConstants.STEP_VALIDATE = "validate"`
- 白名单 SPI `FlowValidateAction`（`engine/type/builtin/`）：`String validate(Map env, Map args)`，null/空串=通过，非空=不通过原因；`beanName()` 默认类名首字母小写
- 配置 `ValidateConfig`：`beanName` / `argsJson` / `Map<String,List<String>> branches`（pass/fail 出口）
- 执行器 `ValidateStepType`：`type()=validate`、`role()=CONTROL`、`completionMode()=SYNC`、`retryable()=false`；发布期校验 Bean 存在 + pass/fail 出口必填；`execute()` 用 `contextHolder.loadEnv` 拿完整上下文（+`params`），通过 `branch("pass")`、不通过 `branch("fail", {"reason":reason})`
- `StepOutcome.branch(key, outputJson)` 重载；引擎 `settle` 的 BRANCH 分支写 `outputData` + 非空时 `saveNodeOutput`，让「不通过原因」可被 fail 下游按参数映射读

### 2. 定时启动流程（JobHandler 体系）
- `FlowExecutionService.startScheduled(definitionId, inputParams, businessKey, tenantId)`：`TenantUtils.execute(tenantId, ...)` 内查定义、确认已发布（复用 `FLOW_EXECUTION_DEFINITION_NOT_PUBLISHED`），`engine.start(..., "CRON", "job", ...)` 返回运行号
- 新建 `FlowTriggerJobHandler`（`cn.boheng.frame.module.flow.job`，`@Component implements JobHandler`）：解析参数 JSON `{tenantId, definitionId, inputParams?, businessKey?}`，调 `startScheduled`；**不走 @TenantJob**（租户是参数显式指定，避免一条任务串跑所有租户）
- flow 模块 pom 补 `boheng-spring-boot-starter-job` 依赖
- 用法：infra_job 配 cron + handlerName=`flowTriggerJobHandler`，参数放上述 JSON

### 编译
`mvn -pl boheng-module-flow -am -DskipTests -Dmaven.test.skip=true compile` BUILD SUCCESS；FlowValidateAction/ValidateStepType/FlowTriggerJobHandler 三 class 已生成。

### 关键技术事实（写代码必守）
- **全库零 `@Version`**：`DeviceCommandDO.version`、`FlowStepExecutionDO.rowVersion` 都是**普通列不是乐观锁**，任何 `updateById` 都不会冲突
- **slot 状态没有 Java 枚举类**：FREE/OCCUPIED 只在 `MaterialInstanceServiceImpl:67-68` 私有常量；LOCKED/CHECKING 仅存于 `SlotDO` Javadoc + DDL 注释，无常量无分支无写入点

- **设备命令状态是裸字符串**，实际值 `ACQUIRED/WAITING/SUCCEEDED/FAILED/TIMED_OUT`。`DeviceEnums.CommandStatusEnum`（PENDING/QUEUED/RUNNING/SUCCESS）**与实际无一相同且全库零引用**，是最易误导后续开发的一处
- **死字段两处**：`DeviceCommandDO.version`（名为乐观锁实为普通列）、`device_info.inflight_count`（DDL 注释写「与 max_inflight 比较决定能否下发」但代码从不读写）——后者正是修在途上限原子性要用的列
- **设备命令状态分布**：CAS 三处（`completeCallback:193` / `timeout:221` / sweeper 两处 `DeviceCommandMapper:44-66`），裸 updateById 五处（`complete:141` / `awaitCallback:160` / `recordSent:173` / `recordPoll:323` / `fail:292`）
- **`inflightCount` 比较符无 off-by-one**：因 `countRunning` 包含本次自己那条，`> limit` 恰好等价于 `countRunning - 1 >= limit`。另 `DeviceHttpService.invoke` **无 @Transactional**，INSERT 与 COUNT 是两个独立自动提交语句（不是原报告说的「两个事务」）

- **`FlowDeviceTaskMapper.finish` 本来就是 CAS（`:eq status CLAIMED`）但返回值被丢弃两次**（`FlowDeviceTaskService:137` + `FlowSignalDispatcher:158`）→ 接上返回值 2 行即得低成本修复

## Flow 参数来源：default_params 回退合并（B 方案）

用户确认 `{"Seconds":"1000"}` 没进 `flow_device_task.params_json`，追链路后定位根因：
`params_json ← ctx.getParams() ← resolveParams(node,env)`，而 `resolveParams` 只遍历 `node.inputMapping`
（INPUT/NODE/LITERAL），**从不读 flow_step.default_params**（该字段此前是「死字段」，只被
FlowStepServiceImpl 存/读，执行链路不消费）。

### 落地（B 方案：能力目录默认参数真正生效）
- `RuntimeNode` 新增字段 `String defaultParams`（来自 flow_step.default_params 原始 JSON）
- `PipelineGraph.of`：step 非空时注入 `node.setDefaultParams(step.getDefaultParams())`（独立于 stepType 覆盖判断）
- `ExecutionContextHolder.resolveParams`：先 parse default_params 作为基底（非法 JSON 忽略不抛），再叠 inputMapping 同名覆盖
- 测试补 3 例（defaultParamsActsAsBaseWhenNoMapping / nodeMappingOverridesDefaultParams / invalidDefaultParamsIgnored）

### 语义（与 FlowStepDO.defaultParams 注释「节点引用时可覆盖」一致）
- 节点没配 inputMapping → params = default_params 内容
- 节点配了 inputMapping → default_params 全量兜底 + 节点映射同名覆盖
- 注意：default_params 里的 `{"Seconds":"1000"}`（字符串）parseObj 后仍是 String "1000"；
  而节点 LITERAL value="1000" 经 plainValue 还原为 Long 1000。数字/字符串类型要按设备端要求对齐

### 验证
- flow 模块全量测试 40/40 通过（含 FlowGraphCheckerTest 9 / ExecutionContextHolderTest 10 / DagSchedulerTest 13 等）
- 结论：用户只需在 flow_step.default_params 填 `{"Seconds":"1000"}`，节点不配映射即可进 params_json（无需节点级 inputMapping）
