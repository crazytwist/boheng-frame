## 定位确认：我们是**自动化执行平台**（用户 2026-11-21 答复）
- 产出修正文档：`.workbuddy/reference/boheng-execution-platform-positioning.md`
- 关键判断：Benchling 有「流程定义权 + 数据记录权」，**无设备执行权**（物理编排靠伙伴 HighRes/Celltrio/Automata，不支持设备走 file watcher 兜底）→ 对我们不是竞品，是上游/集成目标
- 真实竞争对手：**UniteLabs**（最高威胁：纯软件 + Python SDK + 100+ 连接器 + 开源 + SiLA 2 合规）；Automata LINQ（$45M C 轮，Danaher 系）；Biosero GBG（装机 4.8 万）；Agilent VWorks；Tecan FluentControl；PAA Overlord/Sapio（失败恢复状态机可参考）
- 行业基准：Ginkgo + GPT-5 已跑通闭环（36,000 反应/580 板/15 万数据点/6 轮/成本降 40%）→ 竞争转为「谁当 Lab OS」
- **架构主张：以 run 为中心，不以样本为中心**。Run → Step → DeviceAction + ResourceClaim + Output
- 前一轮建议修正：①schema 字段系统 降 P2 ②唯一性规则 降 P2 ③四类分离 收窄为「资源位置 + 执行结果」 ④API 规范 升 P0 ⑤principal_type 升 P0 ⑥归档 P1
- 新增 P0 三项：设备 capability 模型（action_code + param_schema + 约束 + 耗时 + 并发）、指令契约（command 信封：params/timeout/retry/idempotency_key/precondition）、run_record 运行账本（run→step→action 三层）
- 新增 P1：可恢复执行状态机（失败不重跑全链、断点续跑、人工接管）、事件出口（webhook+重试+死信）、DeviceDriver 适配层收敛厂商 SDK 差异
- 现有资产判定：Flow v3（能力×编排正交）、device-task（设备主动拉取 = 气隙场景结构优势）、Sweeper/FANOUT 幂等、WMS 实例域 = 强项；缺 capability 模型、run 账本、事件出口、驱动适配层

## ADR-001 决定：主轴选「自动化」，样本降为贯穿维度
- 文档：`.workbuddy/reference/adr-001-主轴选择-自动化vs样本.md`
- 结论：**自动化=骨架（决定能不能卖、跑不跑得住），样本=血脉（决定说不说得清）**。主轴 run-centric，样本只保留四件事：标识/位置/状态/消耗流水
- 四条理由：①客户为"线能无人值守跑通"付钱，台账是准入条件不是卖点 ②样本表可复制、驱动/调度/恢复不可复制 ③上游 Benchling/ELN 是样本主数据 owner，我们当 consumer 才不会撞车 ④资产重心已在 flow 引擎
- **硬性边界（code review 检查项）**：设备域 own 能力/驱动/健康；编排域 own 流程定义/run 状态机；调度 own 排队/认领/超时/重试/幂等；样本域 own 标识/位置/状态/谱系/流水，严禁 own 设备控制与流程编排
- **三条不变式**：①样本状态唯一写入口是 run 结算，设备只上报结果 ②任何 run 对样本的影响必须能在 ledger 找到行 ③样本域不存"经过哪些设备"
- 铆接层新增两表（SQL 已写在 ADR）：`flow_run_record`（含 **flow_version** 锁历史版本，trigger_type/trigger_by 记录 principal）、`flow_run_io`（direction INPUT/OUTPUT、status_before/after 冗余、idempotency_key、occurred_at 与 create_time 分离）
- 遵循底座约定：不建 UNIQUE、幂等靠 Service 层 + idempotency_key
- 三段路线：①自动化立住（capability+command+run 账本，出口=能完整回放任意历史运行且不联表查样本）②样本收敛（冻结字段、状态变更只由 run 结算，出口=样本表零新增加列）③反向输出（事件 + 追溯视图 + 对接包）
- 翻转条件（4 条）：客户是样本库/预算科目是样本库建设/自动化工作量<30%/需与客户 LIMS 双向同步主数据 → 翻转代价约 3~6 个月重做简化版 Registry

## 代码结构核实（wms / sample 归属）
- `boheng-module-wms/src/main/java/.../wms/service/` 下 **7 个平级子域**：container / content / instance / sample / movement / slot / zone
- 契约在 `boheng-module-wms-api`：SampleApi + SampleStatus + MaterialApi + TransportWmsApi（+dto）
- 结论：sample 是 wms 内**平级子域**，不是"wms 的一个方向"；wms 本质是「物料与资源域」而非仓库域（空间/承载/身份/变动四组语义）
- ⚠️ **现存边界违规**：`boheng-module-flow/.../flow/engine/sample/` 下有 8 个 Water*Action（水质检测示例：登记/分液/合并/滴定/金属前处理/报告），落在 **engine 核心包**且直接读 `env` Map 魔法字符串（"node"/"register"/"output"/"samples"）。engine 其它子包（dispatch/execution/expression/route/signal/type）都是机制 → 业务语义污染编排域，建议迁至 `flow/action/water/` 并加 ArchUnit 规则禁止 engine 反向依赖业务包
