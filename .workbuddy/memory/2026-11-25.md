## AGV genAgvSchedulingTask 契约重建 + 模板内置函数 ${randomHex(n)}
- 报错「设备动作参数不合法：未定义参数 clientCode」来自 `DeviceParamResolver.rejectUnknownParams`（1004002005，**调用期**），不是保存期
- 根因：原 param_schema 是**旧标量简写**（`"podCode":"100001"` 这种示例值），只 11 个字段，缺 clientCode/ctnrCode/ctnrTyp/data/materialLot/tokenCode；用户把厂商完整 16 字段报文当参数传 → 首个缺失键 clientCode 被拒
- 另两处也不对：`request_template` 与 `result_rule` 都是 NULL → reqCode 只能靠调用方传，无法保证每次不重复；也没法判成败
- **`${uuid()}` 不能当 reqCode 用**：它是 36 位带连字符小写，AGV 要 16 位大写 hex（样例 `8FADAE4C08FD0044`）
- 新增内置函数 `MessageTemplateFunctions`：`${randomHex(16)}`（位数省略=16，1..128 夹取，非数字回落默认，SecureRandom + HexFormat 大写）；同步放宽 `DeviceTemplateChecker.FUNCTION_CALL` 为 `name(args)` 并改用 `isSupportedFunction()`；不认识的函数原样保留不静默吞掉；加 `Matcher.quoteReplacement` 防替换值里的 $ / \ 被当分组引用
- SQL `sql/mysql/device-agv-migrate.sql`（幂等 UPDATE）。**最终形态（用户确认）只有 4 个字段**：
  `{"agvCode":"1900","reqCode":"${randomHex(16)}","taskTyp":"${taskTyp}","wbCode":"006800BB031000"}`，param_schema 只有 `taskTyp`（required，无默认）
  - agvCode=1900 / wbCode=006800BB031000 写死为协议常量；reqCode 内置函数；taskTyp 是唯一业务输入
  - **reqCode 刻意不进契约**：由平台生成；调用方硬传会被 rejectUnknownParams 拒（避免两条任务共用流水号）；将来要调用方指定则改回 `${reqCode}` 并补契约
- 中途踩过的弯路：第一版把厂商 16 字段全塞进契约（15 个参数、全给 default），属于"把 schema 当成报文镜像"的过度配置，流程侧被迫传一堆无意义空值 → 已按"只声明业务输入"收敛回 1 个参数
- 实测（48199 + 本地假 AGV 18099）：`{"agvCode":"1900","reqCode":"E150373594E5A76F","taskTyp":"Task01","wbCode":"006800BB031000"}` 与 `...reqCode:"EDE5249F5C683EF6","taskTyp":"Task04"...`；不传 taskTyp → 1004002005 缺少必填参数 taskTyp；硬传 reqCode → 未定义参数 reqCode
- 单测 `AgvTaskCommandTest` 9 项；device 全套 51 项过
- ⚠️ `result_rule` 仍为 NULL：海康 RCS 回 `{"code":"0","msg":"success"}`，目前靠 DeviceResultJudge 兜底判成功，`code != "0"` 的业务失败会被漏判。建议补 `{"successCodePath":"$.code","successCodeValues":["0"],"messagePath":"$.msg"}`

## ★ 参数配置方法论（对接两个设备后总结，四分类）
| 类别 | 判断标准 | 放哪 |
|---|---|---|
| 业务输入 | 换一次调用就变、由流程决定 | param_schema，required |
| 协议常量 | 同动作永远一样 | 模板硬写，**不进 schema** |
| 协议流水号 | 每次要新的 | 模板内置函数 `${uuid()}` / `${randomHex(n)}`，**不进 schema** |
| 设备身份 | 同类设备不同实例不同 | 目前无落点（见下） |
- 口诀：**"这个值换台设备、换次调用还会不会变"**
- 设备身份建议：不新增列，用 device_info 现成的 `model`(型号) / `serial_no`(厂商编号) / `vendor`，注入成 `${device.xxx}`（flatten 已支持点路径，渲染逻辑零改动）
  - 不要用 `device_code` 承接：它是平台逻辑名（可改、给人看），厂商编号是不可变事实；绑死会让"设备改名"变成"改协议标识"
  - **疑似 HPLC 报文错误**：请求模板写 `"DeviceId":"S6000PLUS"`（型号），但厂商回调报文里是 `"DeviceId":"1"` → 该字段多半是设备编号不是型号，待厂商确认
- 待做（已向用户提过，未批准）：P0-1 参数值 JSON 转义（renderValue 目前裸拼，值含 `"` 破包，HplcRotateCommandTest 有用例锁着这个坏行为）；P0-2 preview 预渲染接口；P1-1 `${device.xxx}` 注入；P2 result_rule
- 验证手法存档：真机不能乱发指令时，把 endpoint_url 临时指到本地假 HTTP server，既能看渲染报文又不动设备（指到 127.0.0.1:9 会 ConnectException，request_json 不落库，看不到报文）

## AGV 第二答真实报文核对 + 回调「终态」闸门
- 用户给的真实第二答（POST，海康 RCS 风格）：
  `{"reqCode":"1541954B96B1112","reqTime":"2019-04-03 10:08:06","cooX":"3000","cooY":"21999",

    "podCode":"100001","podDir":"0","robotCode":"6001","taskCode":"test169E0F39740116Q_ECS","wbCode":"p02"}`
- 三个结论：
  1. **关联键 `$.reqCode` 是对的**——设备会把我们下发的 reqCode 带回来（之前悬着的那个问题就此关闭）。
     注意样例里 reqCode 是 15 位（`1541954B96B1112`），我们生成 16 位（`8FADAE4C08FD0046` 也是 16 位），厂家协议本身没卡长度。
  2. **报文没有 `code` / `message`**——result_rule 里那条 `successCodePath=$.code` 在这份报文上取不到值，
     靠「字段缺失跳过」才放行。这条规则实际只对第一答（受理）有效，第二答的成败判不了。
  3. `taskCode` 和我们下发的 `data`（`Task01_xxx`）不是一回事，**不能拿 taskCode 关联**，只能用 reqCode。
- ★ 真问题：`method` 是阶段标识。原来「收到第一条就结算」，若 RCS 也推 `start`/中途回调，
  会把还在路上的车判成完成 → 流程带错结论往下走 → 给忙车派新任务；真正的 end 报文只会收到 409。
- 修法：`result_rule` 支持可选终态闸门
  `{"settlePath":"$.method","settleValues":["end"]}`，语义：
  · 没配 settlePath / 配了但 settleValues 空 / 报文没这个字段 / 正文非 JSON → 照旧结算（宁可结算，别卡死）
  · 字段有值且不在 settleValues → **不结算**，回 200「尚未结束」让设备别重发，打 INFO 日志
  实现：`DeviceResultJudge.isTerminal(action, body)`；`DeviceCallbackService` 注入 `DeviceActionMapper`（按
  deviceTypeCode+actionCode 反查动作）与 `DeviceResultJudge`，两条回调入口（带命令号 / 固定地址）都过这道闸。
- AGV 规则定稿：`{"successCodePath":"$.code","successCodeValues":["0"],"messagePath":"$.message",
  "settlePath":"$.method","settleValues":["end"]}`（已写进 device-agv-ack-migrate.sql 并落库）。
- 单测：判定器 +3（终态值 / 判不了时按终态 / 只配 settlePath 不配 settleValues）、回调 +3
  （真实报文结算 / start 不结算 / 缺 method 仍结算），设备域 72 → **78 全过**。
  · 单测坑：测试里的行快照 `copy()` 漏拷 deviceTypeCode/actionCode → 反查动作拿到 null → 闸门静默失效，
    表现成「start 也结算了」。生产走的是整行，不受影响。
- 实测（48199，AGV 端点临时指本地桩，验完已还原）：
  · `method=start` + 我们的 reqCode → HTTP 200，命令仍 WAITING，日志「还没到终态，命令继续等待」

## 两条 WARN 属误报，已修（跨设备流程日志复盘）
用户贴了 48088 完整跑通日志（AGV→HPLC→AGV→AGV→HPLC→AGV，结束 SUCCESS），里面有两条反复出现的 WARN，

### ① `DeviceResultJudge: [ruleSuccess][规则要求 $.code 但报文里没有该字段，跳过这条判定，请核对 result_rule]`
- 为什么每条 AGV 回调都打：AGV 的 result_rule 有 `successCodePath=$.code`，
  而**受理应答有 code、第二次回调（method=end）没有**。同一份 result_rule 要同时判两种报文，
  缺字段是按设计放行的（`matches` 里缺字段 return true），所以每条回调必然走到这一行。
- 结论：配置是对的，「请核对 result_rule」是错误指引。
- 改法：不降到 debug（会把「路径写错」这种真问题也吞掉），改成**同一动作+同一路径只 WARN 一次**
  （`Set<String> missingFieldWarned = ConcurrentHashMap.newKeySet()`，键 = `类型.动作|路径`）。
  实测 5 条回调只出 1 行 WARN；判定结论不受影响（新增 `shouldJudgeEveryCallbackEvenAfterMissingFieldWarned`）。
- 新增 `sceneOf(action)` = `deviceTypeCode.actionCode`，`ruleSuccess/matches` 多带一个 scene 参数。

### ② `DeviceCallbackService: [issue][设备(X) 未配置 boheng.device.callback-base-url，回调地址落到本机回环，真设备访问不到]`
- 事实核对：`application.yaml` 里是 `callback-base-url: ${BOHENG_DEVICE_CALLBACK_BASE_URL:}`，预发/本地都没设 → 必然触发。
  但该部署里 HPLC 走 `/api/OnResponse`、AGV 走 `/api/agv/callback`，**地址是厂商写死的，我们签发的 URL 根本没用**，
  所以「真设备访问不到」是误导性结论。
- 改法：① 每次下发都打 → 改 `AtomicBoolean loopbackWarned` **进程内只提示一次**；
  ② 措辞改成「设备若按固定地址回调可忽略，否则请配置为设备能访问到的平台地址」。
