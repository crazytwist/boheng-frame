## 伯珩 Flow 参数传递 vs Dify 变量系统（对比结论）

- 取向差异：Dify=面向 LLM 文本流的**插值型**（{{#node.field#}} 模板渲染 + 12 类 SegmentType 强类型 + 聚合器/会话变量）；伯珩=面向设备结构化指令的**绑定型**（param ← {INPUT/NODE/LITERAL + field 路径} 结构化绑定 + DAG 直接前驱强校验）

## deploy.sh migrate NUL 传参 bug + 修法

- 症状：第一次跑后看到 `⚠️  远端不存在: flow-input-params-migrate.sqlflow-step-output-schema-migrate.sqlflow-v3-migrate.sqlwms-sample-migrate.sql` —— 4 个文件名连成一串
- 原因：`CAND_ARG=$(printf '%s\0' "${files[@]}")` 通过 SSH `bash -s "$CAND_ARG"` 命令行参数传 NUL 分隔字符串，远端 `xargs -0 -n1 echo` 把整个串当单参数 `echo` 输出（不是 -0 拆不开就是 echo 吞了 NUL）
- 副作用：preseed 表已建 + 历史预置已写入（这部分对），新迁移没跑（要补）
- 修法：候选列表改成**写本地文件 scp 到远端**，远端 `while IFS= read -r filename` 逐行处理
- 经验：跨 SSH 传数组用**文件**最稳，NUL/换行经命令行参数转义不可靠
- 重跑 `--migrate-only` 即可补上 2 个未跑的 ALTER TABLE（幂等）

## deploy.sh 远端 REMOTE_DIR 默认值 bug + 统一修法

- 症状：发布段报 `cd: /opt/boheng: No such file or directory`（.env 配的是 /home/megarobo/boheng）
- 根因：`<<'REMOTE'` 单引号 heredoc 不做本地变量展开；远端 `REMOTE_DIR="${REMOTE_DIR:-/opt/boheng}"` 永远拿不到本地值，掉默认
- 修法：所有 `<<'REMOTE'` 块统一改成 `bash -s "$VAR1" "$VAR2" ...` 显式传位置参数，远端 `var="$1"; shift` 接住
- 同步检查：之前迁移函数已经用这种模式，但发布段漏了；这次修了 1 处
- 教训：bash heredoc 跨进程传参永远走**显式位置参数**最稳

## deploy.sh: apply_migrations: command not found bug + 公网 28081 DNAT 诊断

### Bug 1: 函数跨进程可见性
- 症状：发布最后一段报 `bash: line 28: apply_migrations: command not found`
- 根因：`apply_migrations()` 是本地脚本 shell 函数，但被错误地放进 `<<'REMOTE'` heredoc 里在远端 bash 进程调用；远端 bash 看不到本地函数
- 修法：从 heredoc 内部挪出来，在 heredoc 结束后于本地进程调用（函数内部本来就有自己的 SSH 调用，自洽）

### 端口配置（公网 28081 不通的根因）
- 用户截图：浏览器所有 `/admin-api/*` 请求都 Connection refused
- SSH 进去探测：
  - 内网 `10.10.2.100:48080` HTTP 200 ✅（web → server 反代全通）
  - 容器内 `boheng.web` → `boheng.server:48080` 返回 `{"code":401,"msg":"账号未登录"}` ✅（401 = 没带 token，预期）
  - server 日志：Tomcat started on 48080 + 项目启动成功，无 ERROR
  - MySQL 日志：InnoDB ready for connections
  - **公网 `123.59.127.6:28081`** Connection refused ❌
- 根因：docker web 宿主端口刚改成 48081，但**网关机上的 DNAT 还在老端口 48080**（或者根本没 DNAT 28081 这一条）
- 网关 DNAT 不在 docker 主机能力范围内（10.10.2.100 无公网 IP，真公网网关在上游，arp 表里看不到任何机器监听 28081）
- 用户拍板选 A：docker 端口**改回 48080**（对齐现有网关机 DNAT 28081 → 48080）

### deploy 验证
- 重跑 `./deploy.sh`：web 容器 `0.0.0.0:48080->80/tcp` ✅，SQL 迁移 4 个候选全部「跳过（已应用）」✅
- docker 全链路 100% 健康，公网侧等用户在网关机/路由器后台确认 DNAT

### 经验
- **docker compose 宿主端口** vs **公网入口端口** 是两件事：公网入口由网关机/路由器 DNAT 决定，docker compose 改宿主端口必须同步通知网管更新 DNAT，否则立刻掉线
- **RST vs timeout**：Connection refused = 对端 RST（收到包但没人监听）；connection timeout = 包根本没到对端。两者诊断方向不同
- 网段内 `for ip in ...; do timeout 2 bash -c "exec 3<>/dev/tcp/$ip/28081"; done` 能快速确认 DNAT 目标是否在该网段内

## 端口 48 段 vs 28 段：用户 .env 真相 + 两个隐藏 bug

### 真相
- 用户 `.env` 实际是 **28 段公网端口**：PORT_WEB=28081 / PORT_SERVER=28088 / PORT_MYSQL=28086 / PORT_REDIS=28082
- 我之前误判成 48 段规则（48080/48081/48082/48083），是因为之前设计文档是 48 段，但用户实际部署早就切到 28 段
- **判断依据**：直接 `grep PORT_ deploy/boheng/.env` 看用户的实际配置，而不是凭历史印象

### 两个隐藏 bug
1. **deploy.sh heredoc 强制 fallback 覆盖 .env 值**
   - `PORT_WEB="${PORT_WEB:-48080}"` 在 heredoc 里执行，**如果 .env 没 export 到新 bash 进程**，fallback 48080 会盖掉 .env 里的 28081
   - 修法：fallback 直接对齐 28 段：`PORT_WEB="${PORT_WEB:-28081}"` 等

2. **`docker compose up -d` 不重建容器时端口不刷新**
   - 症状：`docker compose config` 解析出 `published: "28081"`，但容器实际仍跑在老端口 `48080`
   - 原因：image 没变 → compose 认为容器无变化 → 端口保持
   - 症状细节：`docker ps` 是 48080，`docker port web` 也是 48080，但 `compose config` 是 28081
   - 修法：`docker compose up -d --force-recreate web` 强制重建 web
   - 教训：改 yml 的 ports 后必须 --force-recreate 对应服务，否则端口"卡"在老值
