### 代码事实（已核对源码，非推测）
- 153 Java 文件 / 12,810 行；12 张表；引擎 `FlowExecutionEngine` 1,117 行是唯一推进器
- 引擎不持有内存态运行对象：每轮 `advance` 从库重装（`loadGraph` + `selectByExecutionId`），任意实例可接管
- 并发唯一机制 = CAS（`UPDATE … WHERE status='PENDING'`）；无分布式锁
- 并行 = 就绪判定天然结果（`DagScheduler.decide` 纯静态函数），没有 fork/join 节点
- loop 由引擎按 `sort_no` 区间展开子图（`loopBody`），不递归；subflow 建子执行 + CHILD 信号汇合，FANOUT 幂等靠 `business_key` + `uk_flow_execution_fanout`
- 11 种步骤类型：ACTION(5) / WAIT(2) / CONTROL(3) / SUBFLOW(1)；`StepTypeRegistry` 启动期自检，缺执行器直接起不来
- 设备两类：`device.command` 推（阻塞，占 worker 线程）/ `device.task` 拉（callbackToken 常量时间比对）
- 上下文三层命名空间 INPUT/NODE/SYSTEM，`pathGet` 支持 `a.b[2].c`；`encodeValue` 必须 `JSONUtil.quote(String)`，否则 MySQL JSON 列报错

### 发现的风险（写进 §14，按严重度）
- **R1 定义漂移不检测**：`loadGraph` 每次按 definition_id 重查，从不比对 `execution.checksum`；`FLOW_EXECUTION_CHECKSUM_DRIFT` 错误码声明了但全模块 0 处使用；`rollbackDraft` 允许已发布版本退回草稿再改 → 运行中改图会影响在跑的运行
- **R2 RUNNING 无租约**：进程崩溃后节点行永久 RUNNING，`selectWaiting` 只捞 WAITING → 僵尸运行永不终态
- **R3** worker 池固定 8 线程，device.command 阻塞占线程
- **R4 分支裁剪会误裁汇聚节点**：BranchResolver 的 BFS 只看扇出不看「是否还有存活入边」
- R5 递归推进（settle→advance→dispatch→settle）；R6 上下文每次全表装载；R7 loop body 内 route 指向外部节点不成立；R8 PENDING 运行态未使用；R9 flow_error_action 无运行期消费者；R10 设备任务认领无优先级
