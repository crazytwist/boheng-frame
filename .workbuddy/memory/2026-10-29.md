# 2026-10-29

## Transport V1.0 方案收敛（评审 → 定稿）

对 `boheng-module-transport` 做了两轮评审：先代码层（901 行，10 表 DDL + 1 个受理 + 6 个假 Bean），后方案层。最终按用户约束收敛。

### 用户拍板的约束与决策

- **D1 驱动模型**：Flow 是唯一推进器（可复用）。Transport 不跑后台 sweeper、不做超时/重试编排。→ operation 降级为「命令台账」；锁过期改惰性清理（acquire 时清 expire_at < now）
- **D2/D3**：单 AGV（多 AGV 路线不冲突）、单厂区（不做 site，tenant 即现场）
- **D5 槽位互斥归 WMS**：理由是「出入口物理上只有一个 AGV 位」，只有知道物理拓扑（slot.device_code/capacity）的一方能仲裁。→ local_lock 的 resource_type 收缩为 EXECUTOR/DOOR/MACHINE_INTERFACE/CHARGER
- **D6 route 与 flow 解绑**：route 只描述工艺，Flow 以 routeCode 作启动参数
- **D7 一趟多件物料**（否决「每趟一个物料」）→ stop/operation 必须保留
- **D8 托板模式**：AGV 自带托板（工装，非 WMS 载具），N 件装一板，place 一次、handover 一次、WMS 产生 N 条移动流水
- **D9 多终点预留不实现**：stop 允许多条 DROPOFF，order.current_stop_seq 推进

### 关键技术判断（值得复用）

- 多起点多终点不需要新表：`item` 自带 source/target 就是载体。**order 上绝不能存 source/target**，否则多起点永远做不了
- 决定 stop/operation 存废的变量不是「V1 简不简单」，而是「一趟跑几件物料」
- 原流程图 8 处缺陷：DROPOFF stop 在循环体内会撞 stop_seq 唯一键；local_lock 每轮重建会锁自己；终点接收位每轮重查会导致目标位不一致；AGV move 每轮空驶；WMS 流水/item 更新应为 N 条；失败出口按阶段拆；缺终点位释放；缺 order 完成收口
- 修复：event/evidence/lock_ref 三表缺 5 个审计列（DO 继承 TenantBaseDO）→ 实测 `WHERE deleted=0` 报 1054，已补齐
- `uk_transport_order_seq(request_id, sequence_no)` 与重排（plan_version 递增）冲突，已删除该唯一键
