## 实例域新增 v1.2（容器模型：类型 / 实例 / 内容物）

### 背景
用户要求「不急写代码，先把表结构了解清楚」，在已定的空间域之后设计三张新表：
容器类型表、可无限嵌套的物料实例表、内容物表。
**盘点结论**：原设计稿 14 张表里没有容器模型，属全新增（原稿已存档于
`.workbuddy/reference/lab-wms-ddl-v1.0-original.sql`）。

### 8 条决策（全部经用户逐项确认）
1. **实例/内容物边界**：能独立取放、可单独追踪的物体建实例（管/板/盒/瓶）；
   依附容器、拿不出单独搬的物质记内容物（液体/样本/散装物）
2. **记账分层**：`wms_inventory` 管槽位级，`wms_instance_content` 管容器内，聚合键不变
3. **容器类型独立成表** `wms_container_type`，`wms_material_info` 只加 `container_type_id`
   - 用户先选了「不建表，字段加进物料表」，与开场需求「需要一个容器类型表」矛盾，
     给出对比（板型复用 / 非采购容器 / 设备适配 / 物料表宽度）后改选**独立表**
   - 核心理由：设备适配认**板型**不认物料，换供应商不该改设备配置（Tecan 对接场景）
4. **表名** `wms_material_instance`（不用 container_instance）
5. **实例可不落位**：`root_slot_id` 可空（运输中 / 在设备上 / 临时取出）
6. **嵌套结构**：树边 = `parent_instance_id` + `parent_position_code`
7. **slot 占用方改口径**：`occupied_material_id/code` → `occupied_instance_id/code`
   （理由：槽位上放的多是一个实例（一盒/一板），不再是裸物料）
8. **实例编码**：系统按「板型编码 + 流水号」生成，`barcode` 字段可覆盖

### 关键概念（后续写代码的防混淆约定）
- **两套「位置」**：`slot` 是空间位置（架子第 3 格）；`position_code` 是容器内位置（板子 A1 孔）。
  一块 96 孔板占 **1 个 slot**，内部 96 个孔是实例层坐标，**不落 slot 表**。
- **分层记账示例**：inventory 记「该槽位放着 3 盒枪头」，content 记「盒内剩 86 支」。
- **两级数量口径不强制换算**：inventory 用库存单位、content 用计量单位；
  换算依据落在 `container_type` 容量字段，需要时再补。

### 执行约束（已写进 SQL 注释）
- `MAX_INSTANCE_DEPTH = 16`（受 `instance_path` varchar(512) + 前缀索引 64 容量约束）
- 不允许删除仍有子节点的实例（否则 path 断裂），由 Service 层校验
- 嵌套成环由应用层防护（深度上限 + 祖先链校验，参考 zone 树 `MAX_ZONE_DEPTH` 做法）

## 空间域 / 实例域字段收敛 v1.3

> 用户要求「一张一张来，先把表结构了解清楚」，并圈出 slot 表上 9 个字段让我「斟酌」。
> 结论：这 9 个字段是三组语义挤在一条记录里，其中一组站错了位置。**只动表结构，不碰 Java。**

### 用户圈定的 9 个字段与最终处置

| 组 | 字段 | 处置 |
|---|---|---|
| ① 设备位置映射 | `device_code` / `device_slot_no` | `device_code` 保留；`device_slot_no` → 更名 **`device_position_no`**（厂商位置标识 vs 内部 slot_code 职责分离） |
| ② 物理占用 | `occupied_instance_id` / `occupied_instance_code` / `occupied_time` | **前两个删除**；新增 **`occupied_qty`**（已占标准位数）；`occupied_time` 保留 |
| ③ 逻辑预留锁 | `lock_source` / `lock_ref_id` / `lock_time` / `lock_expire` | **整组删除**（用户拍板） |

### 删 ② 的两条硬理由（核心决策）
1. **「实物 → 位置」只能有一个可写方向**：真相源是 `wms_material_instance.root_slot_id`（已有索引）。
   双向冗余会导致「整盒移动」时必然双写，一定有不一致窗口。
2. **`capacity > 1` 时一个 bigint 装不下多个实例** —— 从建模上就不成立。
   → 改为 `occupied_qty` 表达占用程度，且与 `slot_status` **同源**（qty=0 ⟺ FREE），
   由同一业务方法维护，禁止只改其一。

### 删 ③ 的理由（用户比我更彻底）
预留锁（谁锁的、何时过期）**属调度域，不是仓储档案**。slot 只用 `slot_status` 的
`LOCKED` / `CHECKING` 表达「暂不可用」，不携带元信息。
代价已写进注释：**无法在本表回答「谁锁的、何时过期」**；二期若需要多任务排队竞争、
锁过期自动释放或锁审计，在调度域建独立锁表。

### 实例表（`wms_material_instance`）字段斟酌结论
- **已确认**：实例表已具备上下级能力，树字段保留 ——
  `parent_instance_id` + `parent_position_code`（边）、`instance_path`（物化路径，前缀索引 64）、
  `depth`、`root_instance_id`、`root_slot_id(+code)`
- **保留 `material_id` / `batch_id`**（用户选择）：表达「这件实物本身是哪件采购品」，
  自制工装/周转架留空；密封品与内容物一致，分装/混合场景则不同
- **删除 `device_code`**：「在设备上」统一由 `root_slot_id` 指向 `slot_type = DEVICE` 的槽位表达，
  避免同一事实两个写法
- **`instance_status` 移除 `LOCKED`**（与第 ③ 条一致）；取值 = IDLE / LOADED / CLEANING / SCRAPPED
  - IDLE / LOADED 保留为**便捷状态**（本可由子实例/内容物推导），目的是列表页免 join，
    注释已标明「只做展示缓存，不可单独写」
- **`instance_status` vs `status`**：`status` 0/1 是「启用/停用」，`SCRAPPED` 是报废终态，两者不重叠

### 三种绑定关系的正式表述（写进 SQL 注释第 1–3 条）
1. **规格绑定** → `wms_container_type`：`container_type_id/code`（必填）
2. **落位绑定** → `wms_slot_info`：`root_slot_id/code`（可空 = 运输中/在设备上/临时取出）
3. **内容绑定** ← `wms_instance_content`：该表以 `instance_id` 反向引用（1:N），实例表不存内容物

### 整树冗余的写入口（重要约束，写进注释第 6 条）
`root_slot_id/root_slot_code/root_instance_id/instance_path/depth` 是整树冗余。
**移动整棵子树必须用一条路径前缀 UPDATE**，禁止绕过它单改某一层：
```sql
UPDATE wms_material_instance SET root_slot_id = ?, root_slot_code = ?
 WHERE instance_path LIKE CONCAT(?, '%') AND deleted = b'0';
```
跨父搬迁还需同步重写 `instance_path` 与 `depth`（同一事务内）。

### 落地结果：DDL v1.3
- 文件头：版本 `v1.2` → **`v1.3`**，差异说明新增 **18–22 条**
- `wms_slot_info`：删 6 字段、加 1 字段、改 1 名；索引 `idx_occupied_instance_id`、`idx_lock_expire` 删除，

- **校验**：18 张表全部通过列定义解析（括号平衡、末尾元素为索引/主键），异常 0 张

### 我上一轮的理解偏差（已纠正）
用户说的「一个内容物的表」= **`lab_material_def`（内容物「定义」，物质属性字典）**，
**不是** `wms_instance_content`（实例内容物）。原设计里**内容物是内联在实例上的**
（`content_type` / `material_code` / `batch_no` / `current_vol_ul` / `current_count` 都是实例表的列）。
它能内联，是因为**孔也是实例** —— 1:1 挂得住。我却建了 1:N 的 `wms_instance_content`，
等于把同一件事拆成两张表。

### ★ 核心决策：位置也是实例
`hierarchy_role = WELL` 的孔/位**也是实例**，不是坐标。因此内容物 1:1 内联，
**删除 `wms_instance_content`**，字段并入实例表 `content_*` 组。

| | 原设计（位置即实例） | 旧现设计（位置是坐标） |
|---|---|---|
| 同一场景（96 孔板放料架，A1 孔 200µL 血清） | **97 行**（1 载体 + 96 孔，空孔也建行） | **2 行**（板 1 + 内容物 1） |
| 优点 | 模型统一（「孔」与「15ml 管」结构同构，代码一套）；每孔独立挂批次/效期/状态/来源实验 | 行数少，空位不占行 |
| 代价 | 行数膨胀 | 实例与内容物两套概念并存；内容物拿不到完整生命周期与溯源 |

## 修正 VO 包结构（去多余层级）

用户发现 `vo.xx` 多了一层：`controller/admin/{domain}/vo/{vo}/` 冗余。

### 根因
生成器里 `domain` 和 `vo` 是两个独立维度。zone/slot 两表 domain 与 vo 同名
→ `vo/zone/zone/` 多一层；container/content/instance 三表 domain≠vo，恰好单层（歪打正着）。

### 收敛方案（用户选「vo 下直接放类」）
把 `vo` 维度彻底并入 `domain`，VO 直接放 `controller/admin/{domain}/vo/` 下：
- 删除元数据 `"vo"` 字段
- package/import 里 `vo.$vo` → `vo`
- write 路径 `vo/{vo}/` → `vo/`
- `URL_BY_VO` → `URL_BY_DOMAIN`，key 改 domain 值（zone/slot/container/content/instance）
- Controller 里 `URL_BY_VO[t["vo"]]` → `URL_BY_DOMAIN[t["domain"]]`

### 附带清理
- 删旧代码时只删了 .java 没删目录，残留 13 个空目录
  （zonematerialtype / batch / inventory / material / order 等废弃表目录）
- 用 `find -empty -delete` 会把整条空链连 `src` 一起删掉，生成器会自动重建，无碍

### 结果
- 41 个 Java 文件，VO 全部 `vo/` 单层，无空目录，编译零报错
