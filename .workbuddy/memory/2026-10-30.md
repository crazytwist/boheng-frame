## 消息中心 / 设备报警设计（产出 doc/10-消息中心与设备报警设计.md）

### 现状四个硬事实（调研结论）
- `system_notify_message` 83 条全是芋道 demo（hrm_performance/test），站内信业务未使用 → 改造无包袱
- `device_data_raw.command_id` 是 **NOT NULL** → 设备主动上报（无命令）无处可落
- `DeviceCallbackController` 必须带 commandNo / X-Command-No → 只能收命令回调，收不了设备主动报警
- 无 alarm 表、无设备事件表、无 SSE/WebSocket 基建（全仓 grep 无 SseEmitter）

### 核心判断
**报警 ≠ 消息**。notify_message 是「一人一条 + read_status 一个 bit」，装不了报警的生命周期/聚合/处置。设计分三层：事件流水（事实）→ 报警中心（状态）→ 投递（渠道）。不推翻 notify，只补报警实体。

### 设计要点
- 4 张新表：device_event_log / alarm_code / alarm_record / alarm_action；个人消息复用 system_notify_message
- `alarm_record.active_guard` 生成列 + 唯一键（status IN ACTIVE,ACKED）→ 重复上报撞键转 UPDATE，天然聚合，不靠先查后写
- ACKED 仍占唯一键（确认 ≠ 恢复）
- 未登记报警码不阻塞：默认 WARN + 自动登记 auto_created 字典项
- 抑制三来源取最晚：码配置窗口 / ACK 后静默 / 设备 MAINTENANCE 降级
- 新入口 POST /app-api/device/event/report（批量 50 条、dedup_key = deviceCode+code+occurredAt、不阻塞设备）
- 模块归属：新建 boheng-module-alarm + alarm-api（不进 device，避免反向依赖）

### 待用户确认
1. 厂商报警码表是否提前导入（建议：先自动登记跑通）
2. 设备是否支持回传报警恢复信号
3. V1 是否要企业微信/钉钉 Webhook

## 参考项目调研：librax-lab / 清华（/Users/yinan/workspace/megarobo/qinghua）

### 他们的实现
- `machine_error` 报警码字典（alarm_code/fault_desc/solution）
- `device_log` 异常流水（abnormal_grade 0-3、handle_status 0/1/2，自增 504，代码中无读写）
- 实际用 `sys_operate_log` 承载报警（bizType=ErrorReport）
- `messages`/`message_instance` 建表但无任何读写代码
- 接口：TsinghuaMachineErrorController 的 /alertError、/errorReport、/errorHandle、/searchHandle
- 投递：自写 WebSocketSessionHolder 广播 + 邮件

### 吸收（已改 doc/10）
1. 报警码字典带 solution，详情页必须展示处置建议
2. **处置指令回传**（searchHandle 模式）→ 新增 4.6：alarm_record.resolution_code + 设备轮询 GET /app-api/alarm/resolution，取走即标记 resolved_pulled_at
3. WebSocket 广播 + 轮询兜底（boheng 框架自带 WebSocketMessageSender，支持 Redis 广播，无需自建）
4. 设备只传报警码，level 可选、以字典为准

### 避开的坑（写进 doc/10 第 13.3）
1. 用 sys_operate_log 冒充报警表（success 布尔表达不了生命周期，处置结果塞 msg 字段）
2. 三接口主键语义不一致：errorReport 写 bizId=errorKey，errorHandle 用 logId=errorKey 查（logId 是 UUID）→ 永远查不到
3. 字典未命中直接 NPE
4. 一条上报一条记录无聚合
5. device_name 而非 device_id、无 tenant_id/索引、正则 User=(.*?)Authorization= 从 sessionKey 提 userId
