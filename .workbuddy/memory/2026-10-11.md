## 流程设备异步任务 device.task（提交 323dec7）

需求：流程推进时有些节点**不主动推设备**，而是把任务存入队列，由机器端拉取→执行→回报完成，再往后推进节点。

### 设计（Camunda external-task 模式，复用既有 CALLBACK/信号链路）
- 新增步骤类型 `device.task`（`FlowConstants.STEP_DEVICE_TASK`）：`StepRole.ACTION` + `CompletionMode.CALLBACK`，
  `execute` 入队并返回 `waiting("DEVICE_CALLBACK", taskNo)`；与 `device.command`（同步推）正交
- 新表 `flow_device_task`（tenant 表）：`task_no` + `task_no_guard` 生成列 + 唯一索引 `uk_flow_device_task_no`（租户维度）；
  状态机 PENDING/CLAIMED/DONE/FAILED/CANCELLED；`device_code` 可空（不限设备）× `action_code` 必填（按任务类型）
- 认领走 **CAS**（`PENDING→CLAIMED` 条件更新），防多机重复执行；回报走 `CLAIMED→DONE/FAILED` 条件更新

### 落地点
- 引擎：`FlowSignalDispatcher.deviceTaskSignal/deviceTaskTimeout`；`settle` 的 `deadlineOf` 增加
  `DEVICE_CALLBACK` 分支（按节点超时算到期）；`FlowExecutionSweeper.scanOne` 对 `DEVICE_CALLBACK` 到期按失败结算
- 机器端接口（**`controller/app` 包 → `/app-api` 前缀**，与 admin 区分）：`/flow/device-task` claim + complete，
  `@PermitAll` + **`tenant-id` 请求头**限定租户（机器端知道自己的 lab，不走 `@TenantIgnore`）
- 管理后台监控 `/admin-api/flow/device-task/page`，复用 `flow:execution:query`（**无需新增权限 SQL**）
- 前端：`step.ts` STEP_TYPES + `flow-dag.ts` TYPE_META + `StepForm.vue` 三处加 device.task；
  设备可空（任务可不限设备，拉全量动作列表），actionCode 必填

- 前端 `npm run ts:check`：flow 相关零错误（其余 10 处报错均为 ai/chat、bpm、fms、iot、mes 既有模块，与本轮无关）

## device.task 补任务队列基本功（提交 7360a18，参照 labillion task 模块）

用户参照 `/Users/yinan/workspace/megarobo/labillion/labillion-frame` 的 `labillion-module-task` 模块梳理完整链路，
决策：**不照搬整个 labillion 通用 task 模块（对 boheng 过度设计），只补「任务队列基本功」三件套**。

### labillion task 模块要点（作为对照，不迁移代码）
- 定位：**统一任务队列**，一张 `lab_task` 表承载 INSTRUMENT/MANUAL/AGV/COMPUTE 多 taskType（boheng 只有 device）
- 三张表：`lab_task` + `lab_task_event`（INSERT-ONLY 事件流水）+ `lab_task_executor_config`（并发/容量）
- 解耦：`labillion-module-api/flow-api` 零依赖契约层（DispatchSpi + StepCallbackApi + TaskCompletedEvent），
  flow/task/device 都只依赖契约层；task 完成发 `TaskCompletedEvent`（Spring Event）打破 task↔flow 循环依赖
- 状态机 PENDING→EXECUTING（claim 即开始，无 CLAIMED 态）；`deadlineAt` 只展示不判失败，超时归 flow 重试开新 attempt

### 本轮落地（boheng 增量）
- `callback_token`：入队生成（`IdUtil.fastSimpleUUID`），claim 下发，complete 回报时常量时间校验（`MessageDigest.isEqual`）
- 新建 `flow_device_task_event` 表 + DO/Mapper：INSERT-ONLY，CREATED/CLAIMED/DONE/FAILED 每次流转一行
- `wait_ms`（认领-创建）/ `execute_ms`（终态-认领）耗时统计
- 不改「超时归 flow」：Sweeper 本就在 flow 模块扫 DEVICE_CALLBACK

### 结论
- 直接照搬 labillion task = 过度设计（多 taskType/flow-api 契约层/Spring Event 桥是服务多执行单元+多模块的，boheng 只有设备一个场景）
- 只补基本功：安全凭证 + 审计溯源 + 耗时统计，增量不破坏已提交结构
- 未来若出现 AGV/人工/计算任务或脱离流程的独立任务，再泛化成通用 task 模块（且按 boheng 基座重写）
