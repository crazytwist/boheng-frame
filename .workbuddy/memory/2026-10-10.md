## 交付物：`.workbuddy/reference/flow-v3-design.md`（需求理解 + 设计稿）

- 用户给出 Flow 的**完整需求**：步骤可复用、**步骤类型多种**（设备/脚本/JavaBean/人工/通知，「要区分开来」）、
  完成驱动要有**并行/串行/合并/循环/子流程**。本轮要求先「理解」，故只出设计稿不写代码。
- **核心洞察（本文档的骨架）**：Flow = **能力（`step_type`，怎么执行）× 编排（怎么串）**，两维**正交**。
  同一 `device.command` 可串行、可并行、可放进循环体 → **能力 × 拓扑是组合，不是枚举**，不能合成一个枚举。
- **五个词 → 两种机制**：串行/并行/合并 = **依赖边**（扇出/扇入 + `join_policy`，无需新节点类型）；
  循环/子流程 = **结构化容器节点**（把子图包住，对外仍无环）。
- **循环是 DAG 的天敌**：labillion 明写「Flow 只理解 DAG」，**它也没有循环**。
  本设计选**结构化 `loop` 容器**（Airflow/Argo/BPMN 思路，有 `maxIterations` 兜底），
  否决「自由回边」（图不再无环，校验/调度/可视化全变复杂）。
- 五张运行表：`flow_execution` / `flow_step_execution` / `flow_step_signal` /
  `flow_execution_context` / `flow_branch_decision`；**不搬** artifact / reconciliation /
  compensation / event_log / outbox（一期无需求）。
- `flow_step` 加 `step_type` + `type_config`（+ `default_params`）；
  `flow_node` 加 `role` / `completion_mode` / `join_policy` / `branches` / `output_mapping` /
  `node_config`(JSON 覆盖) / `loop_config`。节点级覆盖**用 JSON 而非 4 个独立列**（与 labillion 的差异点）。
- **依赖环境事实**：`boheng-dependencies` 已管理 `aviator 5.4.4`，`boheng-common` 有 `spring-expression`
  → 表达式求值**无需引新依赖**。`script.run` 要跑真脚本需新引 Groovy/JSR-223。
  **本精简基座没有 notify 模块**（infra 只留 job / file / websocket）→「通知」需定出口。
- 分期：P1 类型注册表（定义层）→ P2 运行闭环（+`DeviceCommandApi`）→ P3 bean/script →
  P4 并行合并 → P5 分支 → P6 人工/通知 → P7 循环 → P8 子流程。P7/P8 最重（唯一需要容器语义）。
- **本版最大风险**：v2 的「依赖不由人填」是防错设计（杜绝「画得出跑不了」）；
  放开 `depends_on` 后这条防线要靠**图校验**补回（无环 / join 与前置数一致 / 容器区间合法 / 子流程引用无环）。
- 待用户拍板的决策：① `flow_step` 的 `device_code`/`action_code` 是否收敛进 `type_config`（推荐收敛）；
  ② 循环/子流程是否纳入一期；③ 是否开工。

## 追加需求：节点「拆分」（分支路由）—— 涉及文档 §3.2 重写

- 用户原话：「一个节点的拆分，按照拆分的属性值走不同的分支，这个是不是在 JavaBean 中去拆分，

- **核心边界（本次最重要的结论）**：**决策**与**执行**必须切开。
  - 决策器（表达式 / Bean / 脚本）只做**纯函数**：`上下文 → 一个 key`。**不 import 调度类、不写运行表。**

## 追加需求 + 决策 D7：96 样本拆机 = 子流程 FANOUT 扇出

- 用户提出场景：96 样本拆 48 去机器 A、48 去机器 B，A/B 之后各自跑流程；
  建议把 A/B 流程做成**子流程**，在 JavaBean 里拆分后启动新子流程。
- **判定：方向正确，且是成熟模式**（同构 Airflow `TriggerDagRunOperator`：task 触发 N 次子 DAG、payload 各异）。
  A、B 流程**本身不同** → 天然是两个子流程定义 → **不需要 §3.5 的同图动态节点实例**，
  `instance_key` 可彻底放弃（D4 的「不预留」继续成立，且更彻底）。
- **边界修正（与 §3.2.2 同一条）**：Bean 只产出**拆分计划**（`[{pipelineKey, input}]`），
  **不自己启动子执行**。理由更硬：① Bean 启动的执行不带 parent 关联 → 孤儿执行，
  监控/恢复/取消/审计全失联；② 计划必须**先落库再执行**，否则 Bean 启动 #1 后崩溃，
  没人知道本该有几个子执行。
- **落地形态**：`subflow` 的 `dispatchMode: SINGLE | FANOUT`。FANOUT 运行语义六条：
  1. 先 CAS 落计划（含 group_index）再逐条建子执行；2. 子执行
  `business_key={execution_id}:{node_id}:{attempt}:{group_index}` **幂等**（恢复/重试按计划补建不重复）；
  3. 收齐 N 个 CHILD 信号才按 `completionPolicy`（ALL_SUCCESS/ANY_SUCCESS）结算；
  4. 空计划直接 SUCCESS；5. 部分失败**默认不取消兄弟**（物理命令安全，同不继承
