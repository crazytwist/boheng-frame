设备域总体架构 v5

一句话：设备域回答「这台仪器怎么启动、参数怎么下发、跑完怎么收数、数据怎么归」； 调度域回答「何时、用哪台、先后依赖」；WMS 回答「板子在哪、谁占了槽位」。三者边界一刀切，不互相渗透。

一、分层总览

四个域纵向分层，只有一条接缝——device-api。调度域只给「条件」，从不给设备编码； 设备域内部五步全走同一条路径；传输层被收缩为两种协议加一个仿真。

图 1 · 分层总览：四个域 + 一条接缝

跨模块方向由 Maven 强制：调度域依赖 device-api（纯契约），物理上拿不到实现类。

二、数据流图①：命令的端到端旅程

这是设备域的主干数据流 —— 一次命令从生到死。三处加粗是相对既往系统的改强： 先落事实再抢设备、状态与等待原因正交、判失败前先对账。

图 2 · 命令流：下发 → 抢占 → 下发 → 回收 → 落库 → 上报

HTTP 在「落库 + 返回 commandNo」处即结束，后续全程异步；错误在参数校验处当场短路，不消耗设备往返。

三、数据流图②：数据三层（L0 → L1 → L2）

设备返回的数据不是直接落一张表就完。它按「不可变 → 可重算 → 可重判」三层落地， 且上下文在摄入那一刻就挂上，不靠事后猜文件名。

图 3 · 数据三层：不可变 / 可重算 / 可重判

L0 是唯一事实源 —— 只要有 L0，L1 和 L2 都能重算；反过来不行。所以 L0 不裁剪、不解释。

四、数据流图③：接入路径与传输层

仪器形态千差万别，但对后端只有一种样子 —— 因为四条路径全部收敛到 DeviceTransport 接口之后。 走哪条由 device_info.connection_type 决定，上层代码一行不改。

图 4 · 接入形态：四条路径，一个接口

平台对外只认 HTTP 与 MQTT 两种协议；串口 / 私有协议 / DLL 一律由 Node-RED 翻译，不进平台代码。

五、核心抽象链

从「这类设备能干什么」一路抽象到「怎么变成厂商协议」。能力用独立表，不塞 JSON —— 因为二期要按能力 JOIN 查设备。

图 5 · 从设备类型到厂商协议的五级链条

每一级都是可独立维护的配置；驱动声明能力（自描述），能力可被人工覆盖且留痕。

行为建模，不按型号；如 PLATE_READER 2 设备动作 DeviceAction ——「能被怎么启动」（设备域的核心） param_schema（默认值 + 约束 + 单位） standard_feature（映射 SiLA 标准特性名） need_busy_check / status_command_code request_template / poll_done_expr / estimate_duration_ms 3 设备属性 DeviceProperty ——「能被观测到什么」（遥测） 温度 / 仓门状态 / 耗材余量 / 当前程序进度 —— 可读、可订阅 定义在 device_property；当前值快照在 device_info.telemetry_json；历史轨迹二期 4 参数集 DeviceParamSet ——「这一次下什么参数」 params_json 是取值；validated 标记「已人工验证」—— 只有已验证的才能被用于发起命令 专用接口 update-validated：只改 validated / validatedBy / validatedTime，避免覆盖并发编辑 5 命令 DeviceCommand ——「实际下发了什么」+「跑到哪了」（只增不改） 参数快照 + 渲染后 payload + 进度（progress_percent / current_step / eta_sec） 失败时带 recovery_action（给人工可操作的恢复动作），不是只给一个错误码 6 驱动 DeviceDriver（对内 SPI）——「怎么变成厂商协议」 describeCapabilities() 自描述 → execute() / queryStatus() / fetchResult() 实现：TecanReaderNetworkDriver ｜ SimulatedDriver（一期先做）｜ …

能力自描述机制（最大的架构升级）

v1 把能力当成我们手工填的台账，接一台新设备要人工录一遍动作和参数。 对标 SiLA 的 introspection 后改为：驱动声明能力，人工可覆盖且留痕。

步动作落点
①装驱动，驱动自带能力描述（代码声明，或随驱动包一份描述文件）驱动制品内
②注册设备 / 首次探活 → 设备域读 describeCapabilities()设备域
③自动导入动作与属性，打上 source=DEVICE_DECLAREDdevice_action / device_property
④人工可覆盖，改过的打 source=MANUAL，留痕（谁改的、原值）同上
⑤冲突策略：MANUAL 优先；驱动升级导致声明变化时提示人工复核，不静默覆盖同上

收益：接新设备 = 装驱动 + 注册 + 能力自动带出，不写前端页面。 Cellario 的能力模型是机器可读的，AI 直接查询「实验室有哪些仪器、方法、约束」—— 这也是我们二期让 AI 规划实验的前提。

三处关键唯一键分工（防止「重试等于没重试」）

唯一键管什么为什么必须有
uk_command_no对外命令号调用方拿这个对账
uk_idempotent传输层重投（MQTT 重发 / 人工重复点）QoS 1/2 必然可能重复
uk_business
(tenant_id, source_type,
business_exec_id, node_id, attempt)		业务执行事实只有单列键时，重试会被拦成「返回原命令」→ 调度域永远看不到第 2 次执行
实测验证（事务内执行后回滚，未污染数据）：同业务节点同 attempt 的第 2 条 → 被唯一键拦下（1062 Duplicate entry '0-FLOW-EXEC-1-NODE-A-1'）； 手工命令（业务字段为 NULL）连插 2 条 → 都成功（MySQL 唯一索引 NULL 不参与去重，正好实现「手工命令不做业务幂等」）； 同节点 attempt=2 → 成功落库，重试链路畅通。

七、执行模型：三种调用方式，一条路径

三种调用方式不是三个接口，而是同一个命令的两个正交维度。给 sync / 异步 / 轮询各开一个接口， 后果是状态机三套、超时逻辑三套、事件三套、测试三套 —— 最终必然出现「某条路径漏了幂等、漏了流水」。

维度取值决定什么
dispatch_mode
下发方式		SYNC / ASYNC调用什么时候返回
result_mode
回收方式		SYNC_RETURN / CALLBACK / POLL结果怎么回来
#形态典型场景超时来源
①同步
SYNC + SYNC_RETURN		读属性、开关门、取状态、停止、急停HTTP 超时 3~5s
②异步回调
ASYNC + CALLBACK		跑板（仪器能推完成事件）callback_timeout
③异步轮询
ASYNC + POLL		老仪器只支持查询、无推送能力poll_interval × max_poll

四层决策，后者覆盖前者：① connection_type 决定 Transport → ② estimate_duration_ms（>3000ms 一律 ASYNC）→ ③ callback_enabled 决定 CALLBACK 还是 POLL → ④ 调用方显式指定（设备能力只说明「能不能」，调度语义才决定「要不要等」）。

CALLBACK 超时必须先降级 POLL 兜一次，不能直接判失败。MQTT QoS 0 可能丢消息、客户端可能掉线， 回调不可靠 —— 先兜一次轮询再判，否则会误报「设备没跑完」而实际早已跑完。这与「判 TIMED_OUT 前先对账」同源。

设备占用锁（对齐 SiLA Lock Controller）

字段作用
lock_holder谁持锁（command_no / USER:1 / TASK:xxx）
lock_typeCOMMAND / MANUAL / MAINTENANCE（人工检修也能锁设备）
lock_acquired_time / lock_expire_time锁必须能过期，否则设备永远锁死
lock_reason人工加锁时必填

抢占用原子 UPDATE（WHERE current_command_id IS NULL 且 affected rows == 1）， 绝不写成「先查后改」 —— 并发下 check-then-act 会让两台仪器收到同一条命令。 锁只在 concurrency_policy=EXCLUSIVE 时使用。

八、三个域的边界

域一句话职责明确不做
设备域（本次）这台设备怎么启动、参数怎么下发、跑完数据怎么收 / 怎么归不决定跑谁、不决定顺序
调度域（未来）什么时候、用哪台、先后依赖、并行、异常重试不碰厂商协议、不解析结果
WMS（已落地）板子在哪、何时上下机、谁占了槽位不碰设备协议

与 WMS 的缝合（零改表）：从货架取板 TAKE_OUT → 进仪器栈 PUT_IN 到 device_position_no 槽位 → 跑板 STATUS_CHANGE（AVAILABLE → IN_USE，ref_type=DEVICE）→ 出仪器 / 回位。 这条链与 SiLA 官网举的自家示例流程一模一样 —— 说明我们的场景是行业标准场景，不是特例。

调度域不自研流程引擎：竞品 UniteLabs 与 Roche AutoLab 均为 Camunda-based。项目根 pom 已有 boheng-module-bpm 占位（芋道自带 BPMN 引擎），但需从上游恢复。分工：流程定义走 BPMN 引擎， 资源分配（此刻用哪台 / 并行怎么排）自研，单设备执行属设备域。 诚实提醒：BPMN 只解决「流程定义」约 60%，「资源分配 / 排程优化」仍要自研。

九、传输层归属（v5 新增）

结论：传输层是 device 自己的 SPI，外部网关（芋道 iot-gateway 等）只能作为它的「实现」接入。 这样才保住「device 整体模块化」—— 删掉适配器模块，主模块零改动。

否决理由事实
它是 sidecar独立 Spring Boot 应用 + RestTemplate RPC 回调主程序 → 多一个进程、多一套契约
它的接缝是物模型IotDeviceMessage.deviceId 是 Long 主键（我们跨模块只认 device_code）；method 是物模型语义，不是我们的 action_code
它拖重依赖rocketmq-spring-boot-starter 会被带进主应用

落地形态（依赖单向）：device-api ← boheng-module-device（自定义 DeviceTransport SPI + 三实现） ← boheng-module-device-transport-iot（可选适配器，按需启用）。 抄实现、不引依赖的三块（一期就能用，零成本）：EMQX 认证事件报文形状 / Vert.x MqttServer 起法 / MQTT topic 拼装。
