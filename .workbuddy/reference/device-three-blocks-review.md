## 0-A ★ 本轮决策（v3 · 对 v2 的三处收敛）

> 这一节是 v3 新增，是「接下来怎么动手」的直接依据，优先级高于 v2 正文中与之冲突的表述。

| # | v2 原结论 | v3 本轮修正 | 影响 |
|---|---|---|---|
| 1 | 仿真独立环境、物理隔离（§3.4，作为「必做」） | 仿真**先不独立**，一期只做「接口可调通」：走真实命令入口、返回可预测的成功/失败、不产真实时序数据 | §3.4 的物理隔离降级为**二期目标**；一期不建仿真独立库/独立 broker |
| 2 | 数据上传「过程数据」是唯一实质缺口（§三 发现2） | 数据上传**两种都要**：① 跑完一次性读板（= 现有 L0/L1/L2 路径，已具备）② 过程实时推流（= 真缺口，二期时序库） | 一期重点是把「读板」路径闭环打通 + 补 `SimulatedDriver` 让仿真也能走通它；过程推流挂到二期 |
| 3 | 模块切分：仿真下沉为驱动实现（§2.1），未明确包/模块物理边界 | **一期：不拆独立 Maven 模块**，`device` 模块内分 4 个包子域（core/invoke/ingest/simulate）；**后续仿真升级为真实时序模拟时，再拆独立模块/独立部署** | 一期改动最小（纯包内重构 + 抽 SPI）；仿真独立是明确的分期目标，不是取消 |

### 0-A.1 一期包结构（在 `boheng-module-device` 内部，不新增 Maven 模块）

```
cn.boheng.frame.module.device
├── core        # 注册表 + SPI（device_info / DeviceDriver 接口）
├── invoke      # ① 调用域（现有 command/action/param_set 迁入）
├── ingest      # ② 数据域（raw/measurement/analysis 迁入；读板路径）
├── simulate    # ③ 仿真域（SimulatedDriver，一期「接口调通」级）
└── codec       # 协议编解码（①②共用，保持独立）
```

> 说明：这是**逻辑分包**，不是物理模块拆分。一期不建 `boheng-module-device-sim` 之类的新 Maven 模块；
> 用包名把三域边界钉死，等仿真要模拟真实时序数据（需要独立时序库、虚拟时钟、录制回放）时，
> 再把 `simulate` 整包迁出为独立模块/服务。

### 0-A.2 一期仿真验收标准（「接口可调通」的确切含义）

| 验收项 | 标准 |
|---|---|
| 走真实命令入口 | 仿真设备点「调用」，必须经过 `DeviceCommandService` 状态机 + L0 落库，**禁止 `if (simulated) return fake`** 旁路 |
| 返回可预测 | 同一 `device_code` + 同一 `actionCode` + 同一参数 → 返回确定性的成功/失败（可配「恒成功 / 恒失败 / 按参数规则」） |
| 数据同构 | 仿真产出的 L0 结构与真机 codec 一致，让前端/编排拿到的是「长得像真机」的响应 |
| 不做的事 | ❌ 不产真实时序曲线 ❌ 不做虚拟时钟 ❌ 不做录制回放 ❌ 不建独立环境 —— 这些全部二期 |

### 0-A.3 一期落地清单（对应 v2 §五的 P0/P1，收窄后）

| 步 | 动作 | 对应 v2 | 依赖 |
|---|---|---|---|
| 1 | 抽 `DeviceDriver` SPI：把焊死在 `DeviceHttpService` 里的「查台账→发 HTTP」收敛成 `HttpDriver` 一个实现 | P0 | 无 |
| 2 | 消歧三字段：`driver_type` 定为分派唯一依据，`connection_type=SIMULATED` 交给 `SimulatedDriver`，`simulation_mode` 收敛为 dry-run 覆盖开关 | v2 §2.2 | 步1 |
| 3 | 实现 `SimulatedDriver`（接口可调通级）：走命令入口 + 确定性响应 + 同构 L0 | P1 | 步1 |
| 4 | 「跑完读板」路径闭环：`ingest` 包子域内打通 raw→measurement→analysis，验证仿真设备也能走通 | —— | 步3 |

> 数据上传的「过程推流」形态、时序库选型（TDengine/TimescaleDB）、共享契约模块、独立环境隔离，
> 全部保持 v2 的结论**不动**，只是排期靠后（二期）。

## 〇、一句话结论

**三块的内容你都识别对了，但它们的「分类轴」不统一 —— ② 是数据面，③ 是控制面的一种实现，二者不是并列关系。**
按现在这个切法往下建，会得到两套命令路径、两个数据入口、仿真永远补不齐真机行为。

**正确的分轴：**
- **按控制面 / 数据面切开** → ① 和 ② 是这一刀切出来的两半
- **仿真（③）下沉为「一个可替换的驱动/传输实现」** → 它同时服务 ① 和 ②，不是第三块

> ★ **v2 补充**：你选了「数据平台单独做」，这让 §〇 的结论从**建议**变成了**必做**。
> 数据面一旦独立成系统，**它就无法再共享设备域的 Java 对象、枚举、上下文注入代码** ——
> 于是「设备身份 / topic 命名空间 / 时间语义 / 上下文最小集」必须在**两个系统之间**定义，
> 而不能像原来那样靠同进程调用隐式传递。见 §3.0 与 §3.3。

## 一、审核发现（先看问题，再看方案）

### ★ 发现 1：三块的分类轴不一致（最高优先级）

| 你的分块 | 实际所在的维度 | 证据 |
|---|---|---|
| ① 设备调用 | **控制面**（命令下行） | 现有代码 `DeviceHttpService.invoke()` 同步 HTTP |
| ② 数据上传 | **数据面**（数据上行） | 行业分层 raw/standardized/analytic（`device-domain-architecture.md` §6.1） |
| ③ 设备仿真 | **控制面的一种实现**（可替换的 driver/transport） | 架构文档 §四自己写的：`DeviceDriver` 的第二个实现 |

①③ 是**同一维度**（怎么下发、下发到谁），② 是**另一个维度**（数据怎么流、流到哪）。

**为什么会出事**：把 ③ 当并列块 → 仿真会做成一条**旁路**。典型失败形态是
「仿真时前端直接造假数据 / 后端加一个 `if (simulated) return fakeData()` 分支」→
于是仿真的命令**不进状态机、不落 L0、不产 L1**，
→ 结果是**仿真跑得通，真机一接全崩**，而且**上报链路在仿真下从未被验证过**。

### ★ 发现 2：② 在现有架构里根本没有位置（最大缺口）

现有代码**只有一条数据入口：命令的同步响应**。

```
现有：POST /device/info/invoke → DeviceHttpService.invoke()
        → DeviceHttpGateway（Hutool 同步 HTTP）
        → DeviceCommandService.complete() → 写 L0 raw → codec 解析 L1 → 标 L2
```

* 全模块**零 `@Scheduled`、零 MQ、零 MQTT 代码**（已 grep 核实）
* `device_property` 只有**定义**（CRUD），**没有任何地方写入当前值**
* `connectionType = MQTT` 只是台账上的一个字符串，**没有实现**

但你要的②是「**实时过程数据**」—— 一台上机仪器的温度/压力/pH/OD 动力学曲线，
是**在命令 RUNNING 期间持续产生**的。它**天然不挂在任何一次 HTTP 响应上**。

> ⚠️ **这是现有架构与你的需求之间唯一的实质性缺口。**
> `device-domain-architecture.md` 的 L0/L1/L2 是为**测量结果**设计的（一次命令 → 一份数据），
> **不是为过程时序数据设计的**。二者必须分开存。

### ★ 发现 3：仿真的语义在代码里已经打架了

现在同时存在三个概念，含义重叠且互相矛盾：

| 字段 | 位置 | 现状 |
|---|---|---|
| `device_info.driver_type` | `device.sql:64` | `SIMULATED` 是合法值，但**没有驱动分派代码** |
| `device_info.connection_type` | `device.sql:67` | `SIMULATED` 是合法值，但 `DeviceHttpService` 只接受 `HTTP`/`NODE_RED` |
| `device_info.simulation_mode` | `device.sql:90` | **没有任何代码读它做分派**，唯一用处是 `/portrait` 接口里拼一句提示文案 |

**实测后果**：种子里两台设备都是 `connection_type='SIMULATED'` + `simulation_mode=1`，
但点「调用」走 `DeviceHttpService` → 直接抛 `DEVICE_HTTP_FAILED("接入方式不是 HTTP")`。
**即：现在这台"仿真设备"连调用都调不动。** 这就是「仿真没落成驱动」的直接症状。

### 发现 4：没有区分「免硬件测试」的三种场景

「不接真机也能做实验」在你的语境里其实是三件事，要求完全不同：

| 场景 | 目标 | 对仿真层的要求 | 数据隔离 |
|---|---|---|---|
| **A. 开发自测 / 单测** | 接口跑通 | mock 即可，**不需要仿真设备** | 不涉及 |
| **B. 交付前全链路演练** | 不接硬件把「下发→状态→收数→分析」整条链路跑通，供前端联调 | **必须走真实命令入口**，产出与真机同构的数据 | 独立环境 |
| **C. 实验方案预演（"先胜后战"）** | 用仿真替代真机**跑真实实验**，跑完看结果决定要不要上机 | **需要真实时序 + 可复现 + 可回放**，不是随机假数据 | ⚠️ **必须强制隔离** |

现有架构文档只覆盖了 **B**（§四 `SimulatedDriver` 返回「96 孔正弦波」）。
**C 才是你说的「不接真机也能做实验」** —— 而 C 的难点不在下发，在**过程数据**。

> ★ **关键洞察**：③ 的验收标准由 ② 决定。
> 仿真能不能替代真机做实验，**取决于仿真能不能产出可信的过程时序数据**。
> 所以 ② 和 ③ 必须**一起设计**，这也反证了它们不该是两块。

### 发现 5：② 是「数据平台」，但边界没定义

> ★ **v2 已定：数据平台单独做，不与业务方向混在一起。** 后果与落地方案见 **§3.0 / §3.0.1 / §3.3**。

「② 属于数据平台」—— 这句话里藏着一个必须先定的问题：
**数据平台是独立系统，还是本平台内的模块？** 三种形态的架构含义完全不同。
**你已选独立系统**，于是下面三件事从「待办」变成「阻塞项」：

* **设备侧身份认证** —— 设备主动上报（MQTT/HTTP）时，**平台怎么知道它真的是这台设备**？现有设计零字提及
* **设备时钟不可信** —— 必须**双时间戳**：设备侧 `device_ts` + 平台侧 `received_at`（**以平台为准**）
* **复现性** —— 仿真出数据必须记随机种子，否则同一实验两次跑出不同结果，**实验不可复现**

## 二、架构建议：四层 + 两个面

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ① 外部世界                                                                │
│   真机 ─ HTTP/MQTT 直连 ──┐                                              │
│   串口/私有协议 ─ Node-RED ┼──▶ 【统一接入层】                             │
│   仿真设备 ─ SimulatedDriver┘    （三条接入路径对平台完全等价）             │
└──────────────────────────────────────────────────────────────────────────┘
                                    │
┌───────────────────────────────────▼──────────────────────────────────────┐
│ ② 接入层（唯一入口，两类流量在此分流）                                     │
│                                                                          │
│   下行：命令 / 参数 ──▶ 同步请求响应                                      │
│   上行：ack / progress / result / telemetry  ──▶ 异步推送                 │
│                                                                          │
│   职责：设备身份认证 · 租户解析 · 幂等去重 · 平台时间戳打标 · 大载荷转文件  │
└───────────────┬──────────────────────────────────┬───────────────────────┘
                │                                  │
┌───────────────▼──────────────┐   ┌───────────────▼───────────────────────┐
│ ③ 设备域 = 控制面             │   │ ④ 数据面 = 数据平台（业务需求②）       │
│    「这台设备怎么跑起来」      │   │    「跑的时候发生了什么」              │
│                               │   │                                       │
│  device_info  台账 + 锁       │   │  实时层（过程时序）                    │
│  device_action 动作 + 参数模式 │   │   telemetry / progress / 曲线          │

│  device_param_set 参数集       │   │                                       │
│  命令状态机（唯一）            │   │  归档层（测量结果）                    │
│  忙闲 / 并发策略（三档开关）    │   │   device_data_raw  ← L0 原文不可变     │
│                               │   │   device_measurement      ← L1 标准    │
│  ★ 驱动/传输 SPI（唯一扩展点） │   │   device_analysis_result  ← L2 结论    │
│    HttpTransport              │   │                                       │
│    MqttTransport              │   │  两条写入路径共用同一套上下文注入       │
│    SimulatedDriver ◀── ③ 仿真 │   │                                       │
└───────────────────────────────┘   └───────────────────────────────────────┘
```

### 2.1 仿真（你的③）怎么放

**结论：仿真不是第三个块，是控制面里的一个实现，同时"伪装"数据面。**

```
                 ┌─ 命令入口（唯一）
业务 / 调度 ─────┤
                 └─ 数据入口（唯一）
                        ▲
                        │  仿真设备必须走这两个入口，禁止旁路
        ┌───────────────┴───────────────┐
        │  DeviceTransport / Driver SPI │
        ├───────────────────────────────┤
        │  HttpTransport    → 真机       │
        │  MqttTransport    → 真机       │
        │  SimulatedDriver  → 仿真 ★     │
        └───────────────────────────────┘
```

**四条硬约束**（写进代码评审清单）：

| # | 约束 | 违反后果 |
|---|---|---|
| **1** | **仿真必须走真实命令入口**，禁止 `if (simulated)` 旁路 | 状态机 / 幂等 / 落库在仿真下不被验证 = 真机一接就崩 |
| **2** | **仿真数据必须与真机同构**（同样的 L0→L1 结构，同样的 codec 路径） | 仿真跑通不代表真机跑通 |
| **3** | **仿真必须能产出过程时序**（温度曲线 / OD 动力学），不只是终值 | 否则场景 C（实验预演）根本不成立 |
| **4** | **仿真数据必须可识别、隔离**，且**记录参数与随机种子** | 仿真数据污染真实实验；同一实验不可复现 |

**必须支持的三个能力**（缺一个，C 场景就不成立）：

| 能力 | 用途 |
|---|---|
| **故障注入 / 异常剧本** | 超时、断连、返回畸形报文、板卡报错 —— 这些**只在仿真时才能测**，真机上不敢测 |
| **虚拟时间加速** | 一次 8 小时的孵育实验，`virtual_clock_rate=1000` 时 30 秒跑完 |
| **录制回放（record & replay）** | 真机跑一次录下来，之后用回放代替真机做回归 —— **最有价值的仿真形态**，因为它用真实行为而非模拟行为 |

### 2.2 消歧：三个字段的职责必须切清

| 字段 | 语义 | 规则 |
|---|---|---|
| `connection_type` | **这台设备物理上怎么到达** | `HTTP` / `MQTT` / `NODE_RED` / `SIMULATED` |
| `simulation_mode` | **本该连真机，但当前按仿真跑**（dry-run / 演练开关） | ✅ 保留 —— 但语义是**临时覆盖**，不是分类 |
| `driver_type` | **用哪个驱动实现** | 与 `connection_type` 二选一为准，**建议合并掉**，避免第三个真相源 |

**对外统一一个入口**：设备模型（API/DTO）只暴露
「**这台设备现在是仿真还是真机**」+「**走哪条链路**」两个问题，两个答案。

## 三、② 数据上报块：这是你要补的重点

### 3.0 ★ 决策落地后：三个域的边界重新划（v2 新增，最高优先级）

**你的决策**：「数据平台单独做，不和业务方向混在一起」。

**这个决策的直接推论：数据平台不是一个"功能块"，而是一个独立的限界上下文。**
所以三域边界要重划成：

| 域 | 一句话职责 | 拥有什么（真相源） | 明确不做 |
|---|---|---|---|
| **设备域（控制面）** | 这台设备**怎么跑起来** | `device_info` 台账 · 动作/属性/参数集定义 · **命令状态机** · 设备锁 · 忙闲并策略 | ❌ 不做时序存储 · ❌ 不做过程数据分析 |
| **数据平台（数据面 · 独立系统）** | 跑的时候**发生了什么变化** | **过程时序数据**（温度/pH/OD 动力学）· 时序查询与降采样 · 数据资产目录 | ❌ 不认识 `device_command`（只认 `command_no` 关联号）· ❌ 不做命令下发 |
| **业务域（未来调度域）** | **什么时候、用哪台、先后顺序** | 实验/任务实例 · 流程编排（BPMN） | ❌ 不碰协议 · ❌ 不碰时序存储 |

**★ 数据所有权划分（必须写进接口文档，否则二期必吵）：**

```
设备域拥有：【语义层】「发生了什么业务事件」
    device_command（命令生命周期）
    device_data_raw（L0 原文快照，命令维度）
    device_measurement + _data（L1 标准化测量结果，孔级矩阵）
    device_analysis_result（L2 结论，按规则重判）

数据平台拥有：【过程层】「物理量怎么随时间变化」
    telemetry（过程时序，时序库）
    status_log（上下线 / 状态轨迹）
    → 数据平台的资产目录 / 查询 API

★ 交叉引用只用一个钥匙：command_no
    数据平台不认识 device_id、不认识 device_command 表结构，
    它只认 (env, device_code, command_no) 三元组。
```

**为什么这条最重要**：数据平台一旦独立，**它和业务域就是不同团队、不同发版节奏**。
共享 Java 对象 = 强制同步发版 = 两个系统事实上被焊死。**用编码 + 契约解耦，不用对象解耦。**

### 3.0.1 过程数据怎么从设备流到数据平台：三种拓扑

数据平台独立后，**过程数据的物理流向必须选一个**：

| 方案 | 链路 | 优点 | 代价 |
|---|---|---|---|
| **A. 同进程分流** | 设备域接入层 → **调用数据平台写入 API** → 时序库 | 设备域掌握认证/幂等/上下文，写入有强保障；一期最快 | 数据平台写入必须支持无模式（新属性免发版）；**设备域可用性受数据平台影响** |
| **B. broker 规则引擎直写** | broker（EMQX）规则引擎 → **直接写时序库** | 数据平台自治性最高，`SimulatedDriver` 与真机都从 broker 统一进入；高频时序不过 Java，无阻塞风险 | ⚠️ 设备认证/幂等/时间戳要在规则引擎里再实现一遍；上下文注入能力弱 |
| **C. 独立采集服务** | 设备域 → MQ → **采集服务（独立部署）** → 时序库 | 边界最清晰，可独立扩缩容、批量写、失败重试；设备域告警不影响数据平台 | 多一个部署单元 + 多一个 MQ |
| **D. 设备直推时序库** | 设备/规则引擎 → 直接写 TSDB | 链路最短 | ❌ **不推荐**：绕过一切校验，上下文全丢，无幂等 |

**建议**：
* **一期走 A** —— 复用设备域已有的设备认证与上下文注入，`SimulatedDriver` 也能立刻产出过程数据
* **数据平台团队就位后迁到 C** —— 边界最干净，且天然获得批量写 + 断点续传
* B 作为**性能兜底**（当遥测频率超过 Java 侧吞吐时，把高频通道切给规则引擎，低频仍走 A/C）

> ⚠️ **无论选哪个，都需要一个"共享契约模块"**（见 §3.3），否则两侧会各自实现一套设备身份、时间戳、幂等规则。

### 3.1 ★ 上报不能只挂测量结果，必须分两类

| 类别 | 内容 | 时间特征 | 现有落点 | 建议落点 |
|---|---|---|---|---|
| **过程数据（你要的实时数据）** | 温度、压力、pH、转速、OD 动力学、步骤进度、耗材余量 | **高频、连续、有时序** | ❌ **现在无处可落** | **独立时序通道 / 时序表** |
| **结果数据（L0/L1/L2）** | 测量头、孔级读数、分析结论 | **低频、离散、一次一份** | ✅ `device_data_raw` → `device_measurement` → `device_analysis_result` | 保持现状 |

> ⚠️ **绝对不要把过程数据塞进 `device_measurement_data`**。
> 那块表的行模型是「**孔 × 波长 = 一行**」，是**二维矩阵快照**，没有时间轴。
> 把 1Hz 的温度曲线塞进去 = 「孔级读数」这个概念被污染，且 96 孔板 × 3 波长 × 8 小时 = 千万行。

**过程数据的存法 —— 你已决策：时序库。** 三选一的对比（v2 更新）：

| 方案 | 定位 | 优势 | 代价 / 风险 |
|---|---|---|---|
| **TDengine** ✅ **推荐** | 国产时序库，专为 IoT/工业 | **超表模型**（`device_code` + `property_code` → 子表，天然一对一台设备一属性）· 官方称压缩率显著优于通用库 · **支持 REST/无模式写入**（taosAdapter）· **支持乱序写入**（对断网补传、设备时钟不准很关键）· 内置降采样/窗口函数 · 数据订阅能力（可做流式管道）· 中文文档与国内支持好 | 引入新数据库与运维技能；**与业务表 JOIN 困难**（跨库）→ 分析侧需在应用层对齐 |
| **TimescaleDB** | PostgreSQL 扩展，不是新数据库 | **与业务表同库可 JOIN**（这是最大优势）· SQL 生态完整 · 团队已有 PG 时几乎零学习成本 | 写入吞吐与压缩率不如专用时序库；时序场景仍需自己设计分区与保留策略 |
| **InfluxDB 3.0** | 重写版时序库 | 生态广、工具链成熟 | ⚠️ **3.0 是重写，社区仍在验证**；开源版与商业版能力差异需自行确认；不建议一期押注 |

**选型建议**：
* **默认选 TDengine** —— 理由集中在两点：**无模式写入**（过程数据属性会不断新增，写死 schema 会逼你频繁发版）
  与**乱序写入**（设备时钟不准 + 断网补传是**必然发生**的，不是边缘情况）。这两条在你这个场景里是刚需。
* **选 TimescaleDB 的唯一充分理由**：你**必须**把过程数据与业务表（实验/样品/物料）做 SQL JOIN 查询。
  如果有这个需求，直接选 TimescaleDB，别在 TDengine 上硬做跨库对齐。

> ⚠️ **时序库不解决的两件事**（别指望它）：
> 1. **幂等去重** —— 补传 / 重投必然产生重复点，**去重必须在应用层用 `(device_code, property_code, messageId)` 做**，不能靠数据库
> 2. **语义校验** —— 时序库不校验上下文是否齐全，`command_no` 挂错了它照收
>
> ⚠️ 上述能力项（无模式写入、乱序、订阅）**属产品能力描述，落地前请用你自己的数据量与写入模式做一次压测验证** ——
> 选型结论不应用于替代实测。

**TDengine 落点草图**（一期形态）：

```sql
-- 元数据表（普通表，属性字典与 device_property 对齐）
CREATE TABLE telemetry_property (
  property_code VARCHAR(64), unit VARCHAR(32),
  value_type VARCHAR(16), device_type_code VARCHAR(64)
);

-- 超表：一行 = 一个属性在一个时刻的一个值
CREATE STABLE telemetry (
  ts           TIMESTAMP,   -- ★ 平台接收时间（权威）
  device_ts    TIMESTAMP,   -- ★ 设备侧时间（仅参考，可能为 NULL）
  value_num    DOUBLE,
  value_text   NCHAR(64),
  quality      TINYINT,     -- 0=可信 / 1=可疑 / 2=坏值
  message_id   NCHAR(64),   -- 幂等去重键
  env          NCHAR(16),   -- 环境标识（prod/staging/sim）
  data_origin  NCHAR(12)    -- REAL / SIMULATED / REPLAY
) TAGS (
  device_code  NCHAR(64),
  property_code NCHAR(64),
  command_no   NCHAR(64),   -- ★ 关联号码（可空：命令外上报）
  batch_no     NCHAR(64)    -- 产物批次（可选）
);
```

> ★ `command_no` 与 `data_origin` **必须是 TAG 而不是普通列** —— TAG 可索引、可做子表筛选，
> 而「剔除仿真数据」「只看某次命令的过程曲线」是两个最高频的查询条件。

**配套动作**：`device_status_log`（原二期表）**要提前到一期**，它就是过程数据的天然落点；
但它现在应该**归数据平台**（进时序库，不进业务库），且必须带 `command_no`，
才能回答「这次跑板过程中的温度」。见 §3.0 的所有权划分。

### 3.2 ★★★ 最关键的架构决策：上报如何挂上实验上下文

这是整个②块**唯一真正难的地方**，也是我建议你重点评审的一条。

| | 命令响应（现状） | 设备主动上报（新增） |
|---|---|---|
| 触发 | 平台发起 | **设备/接入层发起** |
| 上下文 | ✅ **天然携带** `commandNo` | ❌ **默认什么都不知道** |
| 顺序 | 请求-响应天然有序 | ⚠️ MQTT QoS 0/1，**可能乱序、可能丢、可能重** |
| 时间 | 平台自己的时钟 | ⚠️ **设备时钟不可信** |

**所以②块的核心设计任务是：让异步、无序、无上下文的上报流量，重新挂上强上下文。**

三种做法：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 设备回传关联号** | 上行 payload 里带 `commandNo` / `jobId` | ✅ **首选**。要求写进**设备接入契约**（MQTT 信封已有字段位） |
| **B. 接入层维护运行期映射** | `(device_code, jobId) → commandNo` 映射表 | ✅ **必须做**。因为**老旧仪器不会回传我们的关联号**，只能靠 jobId 二次映射 |
| **C. 时间窗归属** | 按 `[sent_at, finished_at]` 时间窗把上报归到最近命令 | ⚠️ **仅作兜底**，多设备并发时必错 |

> ★ **B 是重点，容易被漏掉**：仪器只会回它自己的 `jobId`（甚至只有 `Run 3` 这种）。
> 接入层必须维护一张运行时映射表，**这是①和②之间的缝合点**，也是数据平台能拿到完整上下文的唯一途径。

**达成后，L1 上下文硬约束（架构文档 §6.2）对上报流量同样成立** ——
也就是说，**上报数据也必须在摄入那一刻挂齐** `device_code` / `command_no` /
`plate_instance_code` / `experiment_ref` / `operator` / `driver_version`，
不能事后靠时间猜。

### 3.3 ★★★ 两个独立系统之间的共享契约（v2 重写）

数据平台独立后，**原来靠同进程传递的东西全部消失**，必须在两个系统之间显式定义。
**建议抽一个独立模块**（不放在任一侧，避免反向依赖）：

```
boheng-module-device-contract      ← 设备域 与 数据平台 都依赖它
    ├── 设备身份：device_code 命名规范 / 认证方式声明
    ├── Topic 命名空间：{env}/{ns}/device/{deviceCode}/{cmd|ack|progress|result|telemetry|status}
    ├── 上行信封：{ messageId, deviceCode, commandNo?, ts, type, payload }
    ├── 时间语义：clock_base / time_scale / device_ts / received_at 字段定义
    ├── 上下文最小集：摄入时必须齐备的字段清单（见 §3.2 末）
    └── 环境标识：env / data_origin 枚举
```

> ⚠️ **不要把这个契约放进 `boheng-module-device-api`** —— 那会让数据平台反向依赖设备域，
> 设备域一发版数据平台就得跟着发。**共享第三方模块，两侧都只依赖它。**

**关键：`(device_code, jobId) → commandNo` 的运行期映射（原 §3.2 方案 B）现在跨系统了。**
三个选项：

| 选项 | 做法 | 评价 |
|---|---|---|
| 1 | 映射表放**设备域**，数据平台上报时反查 | ⚠️ 数据平台反向依赖设备域，破坏独立性 |
| 2 | 设备域把映射**发布到 MQ**，数据平台订阅维护 | ✅ **推荐** —— 单向、可重放、两侧解耦 |
| 3 | 映射表放**共享存储**（Redis），两侧读写 | ⚠️ 共享存储 = 隐性耦合，但延迟最低 |

**推荐 2**：设备域在 `DISPATCHED`（拿到 `jobId`）与终态时各发一条**映射事件**，
数据平台维护本地映射表。设备域不可用时数据平台仍能继续消费历史事件。

### 3.4 ★ 仿真独立环境、物理隔离（v2 新增，对应你的第三项决策）

你选了「独立环境，物理隔离」。**这个决策的代价比看起来大**，因为它把仿真从
「一个驱动实现」升级成「**一套完整的环境**」：

| 层 | 隔离动作 | 说明 |
|---|---|---|
| **时序库** | 独立 database / 独立实例 | 时序数据物理隔离（不是在同一个库里打标） |
| **业务库** | 独立库（表前缀区分不够，用独立库 + 独立连接串） | `device_command` / `measurement` 等全部隔离 |
| **Broker** | 独立 EMQX 实例 + 独立 topic 命名空间 `{env}` | 仿真设备连不上生产 broker（网络层就断） |
| **配置** | 环境标识写进**消息信封**，不只是配置项 | 让环境跟着数据走，便于排障与审计 |
| **写入** | 设备域写数据平台时**做环境校验**（生产拒绝收 sim 数据） | ⚠️ **最容易漏的一条**，也是隔离的最后一道闸 |

**★ 隔离之后，`data_origin` 仍然要保留**（`REAL` / `SIMULATED` / `REPLAY`）：
* 物理隔离解决「**数据不混**」
* `data_origin` 解决「**同一环境内的来源可辨**」——
  免硬件演练环境里，可能会**混合**跑 `SIMULATED` 与 `REPLAY` 两种数据
* 二者**不互斥**，别因为做了物理隔离就省掉来源标记

**收益（这是这个决策真正的价值）**：因为环境隔离了，仿真可以**放开跑而不怕污染**：

| 仿真能力 | 用途 | 为什么只在仿真能做 |
|---|---|---|
| **故障注入 / 异常剧本** | 超时、断连、畸形报文、板卡报错、失控曲线 | 真机上**不敢测** |
| **虚拟时间加速** | 8 小时孵育 → 30 秒跑完（`time_scale=1000`） | 真机时间不可压缩 |
| **录制回放** | 真机录一次 → 反复回放做回归 | 真机每次跑都有成本与损耗 |
| **参数扫描（批量仿真）** | 一次跑 100 组参数，找最优实验条件 | 真机上成本不可接受 |

### 3.5 ★ 时间基：仿真物理隔离后新暴露的问题（v2 新增）

**这是仿真独立环境之后才暴露的、最容易被忽略的深坑。**

仿真支持虚拟时钟加速后，系统里同时存在**四个时间**：

| 时间 | 含义 | 用途 |
|---|---|---|
| `received_at` | **平台接收时间**（墙钟） | ✅ **权威索引**，一切时序查询按它 |
| `device_ts` | **设备侧时间** | ⚠️ 仅参考（设备时钟普遍不准，可能有设备不报） |
| `virtual_ts` | **仿真虚拟时间**（加速后） | 仿真的时间轴，与墙钟**不成线性** |
| `monotonic_ts` | 单调时钟 | 算耗时，避免时钟回拨 |

**问题**：一次 8 小时孵育实验在 `time_scale=1000` 下 30 秒跑完，
那么**「OD 上升速率」按哪个时间轴算？**

* 按墙钟算 → 速率是真实值的 **1000 倍**，分析结论**完全错**
* 按虚拟时间算 → 与真机可比 ✅

**硬约束（写进契约）**：
1. **每个仿真运行必须记录** `time_scale` + `clock_base`（时钟基准点）
2. **分析侧必须显式声明**用哪个时间轴 —— 不能默认，不能隐式
3. **`virtual_ts` 与 `received_at` 都要存** —— 前者用于科学分析，后者用于排序与排障
4. **跨环境对比（仿真 vs 真机）必须显式做时钟校准**，不能直接叠图

> ★ 一句话：**仿真的时间不能等于平台的时间。**
> 这条在「仿真只是假驱动」的旧形态下不存在，一旦支持虚拟时钟就必然出现。**现在不定，二期必返工。**

## 四、必须补的横向契约（②块引入的新问题）

| # | 契约 | 为什么现在必须定 | 建议 |
|---|---|---|---|
| **1** | **双向设备认证** | 设备主动上报 = **平台对外开放了入站口**。不认证 = 任何人可伪造实验数据 | 一设备一凭据（MQTT username/密码 或 mTLS）+ **EMQX ACL 限定 topic 前缀** + 租户绑定 |
| **2** | **幂等（上报侧）** | MQTT QoS 1 = at-least-once，**重投是必然事件** | 上行信封带 `messageId`，接入层**按 `(device_code, messageId)` 去重**（与命令侧 `uk_idempotent` 同一套思路） |
| **3** | **双时间戳** | **设备时钟普遍不准**，甚至有设备不报时间 | `device_ts`（设备侧，仅参考）+ `received_at`（平台侧，**权威**）；时序查询一律以 `received_at` 索引 |
| **4** | **大载荷转文件** | 过程数据比测量结果更大（8 小时曲线） | 复用架构文档 §3.5 的 **64KB 阈值** → 转文件引用，MQTT 只传 `{fileUrl, size, sha256}` |
| **5** | **断网续传** | 现场网络抖动，设备侧队列通常极小，**一断就丢** | 接入层（或网关侧）**本地落盘缓存 + 补传**；不要指望仪器 |
| **6** | **仿真数据标记与隔离** | 数据平台做分析时**必须能剔除仿真数据**，否则结论失真 | ✅ 已定：**独立环境物理隔离**（§3.4）+ 保留 `data_origin`(`REAL`/`SIMULATED`/`REPLAY`) 双保险 |
| **7** | **过程数据的保留与降采样** | 1Hz × 8 小时 × N 台 = 迅速膨胀 | 时序库上用**热/温/冷**三档：原样保留 7 天 → 分钟级降采样 1 年 → 归档；TDengine 内置降采样可直接用 |
| **8** | **时间基（v2 新增）★** | 虚拟时钟加速后，「速率/斜率」按哪个时间轴算是歧义的 | `clock_base` + `time_scale` 必须随每次运行记录；分析侧必须**显式声明**时基。见 **§3.5** |
| **9** | **共享契约模块（v2 新增）★** | 两个独立系统再无同进程对象可共享 | 独立 `device-contract` 模块（**不放 `device-api`**），两侧只依赖它。见 **§3.3** |

## 五、落地顺序建议（按依赖，不按块 · v2 更新）

**两条并行主线**：设备域主线（①③）与数据平台主线（②）可以并行开工，
**但汇合点在 P4**（第一次端到端联调），汇合前双方都必须遵守 §3.3 的共享契约。

### 主线的拆分

```
设备域主线（现有仓库）              数据平台主线（新系统）
P0 抽 DeviceTransport SPI
P1  SimulatedDriver
        │                                  D0 时序库选型 + 建库
        │                                  D1 元数据目录（属性字典）
        └──────────────┬───────────────────┘
                       ▼
              P2/P4 遥测写入通道 + 共享契约（★ 汇合点）
                       │
              联调：仿真设备 → 过程数据 → 时序库 → 查询
```

### 阶段清单

| 阶段 | 归属 | 内容 | 为什么这个顺序 |
|---|---|---|---|
| **P0** | 设备域 | **抽出 `DeviceTransport` SPI**，把现在焊死的 `DeviceHttpGateway`（Hutool 同步，20s 超时，见 `service/http/DeviceHttpGateway.java`）**收敛成 `HttpTransport` 一个实现** | ⚠️ **当前最大技术债**：传输层与业务层焊死，仿真插不进来、MQTT 扩不了。**不做这步，②③都无从落地** |
| **P1** | 设备域 | **`SimulatedDriver`** —— 走真实入口、产出同构 L0/L1、支持故障注入 | 你说的③。**先于真机驱动**，解掉「等 Tecan 文档」的阻塞 |
| **D0** | 数据平台 | 时序库选型验证（TDengine `schemaless` 写入 + 乱序补传实测）+ 建库建超表 | 与 P0/P1 并行，不冲突 |
| **D1** | 数据平台 | 元数据目录（属性字典 / 标签定义），与 `device_property` 对齐 | 过程数据要有语义，否则只是数字 |
| **P2** | 双侧 | **共享契约模块**落地（§3.3）+ **遥测写入通道**（§3.0.1 方案 A） | ★ **汇合点**。此刻才开始真正需要两侧协同 |
| **P3** | 设备域 | **运行时映射**：`(device_code, jobId) → commandNo`，并**发布映射事件**（§3.3 选项 2） | 让上报数据挂得上实验上下文 |
| **P4** | 双侧 | **第一次端到端联调**：仿真设备 → 命令 → 过程数据 → 时序库 → 查询出曲线 | ✅ **本轮的验收标准** |
| **P5** | 设备域 | 仿真完整形态：**虚拟时钟 / 录制回放 / 参数扫描**（需 P2 的时间基已定，§3.5） | 场景 C（实验预演）成立 |
| **P6** | 设备域 | 上行接入层独立化：MQTT 订阅 + 设备认证 + 幂等 + 断网续传 | 真机接入前必须就位 |
| **P7** | —— | 真机驱动 / Node-RED 接入 / 调度域对接 | 前述全部就位后 |

**一句话**：**P0 + P1 与 D0 + D1 可以立刻并行开工**；
真正需要停下来对齐的只有 **P2（共享契约）** 这一个点。
