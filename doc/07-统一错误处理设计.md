# 统一错误处理设计（Flow 内部错误 / 设备上报错误）

## 1. 目标和边界

本设计解决两类问题：

1. **平台内部流程错误**：参数、表达式、Bean、WMS 业务规则、依赖调用、引擎异常、恢复失败。
2. **设备上报错误**：拒绝、执行失败、故障、急停、超时、结果不确定、重复或矛盾通知。

平台负责记录、归类和业务处置，但不替设备判断物理现场是否安全，也不因通信失败自动重发物理命令。

## 2. 当前缺口

| 当前能力 | 已有位置 | 缺口 |
|---|---|---|
| 流程最终错误 | `flow_execution.error_code/error_message` | 只能保存最后一次错误，没有发生历史和处置记录 |
| 节点错误 | `flow_step_execution.error_code/error_message` | 没有错误来源、严重级别、原始报文和可重试语义 |
| 设备命令错误 | `device_command.error_msg` | 一段文本覆盖全部语义，不能区分设备故障、业务拒绝和通信异常 |
| 设备任务错误 | `flow_device_task.error_message` | 未保存设备错误码、外部事件 ID、错误原文 |
| 通知处理 | Spring 事件 + 状态扫描 | 没有统一错误事件去重和人工处置入口 |

现有字段继续保留，作为列表快速展示的“最后错误摘要”；完整历史进入错误记录表。

## 3. 统一错误语义

### 3.1 来源

| `sourceType` | 含义 |
|---|---|
| `FLOW_ENGINE` | 引擎推进、调度、状态结算错误 |
| `FLOW_STEP` | Bean、脚本、表达式、校验等节点错误 |
| `WMS` | 样本、物料、槽位和库存业务错误 |
| `DEVICE` | 设备明确上报的错误或故障 |
| `COMMUNICATION` | HTTP/MQTT/网关断线、超时、报文不可解析 |
| `SYSTEM` | 数据库、线程池、配置等平台基础错误 |

### 3.2 分类

| `category` | 示例 | 默认处理 |
|---|---|---|
| `VALIDATION` | 缺参数、格式不合法 | 失败，不重试 |
| `BUSINESS_RULE` | 样本状态不允许、库存不足 | 失败或人工处理 |
| `RESOURCE_UNAVAILABLE` | 物料暂不可用、设备 BUSY | 等待或重新决策 |
| `DEPENDENCY` | WMS/API 暂时不可用 | 有界重试 |
| `COMMUNICATION` | 超时、断网 | 进入 UNKNOWN，先查询 |
| `DEVICE_REJECTED` | 设备明确拒绝命令 | 等待、换设备或终止 |
| `DEVICE_EXECUTION` | 设备执行失败、测量失败 | 失败/补偿/人工处理 |
| `DEVICE_SAFETY` | 急停、门开、碰撞、过温 | CRITICAL，禁止自动重试 |
| `INTERNAL_BUG` | 空指针、非法状态、代码缺陷 | 失败并告警，禁止盲目重试 |
| `UNKNOWN` | 状态冲突、无法解释的设备返回 | 等待外部确认或人工处理 |

### 3.3 严重级别与确定性

| 字段 | 值 |
|---|---|
| `severity` | `INFO / WARNING / ERROR / CRITICAL` |
| `certainty` | `CONFIRMED / UNKNOWN` |
| `retryMode` | `SAFE / IDEMPOTENT / QUERY_FIRST / MANUAL / NEVER` |

`COMMUNICATION + UNKNOWN` 绝不能直接解释成设备未执行；默认 `QUERY_FIRST`。

## 4. 记录模型

### 4.1 设备原始错误：`device_error_event`

设备模块按原样保存外部事实，不做流程决策。

| 字段 | 用途 |
|---|---|
| `id` | 平台记录 ID |
| `external_event_id` | 设备事件 ID；与设备编码组成唯一键，负责去重 |
| `device_code/command_id/command_no` | 设备与命令关联 |
| `device_error_code/device_error_message` | 设备原始错误码和原文 |
| `severity` | 设备声明的严重程度；无法识别时由适配层映射 |
| `occurred_at/received_at` | 设备发生时间和平台接收时间 |
| `raw_payload` | 原始报文，限制长度；敏感字段脱敏 |
| `ack_status` | `RECEIVED/PROCESSED/REJECTED` |

约束：`uk_device_event(tenant_id, device_code, external_event_id)`。

### 4.2 流程错误记录：`flow_error_record`

一条记录代表一次可独立处置的错误事实。

| 字段组 | 字段 |
|---|---|
| 身份 | `error_no`, `dedup_key`, `source_type`, `source_ref_id` |
| 流程定位 | `execution_id`, `node_id`, `iteration_no`, `attempt` |
| 外部定位 | `device_code`, `command_id`, `device_event_id`, `operation_id` |
| 语义 | `error_code`, `category`, `severity`, `certainty`, `retry_mode` |
| 内容 | `message`, `detail_json`, `raw_payload_ref` |
| 处置 | `status`, `resolution`, `resolved_by`, `resolved_at` |
| 时间 | `occurred_at`, `create_time`, `update_time` |

约束：`uk_error_dedup(tenant_id, dedup_key)`，防止重复通知制造多条待处理错误。

### 4.3 处置流水：`flow_error_action`

只增不改，记录自动或人工采取过什么动作：

`RETRY / QUERY_DEVICE / WAIT / SWITCH_RESOURCE / COMPENSATE / SKIP / ABORT / CONFIRM_SUCCESS / CONFIRM_FAILED / ACKNOWLEDGE / COMMENT`。

至少保存 `error_id/action/operator/action_result/comment/create_time`。

## 5. 错误生命周期

```text
OPEN
 ├─ WAITING_RETRY ── retry succeeded ── RESOLVED
 ├─ WAITING_EXTERNAL_CONFIRMATION ── query/event ── RESOLVED
 ├─ WAITING_MANUAL ── human action ── RESOLVED / IGNORED
 └─ terminal decision ── RESOLVED
```

允许状态：`OPEN / WAITING_RETRY / WAITING_EXTERNAL_CONFIRMATION / WAITING_MANUAL / RESOLVED / IGNORED`。

## 6. 处理矩阵

| 场景 | Flow 节点 | 自动动作 | WMS 动作 | 人工入口 |
|---|---|---|---|---|
| 参数/校验错误 | `DEAD` | 无 | 无 | 修改流程后重新启动 |
| WMS 暂时不可用 | 保持当前 attempt | 有界重试 | 不重复扣减，依赖幂等键 | 超限后人工 |
| WMS 业务拒绝 | `DEAD` 或业务分支 | 不重试 | 保持原状态 | 允许换料/终止 |
| 设备 BUSY | `WAITING` | 延后或换设备决策 | 不消耗 | 可选择目标设备 |
| 设备明确 FAILED | `FAILED/DEAD` | 按 retryMode | 未确认完成前不消耗 | 补偿、终止或新 attempt |
| 通信超时 | `WAITING_EXTERNAL_CONFIRMATION` | 按业务键查询设备 | 禁止推进 | 确认成功/失败 |
| 设备安全故障 | `WAITING_MANUAL` | 禁止自动重试 | 冻结相关业务推进 | 必须人工确认 |
| 重复错误通知 | 状态不变 | 按 eventId/dedupKey 丢弃重复处理 | 不重复操作 | 展示重复次数即可 |

## 7. 设备错误接入契约

设备侧至少提交：

```json
{
  "eventId": "stable-device-event-id",
  "deviceCode": "TECAN_F200_01",
  "commandNo": "CMD-...",
  "status": "FAILED",
  "errorCode": "DOOR_OPEN",
  "errorMessage": "Front door is open",
  "severity": "CRITICAL",
  "occurredAt": "2026-10-25T10:30:00+08:00",
  "details": {}
}
```

原则：原始错误码和原文必须保存；平台映射出的中文、分类和处理策略作为独立字段，不能覆盖原文。

## 8. 实施拆分

| 阶段 | 内容 | 预计成本 |
|---|---|---:|
| E-1 | 枚举、DTO、错误分类器、错误码命名约定 | 0.5～1d |
| E-2 | `flow_error_record/action` DDL、DO、Service、查询 API | 1.5～2d |
| E-3 | Flow 内部异常统一写入错误记录 | 1d |
| E-4 | `device_error_event` 与设备回调错误接入 | 1～1.5d |
| E-5 | 人工处置 API/页面：查询、确认、终止、重试意图 | 1.5～2d |
| E-6 | 去重、重启恢复、通信未知、设备安全错误测试 | 1～1.5d |

建议先做 **E-1 + E-2 + E-3**，让内部流程错误先完整落库；随后接设备错误，避免两条链路同时改动难以验证。

## 9. 第一版验收标准

- 同一节点连续失败三次能看到三条发生记录及各自 attempt，而不是只剩最后一段文本。
- 设备错误保留设备原始错误码、原文和原始报文引用。
- 重复 `eventId` 不会重复推进流程或重复创建待处理错误。
- 通信超时进入 `WAITING_EXTERNAL_CONFIRMATION`，不会自动重发物理命令。
- CRITICAL/设备安全错误只能人工确认，不允许自动重试。
- 每次人工确认、重试、跳过、终止都有操作者、时间、原因和结果流水。
