# 三模块修复计划(device / flow / wms)

> 依据:2026-10 架构评审 28 条建议逐条核实后的结论。核心原则:**每类业务状态只有一个模块负责;跨模块只走契约层;对真实设备和物料的操作必须可追踪、可幂等、可恢复。**
>
> 估算口径:一名熟悉本代码库的后端全职开发。工作项编号 W-x.y,建议编号(#)指评审原条目。

## 实施策略摘要:先单并发,再按需要升级多并发

> 当前推荐选择:**单应用实例 + 单流程执行线程 + 单设备独占 + WMS 轻量占用**。业务接口从第一天保留
> `executionId/nodeId/iterationNo/attempt/idempotentKey`，数据库继续保留唯一约束和状态条件更新；这样一期不承担
> 分布式并发复杂度，但以后升级多并发时不需要推翻接口和核心表。

### 当前实施范围（2026-10-25 确认）

#### 核心责任边界

| 模块/系统 | 负责决定什么 | 明确不负责什么 |
|---|---|---|
| Flow 调度域 | 何时执行、执行顺序、依赖关系、分支/汇合、超时策略、业务重试意图、人工介入、流程最终结果 | 不判断设备是否真实空闲；不维护设备占用锁、运行队列、在途数；不决定同一命令能否在设备端再次执行 |
| 设备侧 | 是否接受命令、设备占用、忙闲、运行、暂停/取消、排队、并发能力、命令幂等、命令终态和设备故障 | 不决定整个业务流程的下一节点、样本生命周期或 WMS 物料变化 |
| WMS | 样本/物料是否可用、数量变化、槽位状态、样本谱系、消耗幂等和库存流水 | 不控制设备运行；不决定流程分支和流程最终状态 |

> **明确原则：本系统以“整体业务调度”为核心。** Flow 向设备侧表达“希望执行什么”以及业务身份、截止时间和业务上下文；
> 设备侧根据自身能力决定“能否执行、何时执行、是否重复、当前执行到哪里”。Flow 只消费设备侧返回的
> `ACCEPTED/BUSY/RUNNING/SUCCEEDED/FAILED/TIMED_OUT/CANCELLED` 等事实，并据此推进业务流程。

设备调用采用“命令请求 + 状态事实”边界：

| Flow 发给设备侧 | 设备侧返回给 Flow |
|---|---|
| `businessKey/sourceRef` | `deviceCommandId` |
| 设备与动作标识 | 是否接受：`ACCEPTED/BUSY/REJECTED` |
| 参数和期望截止时间 | 当前状态：`RUNNING/...` |
| 业务执行上下文 | 最终状态与结果/错误 |
| 取消意图（如设备支持） | 完成通知及可查询结果 |

Flow 的“重试”只表示重新提出业务意图：相同 attempt 使用同一业务键，设备侧必须返回原命令；只有 Flow 创建新的
attempt 时才形成新的业务键。设备侧仍有权根据设备能力拒绝、排队或接受这次新尝试。

#### 外部执行方边界

设备侧属于**不受本系统直接管理的外部执行方**。本系统不能把“请求已发送”“HTTP 200”“请求超时”直接解释成设备真实执行结果：

| 本系统观测到的情况 | 能说明什么 | 不能说明什么 | Flow 应采取的动作 |
|---|---|---|---|
| 请求发送成功 | 通信请求已经发出 | 设备已经接受或开始执行 | 等待设备侧返回命令号/受理状态 |
| HTTP 200/202 | 网关或设备侧已受理请求 | 物理动作已经完成 | 节点进入 WAITING，查询或等待完成通知 |
| HTTP 超时/断网 | 本系统没有及时获得响应 | 设备一定没有执行 | 按业务键查询；无法确认时进入 UNKNOWN/人工确认，禁止盲目重发 |
| BUSY/REJECTED | 设备侧当前不接受任务 | 设备故障或永远不能执行 | Flow 决定等待、换设备、结束或人工处理 |
| RUNNING | 设备侧声明正在执行 | 最终一定成功 | 持续等待或按业务超时策略升级处理 |
| SUCCEEDED | 设备侧声明完成 | WMS 已完成消耗或样本已推进 | Flow 再驱动 WMS 完成业务状态和物料流水 |
| FAILED/TIMED_OUT | 设备侧声明失败/超时 | 物理现场一定处于安全状态 | Flow 进入失败/人工分支，必要时要求现场确认 |
| 完成通知重复到达 | 至少一次投递语义 | 需要再次完成流程节点 | 按事件 ID/命令 ID 幂等消费 |

设备侧自身需要处理的事项：

| 设备侧责任 | 最低要求 |
|---|---|
| 命令受理 | 明确返回 ACCEPTED/BUSY/REJECTED，不用模糊的 HTTP 成功代替业务受理结果 |
| 命令身份 | 保存本系统业务键与设备命令号映射，支持重复请求返回原命令 |
| 设备占用 | 自行判断忙闲、维护锁、通道占用和最大在途数 |
| 命令运行 | 自行负责开始、暂停、继续、取消、完成和故障处理 |
| 状态持久化 | 设备侧重启后仍能查询已受理命令，不依赖本系统内存状态 |
| 结果查询 | 按命令号或业务键返回权威状态和结果 |
| 完成通知 | 使用稳定事件 ID；允许重投，直到获得确认或达到设备侧策略上限 |
| 超时处理 | 区分“通信超时”“排队超时”“执行超时”，不能统一解释为未执行 |
| 安全处置 | 物理动作失败、急停、断电后的现场安全由设备侧负责 |

本系统的决策责任：

| Flow/WMS 责任 | 处理方式 |
|---|---|
| 任务编排 | 决定先后顺序、依赖、分支、汇合和业务截止时间 |
| 设备选择意图 | 指定目标设备/能力，或根据业务规则选择候选；不直接控制设备锁 |
| 状态对账 | 对通知结果进行查询复核；UNKNOWN 状态不自动当成功或失败 |
| 业务重试 | 创建新的 attempt；是否真正执行仍由设备侧受理 |
| 异常决策 | 决定等待、换设备、补偿、终止或人工介入 |
| WMS 推进 | 仅在获得明确设备事实后执行样本状态与物料变化 |
| 全链路追踪 | 保存 execution/node/attempt 与外部 commandId、eventId 的对应关系 |

建议 Flow 对外部执行结果增加 `UNKNOWN` 语义：当通信结果不确定、设备侧暂不可查询或状态相互矛盾时，节点进入
`WAITING_EXTERNAL_CONFIRMATION`，由后续查询或人工确认收口；禁止直接重新执行物理动作。

| 范围 | 当前决定 | 责任边界 | 本计划动作 |
|---|---|---|---|
| Flow 节点认领 | **先做** | 本系统 Flow 模块 | 保留并强化 `PENDING → RUNNING` 条件认领；补孤儿节点恢复，为以后租约升级预留字段和接口 |
| WMS 物料使用 | **先做** | 本系统 WMS 模块 | 完成可用性检查、物料使用/消耗、必要的轻量占用和流水闭环 |
| WMS 操作幂等 | **先做** | 本系统 WMS + Flow 调用侧 | 接通现有 `uk_idempotent`；Flow 统一生成并传递 `idempotentKey` |
| 样本谱系 | **先做** | 本系统 WMS 模块 | 固化原始样本、单父分样、实物实例关联；多父合样按实际需求单独启用 |
| 事件通知 | **先做** | 本系统模块间协作 | 一期采用 Spring 事件加速 + DB 状态/扫描补偿；补事件标识、消费幂等和测试 |
| 设备调度 | **忽略/不做** | 设备侧 | 本系统不实现设备排队、`maxInflight`、平台队列或设备队列 |
| 设备命令幂等 | **设备侧负责** | 设备侧 | 本系统只透传 `sourceRef/idempotencyKey` 并查询设备侧命令结果，不建设设备内部幂等实现 |
| 设备占用 | **设备侧负责** | 设备侧 | 本系统只消费“可执行/忙/完成/失败”结果，不维护设备锁和在途计数 |

> 设备侧需要向本系统提供的最小契约：①按业务幂等键提交命令；②重复提交返回同一命令；③按命令号或业务键查询状态；
> ④明确返回 BUSY/ACCEPTED/SUCCEEDED/FAILED/TIMED_OUT；⑤完成通知至少一次投递。Flow 不推断设备内部占用状态。

### 单并发与多并发总览

| 维度 | 单并发方案（一期推荐） | 多并发方案（出现真实需求后） | 单并发成本 | 升级多并发增量 | 升级难度 |
|---|---|---|---:|---:|---|
| 部署形态 | 单个 `boheng-server` 实例 | 多实例部署、任意实例可接管任务 | 0.5d | 2～3d | 中 |
| Flow 执行 | 单线程 Worker；一次执行一个可运行节点 | 可配置线程池；多个流程/节点并行 | 1d | 2～3d | 低 |
| 节点认领 | 保留现有 `PENDING → RUNNING` 条件更新 | CAS + `workerId/leaseUntil/heartbeat` 租约 | 0.5d | 3～4d | 中高 |
| 宕机恢复 | 启动/定时扫描孤儿 `RUNNING`；按步骤类型恢复 | 多实例争抢恢复租约；任一实例接管 | 2～3d | 2～3d | 中 |
| 设备调度 | 设备侧负责，本系统忽略 | 由设备侧决定独占、排队和 `maxInflight` | 0d | 不在本计划 | 外部依赖 |
| 设备命令幂等 | 设备侧实现；本系统透传业务键 | 设备侧保证重复提交返回同一命令 | 0.5d（接入） | 不在本计划 | 外部依赖 |
| 设备占用 | 设备侧负责；本系统只处理 BUSY 等结果 | 设备侧维护锁、在途数和释放 | 0d | 不在本计划 | 外部依赖 |
| WMS 物料使用 | 使用前校验，使用后立即消耗 | 预留、续期、释放、过期回收、竞争裁决 | 1～2d | 4～6d | 高 |
| WMS 操作幂等 | 接通已有 `uk_idempotent` | 机制不变，增加并发与批量冲突测试 | 1～2d | 1～2d | 低 |
| 样本谱系 | 原始样本 + 单父分样 | 多父合样、并行分支谱系合并 | 1～2d | 3～5d | 中 |
| 事件通知 | Spring 事件加速 + DB 扫描补偿 | Outbox/MQ、消费者幂等、多实例投递 | 1d | 5～8d | 高 |

| **合计** | **约 18～24 人日** | **额外约 30～45 人日** | **18～24d** | **30～45d** | **整体中等** |

### 什么算“单并发”和“多并发”

| 场景 | 单并发阶段如何处理 | 何时必须升级多并发 |
|---|---|---|
| 多个用户同时点启动 | API 可以同时访问，但系统串行执行流程 | 出现明显排队、等待时间不能接受 |
| 同时存在多个流程实例 | 可以创建多条记录，但一次只推进一个设备动作 | 要求多个实验流程真正同时运行 |
| 一个流程有并行分支 | 逻辑上保留 DAG，并行分支按顺序执行 | 并行分支必须同时占用不同设备 |
| 多台设备同时工作 | 一期串行调度，不同时下发 | 实验室要求多台仪器同步工作 |
| 同一设备多命令 | 永远独占，一条结束后才允许下一条 | 设备原生支持队列或多通道并行 |
| 多个流程争抢同一试剂 | 单流程阶段不会竞争，使用前再校验 | 多流程运行后需要提前预留资源 |
| 多人重复提交同一操作 | 仍由业务幂等键拦截，不能省略 | 多并发阶段沿用，无需重做 |
| 设备重复回调 | 仍由命令状态 CAS/唯一信号拦截 | 多并发阶段沿用，只增加压力测试 |
| 应用重启 | 扫描数据库恢复，不直接重发物理命令 | 多实例时增加租约和接管机制 |
| 多服务器部署 | 不支持主动—主动，只运行一个业务实例 | 高可用、滚动发布或横向扩容时必须升级 |

### 单并发阶段保留的升级接口

| 保留项 | 单并发时用途 | 多并发升级时的价值 |
|---|---|---|
| `executionId/nodeId/iterationNo/attempt` | 全链路追踪 | 直接作为分布式任务业务身份 |
| `idempotentKey/sourceRef` | 防重复提交、重启重复执行 | 防多实例重复下发和重复扣减 |
| 数据库唯一索引 | 防误操作和重复请求 | 作为并发竞争的最终防线 |
| 状态条件更新（CAS） | 防重复回调 | 支撑多 Worker 抢占与结算 |
| `timeoutAt/deadlineAt` | 超时恢复 | 支撑租约和跨实例接管 |
| API 契约层 | 隔离 flow/device/wms | 后续拆服务时接口基本不变 |
| WMS 流水 | 审计与追踪 | 并发冲突、补偿和对账依据 |

### 易用性评价

| 对象 | 单并发体验 | 升级多并发后的体验 | 评价 |
|---|---|---|---|
| 操作人员 | 简单；设备忙时明确提示或串行等待 | 可同时运行多流程，但需要显示排队、预留、冲突 | 单并发更易用 |
| 流程设计人员 | 不需要配置并发数、队列和资源锁 | 需要理解并行分支、重试、资源预留 | 多并发学习成本较高 |
| 开发人员 | 状态链短，容易调试和定位 | 需要处理租约、竞争、重复消费和部分失败 | 单并发维护成本明显更低 |
| 运维人员 | 单实例、MySQL、Redis 即可 | 需要多实例、健康检查、统一调度或 MQ | 单并发部署最简单 |
| 后续升级 | 保留幂等键/CAS/API 契约后可渐进升级 | 不需要重写业务模块，只增强调度与资源层 | **易用性中高** |

### 推荐决策

| 决策项 | 当前选择 | 说明 |
|---|---|---|
| Flow Worker | 单线程 | 不删除 DAG，只把执行并发度设为 1 |
| Server 实例 | 单业务实例 | 暂不支持主动—主动；数据库和 Redis 可独立部署 |
| Device | 设备调度、幂等、占用均由设备侧负责 | 本系统仅透传业务键、查询状态、消费完成通知 |
| WMS | 轻量占用，不做完整预留系统 | 如果设备等待时间较长，可只加 `reservedByExecutionId` |
| 事件 | Spring 事件 + DB 扫描补偿 | 暂不引入 MQ/Outbox |
| 幂等 | 必须完成 | 它解决的不只是并发，还解决重复请求和宕机恢复 |
| 恢复 | 必须完成 | 单实例重启后没有其他实例接管，更不能省略 |
| 流水 | 必须保留 | 属于审计和追溯，不是并发附属功能 |

### 从单并发升级到多并发的触发条件与步骤

| 阶段 | 触发条件 | 主要改动 | 增量成本 |
|---|---|---|---:|
| S0 单并发上线 | 当前一期 | 单线程 Worker、设备独占、业务幂等、重启恢复、核心闭环 | 18～24d |
| S1 多流程串行排队 | 同时提交任务增多，但设备仍不能并行 | 增加流程待执行队列、优先级、预计等待展示 | 3～5d |
| S2 多设备并行 | 两台以上设备需要同时工作 | 本系统 Worker 池配置化和并行分支调度；设备锁仍由设备侧负责 | 3～5d |
| S3 WMS 资源竞争 | 多流程会争抢同一样本/试剂/槽位 | 完整预留、释放、过期回收、取消补偿 | 5～8d |
| S4 多服务实例 | 需要高可用或横向扩容 | 节点租约、心跳、扫描抢锁、跨实例接管 | 8～12d |
| S5 可靠异步事件 | 事件量上升或需要拆服务 | Outbox/MQ、消费幂等、重试和死信处理 | 6～10d |

升级顺序必须保持 `S0 → S1/S2 → S3 → S4 → S5`。其中 S1 与 S2 可按业务需求二选一先做；没有多实例部署需求时不要提前实现 S4/S5。

## 附 C：固定编码值治理约定

| 场景 | 统一规则 | 禁止做法 |
|---|---|---|
| 状态、类型、模式、来源、等待原因 | 在所属领域的 `enums` 包定义枚举，由领域模块拥有 | Service/Mapper 中直接写 `"RUNNING"`、`"MANUAL"` 等裸值 |
| 数据库存储、跨模块 DTO | 字段可继续保持 `String` 兼容数据库和 JSON，但写入/比较必须来自枚举 | 为了省事在多个模块重复声明同名常量 |
| 状态迁移 | 迁移规则集中在领域 Service 或状态机表中，非法值明确拒绝 | Controller、Flow 直接替 WMS/设备决定领域状态 |
| 外部设备返回值 | 在 device-api 契约层收敛；未知值保留原文并进入待确认/失败路径 | Flow 猜测设备是否执行成功，或把超时当作失败重发 |
| 展示文案、JSON 字段名、错误码 | 不属于状态枚举，可保留字符串；高频字段名可另建常量 | 为“零字符串”机械枚举普通中文、日志和协议字段名 |

新增固定编码值时，代码评审必须回答三件事：归哪个领域所有、是否需要持久化兼容、未知值如何处理。若答案中包含“多个 Service 自己约定”，则不得合并。
