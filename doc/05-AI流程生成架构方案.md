# AI 生成实验流程：工程化架构方案

> 目标：用现有框架（Flow v3 + WMS + device.task）接入大模型（ChatGPT / 通义千问 / 本地模型），
> 支持**自然语言或一份 SOP 文件 → 生成可发布的实验流程定义**。
> 本文只谈工程化落地：分层、契约、校验闭环、安全红线、数据模型、接口草案、分期。

---

## 一、结论先行

五条关键决策，后面各章是它们的展开：

| # | 决策 | 理由 |
|---|---|---|
| D1 | **LLM 只产出 `FlowNodeDraft` 列表（IR），不产出 DO / SQL / JSON 自由文本** | 校验与装配已有唯一实现，AI 与 UI 共用同一个收敛点 |
| D2 | **分段生成（意图 → 选型 → 组装 → 修复），不做 one-shot 大 JSON** | 20+ 节点一次性生成最容易在 `dependsOn` 上错位；分段后每段可测、可缓存、可人干预 |
| D3 | **能力目录自动导出为工具签名（JSON Schema），新增能力零改 AI 代码** | 「能力 × 编排正交」的设计红利：`step_type` 注册表天然就是函数注册表 |
| D4 | **`bean.invoke` / `script.run` / `route` 的取值必须来自白名单枚举** | 这三处是执行面（RCE 面），LLM 输出视为不可信输入 |
| D5 | **Spring AI 1.1.x 限制在 `boheng-module-ai` 内部，业务模块只依赖自研契约 `LlmApi`** | 换框架（LangChain4j / 直连 HTTP / 外部网关）不影响 flow 代码 |

框架选型结论：**主干用 Spring AI 1.1.x**（`boheng-frame` 是 Spring Boot 3.5.15，正好对上 1.1.x 这条线；
2.x 要求 Spring Boot 4.x，那是 `sz-boot-parent` 那条线的选择）；通义千问走
`spring-ai-alibaba-starter-dashscope`，OpenAI / Azure / 自建 vLLM / Ollama 走 OpenAI 兼容端点。

## 二、现状盘点：谁是现成的，谁要从头做

### 2.1 现成可复用的（AI 链路里的角色）

| 现有组件 | 位置 | 在 AI 链路里的角色 |
|---|---|---|
| `StepTypeDescriptor` / `StepTypeRegistry` | `engine/type/` | **工具签名源**：`type()/role()/configType()/validate()` 就是能力声明 |
| `engine/type/config/*Config` | `engine/type/config/` | 配置 POJO，反射生成 JSON Schema 的原料 |
| `flow_step`（能力目录） | 表 | **业务能力清单**：`stepKey/name/stepType/typeConfig/defaultParams` + 语义说明 |
| `FlowBeanAction` / `FlowRouteAction` / `FlowDispatchAction` | `engine/` | **白名单枚举源**：Bean 名、路由动作只能从这里取 |
| `FlowNodeDraft` | `service/definition/model/` | **IR（中间表示）**：nodeId/stepType/typeConfig/dependsOn/joinPolicy/branches/mappings |
| `FlowDraftAssembler` | `service/definition/` | 行 → Draft 装配（apply 落地时的对照物） |
| `FlowGraphChecker` | `service/definition/` | **免费校验器**：`checkStructure` / `checkPublish` / `checksum`，带 `DeviceLookup`、`SubflowLookup` 回调 |
| `FlowConstants` | `enums/` | 硬约束：`MAX_NODES=60`、`NODE_ID_REGEX`、`BRANCH_KEY_REGEX`、`MAX_ATTEMPTS_LIMIT=5`、`PARAM_COMMENTS_KEY` |
| `FileApi` | `boheng-module-infra/api/file/` | SOP 文件存取 |
| `FlowLogContextHolder` + `FlowLogConverter` | `framework/log/` | LLM 调用日志与执行日志同构（同 trace 风格） |
| `FlowDefinitionController` | `controller/admin/definition/` | `/validate`、`/publish`、`/revise` 直接复用，不必新写发布链路 |

**最重要的一条**：`FlowGraphChecker` 已经把「画得出跑不了」的防线做完了
（节点编码规则、依赖存在性、环检测、汇合策略、分支出口 `default` 兜底、设备/子流程引用）。
LLM 输出走同一个校验器，等于**零成本获得一个确定性验证器**。这是整个方案能低成本起步的根本原因。

### 2.2 缺口

| 缺口 | 说明 |
|---|---|
| 无 AI 模块 | 仓库里没有 `boheng-module-ai`，也没有任何 `spring-ai` / LLM SDK 依赖 |
| 无 LLM 客户端与模型配置 | 没有 key 管理、模型路由、限流、计量 |
| 前端 `web/src/views/ai/*` 是模板残留 | `chat/image/knowledge/mindmap/model/music/workflow/write` 是 yudao 原版页面，后端无对应实现，路由未接。**不要误以为已经有一套 AI 模块** |
| SOP 文档解析 | 无 word/pdf 解析；`FileApi` 只负责存取 |

```
└──────────────────────────────────────────────────────────────────────┘
                                 ↓ 自然语言 / fileId / 增量指令

                                 ↓ LlmApi（自研契约，不泄漏 Spring AI 类型）
┌──────────────────────────────────────────────────────────────────────┐
│ L3 LLM 接入层（新增 boheng-module-ai / boheng-module-ai-api）         │
│  LlmApi · 模型配置（落库 + 前端可配）· 多模型路由 · 限流 · token 计量  │
│  实现：SpringAiLlmApiImpl（Spring AI 1.1.x ChatClient）               │
└──────────────────────────────────────────────────────────────────────┘
                                 ↓ 结构化输出 / tool calling
┌──────────────────────────────────────────────────────────────────────┐
│ L2 模型       千问（DashScope） · OpenAI/Azure · 自建 vLLM/Ollama      │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ L1 底座（已有，不改）  Flow 引擎 · WMS 实例/样本 · device.task 队列     │

└──────────────────────────────────────────────────────────────────────┘
```

```
boheng-module-flow  ──depends──▶  boheng-module-ai-api   （只依赖契约）
                                        ▲
                                        │ implements
                                  boheng-module-ai        （Spring AI 在这里）
```

## 四、关键机制设计

### 4.1 能力目录 → 工具签名（D3，方案的核心）

聚合四个来源，输出两套视图：

| 来源 | 枚举方式 | 产出 |
|---|---|---|
| 内置类型 | `StepTypeRegistry` 全部 `StepTypeDescriptor` | `type` / `role` / `completionMode` / `retryable` |
| 类型配置 | `descriptor.configType()` 反射（Jackson 注解）+ Bean Validation 注解 | `typeConfig` 的 JSON Schema |
| 白名单动作 | `FlowBeanAction.beans()`、`FlowRouteAction`、`FlowDispatchAction` | `beanName` / 动作码的枚举值 |
| 业务能力 | `flow_step` 表（仅 `status=0`） | 可复用步骤清单（`stepKey` + 语义说明） |
| 设备能力 | `boheng-module-device-api`（设备/动作码） | `device.command` / `device.task` 的合法取值 |

两套视图：

- **紧凑视图（给 S2 选型用）**：`stepKey` + `name` + 一句话语义 + 关键参数名。控制在几百 token 内，可缓存。
- **完整视图（给 S3 组装用）**：每个候选步骤一份 JSON Schema 工具定义。

> 参数语义注释可以直接复用 `FlowConstants.PARAM_COMMENTS_KEY`（`__comments__`）这个已有约定——
> 这个机制本来就是「给人看的字段说明」，喂给 LLM 是同一件事，不用新造轮子。

### 4.2 四段式生成（D2）

```
S1 意图解析   NL / SOP 文本 ──▶ ExperimentIntent
              {goal, sampleSpec, detections[], deviceConstraints, parallelism,
               expectedOutputs, openQuestions[]}

S2 能力选型   Intent + 紧凑目录 ──▶ 有序步骤清单
              [{rank, stepKey|stepType, why, paramsDraft}]     ← 人可干预点

S3 图组装     清单 + 完整 schema ──▶ FlowNodeDraft[]
              {nodeId, stepType|stepId, typeConfig, dependsOn,
               joinPolicy, branches, mappings, runConfig}

S4 校验修复   drafts ──▶ FlowGraphChecker.checkStructure / checkPublish
              issues 为空 → 落草稿；非空 → issues 回喂，最多 3 轮 → 仍失败交人工
```

为什么这样切：

- **S2 是人工干预的黄金位置**。选错了能力比画错了线更好修——用户在这里删一行/加一行，比在图上看 20 个节点快得多。
- **S4 用确定性校验器，不让 LLM 自评**。模型的自我检查不可信，`FlowGraphChecker` 可信。
- 每段输出小，可以**独立缓存 + 独立重试**：S2 的目录快照、S3 的 schema 都是可复用的 prompt 前缀（配合 Prompt Caching 能显著省成本）。
- 复杂度低时可以退化成 one-shot（S2+S3 合并），但**默认走分段**。

### 4.3 IR 契约

LLM 的产出结构体就是 `FlowNodeDraft` 的 JSON 形态，字段一一对应。
配套要求（都来自 `FlowConstants`，作为 schema 的一部分约束给模型）：

| 字段 | 约束 | 来源 |
|---|---|---|
| `nodeId` | `^[a-z][a-z0-9_]{0,31}$` | `NODE_ID_REGEX` |
| 分支出口名 | `^[a-z][a-z0-9_]{0,31}$`，且含 `default` | `BRANCH_KEY_REGEX` / `BRANCH_DEFAULT` |
| 节点数 | ≤ 60 | `MAX_NODES` |
| `timeoutMs` | 1000 ~ 86400000（或 -1 永不超时） | `MIN/MAX/NO_TIMEOUT_MS` |
| `maxAttempts` | ≤ 5 | `MAX_ATTEMPTS_LIMIT` |
| 参数注释 | `__comments__` 保留键 | `PARAM_COMMENTS_KEY` |

**结构化输出的实现方式**：用 Spring AI 的 `ChatClient` + `BeanOutputConverter`
（或 `generateObject` 风格调用），由框架把 schema 注入 prompt 并解析回 POJO——
不要自己拼 "请返回 JSON" 再手工 parse。

### 4.4 落地与 Diff

- `/flow/ai/apply`：把 IR 写进指定 `definitionId` 的**草稿**（`status=DRAFT` 才允许）。
  - 按 `nodeId` upsert；IR 中不存在的旧节点删除（差集）；
  - 写完后调 `FlowGraphChecker.checkStructure` 兜一层（防止并发改写）；
  - 返回 `checksum`（`FlowGraphChecker.checksum(nodes)`）供前端做变更指纹。
- **绝不自动发布**。生成 → 落草稿 → 人工在画布上点验 → 走既有 `/publish`。
  这是 GxP 场景下唯一能接受的姿势（谁批准了这条流程，审计要能答）。

### 4.5 安全红线（D4）

> 原则一句话：**LLM 的输出等价于外部用户输入，必须过服务端白名单。**

| 风险面 | 禁止 | 正确做法 |
|---|---|---|
| `bean.invoke.beanName` | 模型自由生成 Bean 名 | 只从 `FlowBeanAction` 实现集合里选，服务端二次校验不在集合直接拒绝 |
| `script.run` 表达式 | 模型自由生成 aviator 表达式 | 不开放自由生成；只允许从预置表达式模板 + 参数占位符里选 |
| `route` / `validate` 动作 | 自由命名 | 从 `FlowRouteAction` / 白名单 Bean 枚举里选 |
| 控制类节点 | 由 LLM 自由构造嵌套结构 | 只允许按固定模板在 S4 修复阶段插入（loop/subflow 由引擎语义强约束） |
| SOP 文件内容 | 当作指令执行 | **文件内容按数据处理**，system prompt 固定，工具白名单不变（防 Prompt 注入） |
| 停用能力 | 进入 prompt | `flow_step` 只取 `status=0` |

`bean.invoke` 已经实现了「只有显式实现 `FlowBeanAction` 的 Bean 能被调用」，
这个白名单现在要**再往前推一步**：不仅执行时校验，生成时也不给模型任何白名单外的选项。

### 4.6 dry-run 沙箱

生成出来的流程不能只是"看起来对"。利用引擎的 `StepExecutor` 抽象做零侵入模拟：

- 新增 `dryrun` profile 下的 `MockDeviceCommandExecutor` / `MockDeviceTaskExecutor`
  （同 `type()` 优先注册，或加一层装饰器），返回预置的成功/失败样本；
- `timer.wait` 压缩为 0；`manual.task` 自动通过；
- 输出「预计执行轨迹」：节点顺序、各节点入参、分支走向、总节点数；
- 限制：dry-run 只跑单次（不展开 loop、不扇出 FANOUT 超过 1 组），并设总时长上限。

### 4.7 可观测与成本

- 生成会话号 `gen_no`（前缀风格与 `EXECUTION_NO_PREFIX` 对齐），LLM 调用日志走 Loki，
  格式与执行日志同构：`[gen=xxx model=qwen-max tokens=1234/567 latency=2.3s]`；
- token 计量入表，可按会话/模型/租户聚合；
- 输入 hash 命中缓存直接回放（S2 的目录快照 + S3 的 schema 部分尤其值钱）。

## 五、框架选型对比

| 方案 | 形态 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A. Spring AI 1.1.x + DashScope starter / OpenAI starter** | 框架 | 官方维护；`ChatClient` 流式/结构化输出/tool calling/ChatMemory/Advisor/重试全套；多模型统一 API；有 MCP 官方支持 | 需引新依赖（版本必须锁 1.1.x，对 Boot 3.5）；抽象层对厂商特有能力的覆盖要逐个验证 | **★ 主干** |
| B. spring-ai-alibaba Agent Framework（ReactAgent / Graph Runtime） | 框架（A 之上） | 多角色协作（生成-评审-修复）、人类介入、状态快照、图运行时 | 引入 LangGraph 式心智负担；当前需求是"生成草稿"，不是长跑 Agent | 二期可选（做三角色迭代评审时再上） |
| C. LangChain4j | 框架 | 生态成熟，`AiServices` 注解式声明很省事 | 与 A 功能高度重叠，多养一套抽象；两套 Message 体系容易混 | 备选，不并行引入 |
| D. 直连 HTTP（WebClient + OpenAI 兼容协议） | 自研 | 零新依赖；对自建 vLLM / Ollama / 未支持厂商最省事 | tool calling / 结构化输出 / 重试 / 流式解析全部自己写 | **兜底扩展点**（作为 `LlmApi` 的第二种实现） |
| E. 外部平台（Dify / Coze / n8n）扛编排 | 平台 | 搭对话机器人快 | 流程图生成的校验闭环在我们这边，隔着平台会造成**双份真相**；调试链路断在中间 | 不做主链路；运营侧问答可另说 |

选 A 的额外理由：`spring-ai-alibaba-starter-dashscope` 依赖里带的
`victools jsonschema-generator` 正好是 4.1 节「POJO → JSON Schema」要用的东西，不用另找轮子。
注意点两个：DashScope starter 会带 `dashscope-sdk-java` 的传递依赖，
需要 `dependencyManagement` 里统一 `jsonschema-generator` 版本、并排除 `slf4j-simple` 防止与 logback 双绑。

> 版本线提醒：Spring AI 2.x 要求 Spring Boot 4.x——如果以后 `boheng-frame` 跟着升到 Boot 4，
> 才是切 2.x 的时机；现在选 1.1.x 是唯一正确的对齐点。

## 六、数据模型（新增表）

沿用底座约定：租户表继承 `TenantBaseDO`（带 `tenant_id`）、审计列固定、
**全库 0 UNIQUE**（普通索引 + Service 层唯一校验）、主键显式 `@TableId(ASSIGN_ID)` 雪花。

```sql
-- 模型配置：前端可配、多模型并存、key 加密存储
ai_model_config
  id, tenant_id, name, provider(DASHSCOPE|OPENAI|OPENAI_COMPAT),
  base_url, api_key_cipher, model, temperature, max_tokens,
  timeout_ms, default_flag, status, remark,
  creator, create_time, updater, update_time, deleted

-- 生成会话：一次"把某个实验意图变成流程"的完整过程
ai_flow_session
  id, tenant_id, definition_id, title, model_config_id,
  phase(INTENT|SELECT|ASSEMBLE|REPAIR|DONE), status,
  last_generation_id, ..., deleted

-- 每次生成（含中间段与修复轮次）：审计与回放的核心
flow_ai_generation
  id, tenant_id, session_id, round, phase, model,
  prompt_text, file_id, input_hash,
  intent_json, selection_json, ir_json, issues_json,
  prompt_tokens, completion_tokens, latency_ms, status,
  ..., deleted
```

设计要点：

- `input_hash` 用于**缓存命中**与去重（同输入同模型同 prompt 版本 → 直接回放，不烧 token）；
- `ir_json` 存每次产出的快照，`issues_json` 存校验结果——出问题能完整复盘"模型当时输出了什么、校验器报了什么都"；
- `ai_flow_session.definition_id` 允许为空（先自由生成，再决定落到哪个流程编码）；
- 菜单挂到流程域下（写菜单 SQL 前先查 `MAX(id)`，沿用现有 ID 段约定）。

## 七、接口草案

```
# 会话
POST /admin-api/ai/flow-session/create      {definitionId?}                → sessionId
POST /admin-api/ai/flow-session/generate    {sessionId, prompt?, fileId?}  → generationId
POST /admin-api/ai/flow-session/refine      {sessionId, instruction}       → generationId
GET  /admin-api/ai/flow-session/page        # 会话列表（谁生成了什么）
GET  /admin-api/ai/flow-session/{id}/draft  → {phase, nodes[], issues[], checksum, question?}

# 落地
POST /admin-api/ai/flow-session/{id}/apply  {definitionId}  → {changed, checksum}
POST /admin-api/flow/definition/{id}/dry-run                → {trace[], warnings[]}   # 新增

# 配置
GET  /admin-api/ai/model/simple-list
POST /admin-api/ai/model/save | /delete | /test-connection
```

`{id}/draft` 返回 `question` 字段是为了让 S1 能反问
（比如"样本是血清还是全血？""用哪台酶标仪？"）——
这比让模型瞎猜参数值强，也是 Intent 阶段 `openQuestions[]` 的出口。

## 八、落地分期

| 期 | 内容 | 验收标准 |
|---|---|---|
| **P0** | `boheng-module-ai` + `ai_model_config` + `LlmApi`；跑通一次「qwen-max 结构化输出 FlowNodeDraft」冒烟 | 一个单测：给定 prompt，拿到能通过 `checkStructure` 的 drafts |
| **P1** | 能力目录导出 + 四段式生成 + `apply` 落草稿 + 设计器右侧 AI 面板 | 自然语言"把 12 个水样做重金属前处理再上机检测"→ 生成可校验通过的草稿 |
| **P2** | SOP 文件解析（docx/pdf）+ dry-run + diff 预览 + token 计量与多模型配置页 | 上传一份 SOP → 生成的流程与人工编排结果差异可解释 |
| **P3** | 参数推荐/自优化（接数据收集方向的历史执行数据做 few-shot 与参数先验）；能力目录暴露为 MCP server 供外部 Agent 调用 | 参数推荐命中率可量化 |

**P1 就是最小闭环**，值得一次性做完——只有生成不能落地，等于没做。

## 九、风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模型幻觉节点/参数 | 流程跑不起来或跑错实验 | JSON Schema 强约束 + `FlowGraphChecker` 兜底 + 强制人工确认发布 |
| `dependsOn` 拓扑错位 | 图非法（环/悬空引用） | 分段生成 + S4 修复回喂 + 发布期全量校验 |
| `bean.invoke` / `script.run` 变成 RCE 入口 | **安全事故** | 白名单枚举 + 服务端二次校验（见 4.5） |
| SOP 文件内 Prompt 注入 | 越权生成 | 文件按数据处理、system prompt 固定、工具白名单不变 |
| 成本不可控 | 烧钱 | 会话配额 + 输入 hash 缓存 + prompt 前缀复用 + Prompt Caching |
| 模型不可用/不稳定 | 功能不可用 | 多模型路由（主备）+ 降级到人工画布 + 生成全程可中断 |
| 供应商锁定 | 迁移成本 | 业务模块只依赖 `LlmApi`，Spring AI 类型不外泄（D5） |
| 生成结果无人负责 | 合规风险 | 会话表记录 prompt/模型/产出/校验/操作人，发布沿用既有审计链路 |

---

## 十、一句话总结

**这套方案能便宜地做起来，不是因为 LLM 有多强，而是因为 Flow v3 已经把
「能力目录 + IR + 确定性校验器」三件东西备齐了**——AI 要做的事情被压缩成
「按 schema 填一个 IR」，剩下的正确性由既有校验器保证。工程上真正要投入的只有：
LLM 接入层、能力目录→schema 的导出、四段式生成编排，以及守住 4.5 的安全红线。
