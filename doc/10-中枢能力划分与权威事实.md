# 中枢能力划分与权威事实（v1 讨论稿）

> 接续 `00-整体架构分析.md`。00 回答「四块怎么拼起来」，本篇回答「作为实验室中枢，哪一条事实归谁」。
> 本文所有「现状」列均对照当前代码核对，不是设计设想。
> 配图：`doc/diagrams/capability-authority.html`（能力与权威边界，5 纵向域 + 2 横向层）。
> 实施排期见 `11-中枢平台实施方案.md`。

---

## 一、结论

1. **现有四域（物料/样本、设备、流程）作为起步骨架成立**，不需要推倒重构。
2. **但对外目标架构应表述为「5 个纵向能力域 + 2 个横向支撑层」**，而不是六个平级域。
3. **权威按事实划分，不按系统划分**；并且必须补上「时间权威」这一维度。
4. 当前最贵的缺口不是功能，是**外部关联没有统一模型**——已有五套互不相认的关联字段。

## 二、第一原则：一个事实只能有一个写入者

### 2.1 三层权威

| 层次 | 权威归属 | 内容 | 外部系统可否改写 |
|---|---|---|---|
| **业务权威** | 外部系统（LIMS/MES）或平台 | 业务编号、业务要求、业务优先级、样本业务身份 | 业务字段可，执行字段不可 |
| **执行权威** | 平台，唯一 | 分了哪台设备、走到哪一步、出了什么异常、产出什么原始数据 | **不可** |
| **物理权威** | 平台，唯一 | 实物在哪、占哪个库位、被谁占用 | **不可** |

判据一句话：**外部系统可以「提出要求」和「接收结果」，不能「改写过程」。**

### 2.2 时间权威（本稿新增）

只有「谁写」没有「何时算数」，中枢仍然不可审计。必须区分四条时间轴：

| 时间轴 | 语义 | 载体 | 现状 |
|---|---|---|---|
| 业务时间 | 事情何时真的发生 | `flow_step_execution.started_at/finished_at`、`device_command.sent_at/finished_at` | ✅ 有 |
| 记录时间 | 平台何时知道 | `create_time/update_time` | ✅ 有 |
| 设备时间 | 设备自己打的时间戳 | 仪器数据文件内部 | ❌ **无字段承载** |
| 时钟偏移 | 设备时钟相对标准时的漂移 | 无 | ❌ **无字段承载** |

实测：`device_data_raw` 共 19 列，只有 `received_time`，没有 `device_time`，
也没有 `clock_offset_ms`。后果是——仪器文件里自带的时间戳无法归一到平台时基，
审计时只能回答「我们几点收到的」，不能回答「几点测的」。

**最小改动**：`device_data_raw` 增加 `device_time` 与 `clock_offset_ms`；
校准记录（`device_calibration`）同时保存「校准当时测得的偏移」，让历史数据可回溯换算。

### 2.3 时间的两个陷阱

- **记录时间不能被业务时间覆盖**。`update_time` 一旦被回填为业务时间，审计链即失效。
- **排序不能依赖业务时间**。设备时钟漂移会让业务时间乱序，事件重放必须按记录时间。

## 三、权威矩阵

每一行是「一条事实」，而不是「一张表」。同一张表可能承载多条事实（如 `wms_sample_info`
同时承载业务身份与执行状态），这两条事实的权威归属不同。

| # | 事实 | 载体 | 唯一写入者 | 外部可读 | 外部可否决 | 现状 |
|---|---|---|---|---|---|---|
| 1 | 业务任务身份 | 外部单据（LIMS/MES） | 外部系统 | — | — | ❌ 平台内无载体 |
| 2 | 平台任务 ↔ 外部任务映射 | 待建关联表 | 关联层 | 是 | 是（撤回） | ❌ 散落 5 处 |
| 3 | 执行实例 | `flow_execution` | 实验执行域 | 是 | 否 | ✅ |
| 4 | 步骤执行 | `flow_step_execution` | 实验执行域 | 是 | 否 | ✅ |
| 5 | 步骤输入快照 | `flow_step_execution.input_snapshot` | 实验执行域 | 是 | 否 | ✅ |
| 6 | 设备命令 | `device_command` | 设备域 | 是 | 否 | ✅ |
| 7 | 设备命令结果 | `device_command.status` + `response_json` | 设备域 | 是 | 否 | ✅ |
| 8 | 原始数据 | `device_data_raw` | 数据域 | 是 | 否 | ⚠️ 缺设备时间 |
| 9 | 标准化测量 | `device_measurement` | 数据域 | 是 | 否 | ✅ |
| 10 | 分析结论 | `device_analysis_result` | 数据域 | 是 | 否（可要求重算） | ✅ |
| 11 | 样本业务身份 | `wms_sample_info.external_id` | 外部系统 | — | 否 | ⚠️ 单串，无来源系统 |
| 12 | 样本执行状态 | `wms_sample_info.status` | 实验执行域（经 `SampleApi`） | 是 | 否 | ⚠️ 无权威声明 |
| 13 | 实物实例 | `wms_material_instance` | 样本与物料域 | 是 | 否 | ✅ |
| 14 | 库位占用 | `instance.root_slot_id` | 样本与物料域 | 是 | 否 | ✅ |
| 15 | 资源租约 | 待建 | 资源调度域 | 是 | 否 | ❌ |
| 16 | 审计记录 | 待建 | 身份与合规层 | 是（只增） | 否 | ❌ |

**矩阵里最危险的是第 12 行。** `wms_sample_info.status` 现在有两个潜在写入者：
业务系统想改（因为它认为样本状态是它的业务字段），流程引擎也要改（因为八态由执行驱动）。
这一条必须在文档里显式声明为「执行权威」，否则接入 LIMS 的第一天就会打架。

## 四、对六域划分的修正意见

### 4.1 判据：纵向域必须拥有独立事实链，且可被单独替换

用这条判据筛一遍：

| 能力 | 独立事实链 | 判定 |
|---|---|---|
| 实验执行 | 方法定义 → 执行实例 → 步骤执行 → 信号 | ✅ 纵向域 |
| 设备 | 设备 → 能力 → 命令 → 结果 | ✅ 纵向域 |
| 样本与物料 | 实例 → 落位 → 流水 | ✅ 纵向域 |
| 资源调度 | 申请 → 租约 → 释放 | ✅ 纵向域 |
| 数据与结果 | L0 → L1 → L2 | ✅ 纵向域 |
| 任务与集成 | 无——事实分散在外部单据与各域执行记录中 | ❌ 横向层 |
| 身份与合规 | 无——是策略与记录，不产生事实 | ❌ 横向层 |

### 4.2 「任务与集成」是横向关联层，不是第一个域

它排在第一是因为它是**入口**，不是因为它是一条事实链。它真正的职责只有三件：

1. **映射**：外部任务 ID ↔ 平台执行实例 ID
2. **兜底**：外部任务先到、样本未到 → 落「未匹配」态，不丢数据
3. **幂等**：同一外部任务重复下发 → 同一执行实例（或明确拒绝）

它不持有业务状态，不持有执行状态。把它做成域，会重演「流程域变万能域」的老问题。

### 4.3 「实验执行」：方法定义与执行实例已经分开了

现状是正确的：`flow_definition`（含 `pipeline_key + version + checksum`，`PUBLISHED` 不可变）
与 `flow_execution`（冻结 `definition_id + checksum`）是两张表、两个生命周期。
这一条不用改，只需要在文档里写死：**执行实例只能引用已发布的定义版本，不能引用草稿。**

### 4.4 「样本与物料」：分裂权威，必须显式声明

同一条记录承载两类事实（矩阵第 11、12 行）：
- 业务身份（单号、来源、优先级）→ 外部权威
- 执行状态（八态）→ 平台执行权威

建议在 `wms_sample_info` 增加 `status_authority` 或直接写进契约文档：
**`external_id` / `source` / `order_no` / `priority` 由外部维护，`status` / `current_execution_id`
只允许平台写入。** 这是接入 LIMS 前必须谈定的一条。

### 4.5 「资源与调度」：不是「拆出来」，是「先统一资源模型」

反对现在就把调度器拆成独立模块。理由是三种资源目前完全异构：

| 资源 | 载体 | 可用性表达 |
|---|---|---|
| 库位 | `wms_slot_info.slot_status` | `FREE/OCCUPIED/LOCKED/CHECKING` |
| 设备 | `device_info.status` | `'ONLINE'` 字符串 + busy 标志 |
| 通道/人力/时间窗 | 不存在 | — |

此时拆出来的调度器只能调度它认识的那一种，结果是一个「设备排队器」，而不是调度域。

正确顺序：
1. 定义 `Resource` 抽象：`resource_type + resource_id + capability + capacity`
2. 把 slot / device 各自映射到该抽象（适配器，不改原表）
3. 再按 `doc/08` 已有的 `ResourceLease + fencing token` 设计落地租约

`doc/08` 的方向是对的，缺的就是第 2 步的映射层。

### 4.6 「数据与结果」：L0/L1/L2 是基础，缺两个东西

- **Schema 版本**：`device_measurement` 有 `driver_version`，但没有输出 schema 版本。
  结论一旦可重算，就必须锁定「用哪一版 schema 解释的」。
- **重算入口**：`device_analysis_result` 有 `rule_code + rule_version`（设计正确），
  但没有「按新规则重算历史 measurement」的批处理入口语义。

## 五、建议补上的第七块：身份与合规（横向）

### 5.1 为什么不能塞进任何一个业务域

审计追踪有三条硬约束，任何一条都要求它独立：

1. **跨域**：一次实验的证据横跨执行、设备、数据、物料四个域，放哪个域都是残缺的。
2. **只增不改**：如果审计表放在 wms 模块里，wms 的代码就有权改证据 —— 证据即失效。
3. **不可由业务方授予**：电子签名需要独立的身份与凭证存储，不能跟着业务表。

### 5.2 最小落地（不要求现在就建模块）

| 能力 | 最小形态 |
|---|---|
| 审计追踪 | 一张 `audit_log`（entity + entity_id + action + before/after + actor + 时间），由 AOP 或领域事件统一写，业务代码无写权限 |
| 电子签名 | 一张 `signature`，绑定 `entity + hash + signer + 时间 + 意图`，与审计表分表 |
| 数据留存策略 | 策略表 + 定时任务，按 `data_type` 分级（原始数据永久、中间结果 N 年） |
| 身份 | 复用 system 模块的用户与角色，但签名凭证独立存 |

## 六、三层契约（当前只有第一层）

| 层 | 面向 | 载体 | 状态 |
|---|---|---|---|
| **能力契约** | 模块之间 | `wms-api` / `device-api` | ✅ 已有，缺 `flow-api` |
| **集成契约** | 外部系统（LIMS/MES/设备） | 待建：版本化 API + 事件 + 幂等键 | ❌ 无 |
| **证据契约** | 审计、复算、对外出具 | 待建：只读导出 + schema 版本 + 重放 | ❌ 无 |

三层契约对应三级台阶：能换 / 能接 / 能审。现在第一层都没补齐（`transport → flow`
仍直接 import 6 个实现类），所以谈第二三层为时过早，但**边界要先画出来**。

## 八、待决策（附推荐方案）

以下五条需要业务方或客户拍板。每条都给了推荐方案与理由——**推荐方案按「不把改造成本推给客户」
和「不产生不可追溯的数据」两条原则给出**，可以直接拿去讨论，不需要从零推演。

| 编号 | 决策 | 推荐结论 | 拍板人 |
|---|---|---|---|
| D1 | 样本业务身份唯一性 | `(source_system, external_id)` 联合唯一，不要求全局唯一 | 客户 IT / LIMS 厂商 |
| D2 | 任务撤回语义 | 拆成「撤回」与「终止」，已产生数据一律不删 | 质量负责人（QA） |
| D3 | 时钟基准 | 平台 NTP 为记录时基，设备偏移换算业务时基 | 设备厂商 + 平台架构 |
| D4 | 数据留存期限 | 原始永久只归档；其余按层级分档，≥ 有效期后 1 年 | QA + 客户合规 |
| D5 | 审计追踪粒度 | 只对受控字段做字段级，其余记录级 | QA |

### D1 样本业务身份的唯一性

**问题**：`wms_sample_info.external_id` 是否要求全局唯一？由哪个系统保证？一期是否允许多来源？

**推荐**：不要求 `external_id` 全局唯一，改为 **`(source_system, external_id)` 联合唯一**。
平台自己的 `sample_id` 才是全局主键，外部号只是别名。

**理由**：
- LIMS 与 MES 的单号体系互不相通，强行全局唯一等于要求某一方改造，成本落在客户身上。
- 联合唯一天然支持多来源，且与关联层的三元组（来源系统 + 外部号 + 平台号）口径一致。
- 一期若客户只有单一来源，也不用改表——`source_system` 恒为同一个值即可。

**落地**：`wms_sample_info` 增加 `source_system varchar(32)`；
唯一键用生成列技巧兼容逻辑删除：`CONCAT(tenant_id,':',source_system,':',external_id)`，
仅在 `external_id` 非空时生效（`NULL` 不参与唯一）。

**风险**：若客户明确拒绝改造 MES 侧，退化为 `external_id` 唯一单列，表结构无需变更。

---

### D2 任务撤回语义

**问题**：外部系统撤回任务时，已开始的执行是「取消」还是「终止并保留证据」？

**推荐**：**拆成两个动作，不要合并。**

| 动作 | 前置条件 | 平台行为 |
|---|---|---|
| **撤回 Revoke** | 尚未产生任何 `flow_step_execution` 行 | 删除待执行记录，释放幂等键；`task_correlation` 记一条 revoke 事件 |
| **终止 Abort** | 已产生任意 `flow_step_execution` 行 | **不删除任何记录**；`flow_execution.status = ABORTED`，保留全部步骤、`input_snapshot`、原始数据、设备命令 |

**理由**：
- 生产/受控环境下，「已经产生的数据不能因为业务撤回而消失」是底线，不是选项。
- 判定条件必须是**客观的**（有没有步骤执行行），不能靠外部系统自称「还没开始」。
- 撤回请求本身也要留痕——否则审计时无法解释「这个任务为什么没了」。

**落地**：关联层暴露两个接口 `revokeTask` / `abortTask`；`abortTask` 内部复用流程引擎
已有的取消路径，只增加 `abort_reason` 与 `abort_source`（谁发起的）。

**风险**：若客户要求「撤回即全删」，需由 QA 出具书面豁免，并接受该批次数据不可用于放行。

---

### D3 时钟基准

**问题**：以平台 NTP 为准，还是以某台参考设备为准？

**推荐**：**平台 NTP 做记录时基，设备偏移换算业务时基；不设「参考设备」。**

三层处理：
1. **记录时基** = 平台 NTP，写 `create_time` / `received_time`，**永不覆盖**。
2. **业务时基** = 设备自报时间 − 该设备在最近校准周期测得的 `clock_offset_ms`。
3. **偏移快照**：offset 随原始数据一起落盘（`device_data_raw.clock_offset_ms`），
   不引用校准表的当前值——否则校准记录一变，历史数据的解释就变了。

**理由**：
- 「以参考设备为准」是单点故障：参考设备漂了全局都漂，而且事后无法判断漂了多少。
- 偏移是可测量的：每次校准/期间核查时记录设备时钟与 NTP 的差值，成本几乎为零。
- 快照而非外键，是保证「历史数据永远按当时的偏移解释」。

**落地**：`device_data_raw` 增加 `device_time datetime` + `clock_offset_ms int` +
`time_quality enum(DIRECT, OFFSET_CORRECTED, INFERRED)`。

**风险**：部分老设备不提供时间戳，退化为 `received_time` + `time_quality = INFERRED`，
在数据上明确标记，而不是假装它是准确时间。

---

### D4 数据留存期限

**问题**：原始数据、中间结果、审计记录分别留多久？

**推荐**：**「原始永不物理删除」是唯一硬规则，其余按层级分档。**

| 数据 | 留存 | 处置方式 |
|---|---|---|
| L0 原始（`device_data_raw` + 文件） | 永久 | 元数据永久在线，文件转冷存储；**不删除** |
| L1 标准化（`device_measurement`） | ≥ 产品有效期后 1 年，且不少于 3 年 | 到期归档，不删除 |
| L2 结论（`device_analysis_result`） | 与 L1 同期（因为要能重算） | 归档 |
| 执行记录（`flow_execution` / `step_execution`） | 与 L1 同期 | 归档 |
| 物料流水（`wms_material_movement`） | 与 L1 同期 | 归档 |
| 审计记录（`audit_log`） | ≥ 它所覆盖的最长留存对象，且不少于 10 年 | **只增，永不删** |

**理由**：
- 行业通行做法是「保存至产品有效期后 1 年」，但若涉及出口（FDA/EMA），一般按 10 年配置更安全。
- 只要 L0 还在，L1/L2 理论上可以重算——所以把 L0 定成永久，其余层级就有了兜底。
- 归档 ≠ 删除。删除动作本身需要审批与留痕，成本远高于多存几块硬盘。

**落地**：`data_retention_policy(data_type, retain_days, action)` + 定时任务；
`action` 枚举只允许 `ARCHIVE` / `NOTIFY`，**不允许 `DELETE`**，删除必须走人工审批工单。

**风险**：若客户成本敏感，可在合同里明确「冷存储费用由客户承担」，
但不要为了省钱把 L0 设成可删。

---

### D5 审计追踪粒度

**问题**：审计记录是「谁改了哪一行」，还是「哪一列从什么值改成什么值」？

**推荐**：**只对「受控字段」做字段级，其余做记录级。**

| 级别 | 覆盖字段 |
|---|---|
| 字段级 | 状态、数量、位置、结论值、放行标志、有效期、批次 |
| 记录级 | 备注、显示名、排序、扩展 JSON |

**理由**：
- 全字段级会让 `audit_log` 体积失控——一次 96 孔板实验可产生数十万行。
- 但纯记录级又不够：审计员最常问的恰恰是「这个状态什么时候被谁从什么改成什么」。
- 受控字段是有限的、可枚举的，成本可控而覆盖面足够。

**落地**：`audit_log(entity, entity_id, field, old_value, new_value, actor, actor_type, at, trace_id)`；
字段级白名单写成配置，新增字段需走评审。

**风险**：白名单漏项会导致关键变更无痕。建议在每个域的 Service 层加一条测试用例，
断言受控字段被修改时一定产生审计行。
