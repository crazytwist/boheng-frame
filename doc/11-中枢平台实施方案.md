# 中枢平台实施方案（v1）

> 接续 `10-中枢能力划分与权威事实.md`。10 回答「该是什么样」，本篇回答「按什么顺序做、每期怎么验收」。
> 工期按**单人全职**估算；多人并行的压缩比见第四节。

---

## 一、总体策略：先横后纵，按事实切片

三句话，决定了后面所有排期：

**1. 不按模块排期，按事实链排期。**
「这季度做 WMS、下季度做 Device」的结果是每条链都只有半截，谁也不能单独交付。
按事实链排，每一期结束时都有一条链路能被外人验证。

**2. 横切能力必须先于业务表增长落地。**
审计、时间、关联这三样，每新增一张业务表就要补一次。现在业务表约 30 张，
等长到 80 张再补，成本是现在的三倍以上，而且要回头改历史数据。

**3. 每期必须有一个「别人能验证」的出口。**
不是「做完了」，而是「这件事现在可以被第三方检查了」。出口判据写在每期末尾。

## 二、五期总览

| 期 | 目标 | 单人工期 | 出口判据（一句话） | 记分卡变化 |
|---|---|---|---|---|
| **0 止血与基线** | 契约闭环、指标可测 | 2 天 | 非契约依赖归零，记分卡一条命令出数 | 契约 1→2 |
| **1 关联与时间** | 能接 LIMS、时间可换算 | 1.5 周 | 外部单号能反查到执行实例；任一读数能答「几点测的」 | 契约 2→3・证据 1→2 |
| **2 资源统一** | 资源可寻址、可租用 | 2.5 周 | 新增一种资源只写适配器，调度器不改 | 模型 2→3 |
| **3 证据层** | 能过第三方审计 | 3 周 | 审计员只读系统即可还原一次实验 | 证据 2→3 |
| **4 对外契约** | 可被集成、可对外出具 | 2.5 周 | 没读过代码的人只看 OpenAPI 能写集成 | 互操作 1→2 |

**合计约 10 周单人。** 目标终态记分卡：8/24 → 18/24（L3 能审达成，L4 定标准留待行业背书）。

## 三、分则

### 期 0 · 止血与基线（2 天）

| 编号 | 工作项 | 验收方式（可执行） |
|---|---|---|
| T0.1 | 新建 `boheng-module-flow-api`：`transport` 现在直接 import 的 6 个实现类收敛成接口 + DTO | `grep -rE "import cn\.boheng\.frame\.module\.flow\." --include=*.java boheng-module-transport \| grep -v "\.api\."` 返回 0 行 |
| T0.2 | `boheng-module-transport/pom.xml` 依赖改为 `boheng-module-flow-api` | `mvn -pl boheng-module-transport -am compile` 通过，且 `mvn dependency:tree` 中无 `boheng-module-flow` |
| T0.3 | 把架构记分卡写成脚本（六维，每维一条可跑的检查） | `script/arch-score.sh` 输出六维分数与总分 |
| T0.4 | CI 加契约纪律检查 | 故意在 `transport` 里 import 一个 flow 实现类，CI 必须失败 |

**为什么先做这个**：T0.1 是唯一一处架构纪律破口，改动面极小但性质严重——
它证明「契约隔离」只是口头约定，不是机制。T0.3 则是把「架构指标」从文档变成可执行物，
后面每期结束都要跑它。

T0.3 的六维检查建议：

| 维度 | 检查方式 |
|---|---|
| 契约稳定性 | 非契约跨模块 import 计数（应为 0），有无 `-api` 模块 |
| 可替换性 | 是否存在 SPI 接口目录，适配器注册点数量 |
| 证据可审计 | `audit_log` 是否存在，受控字段白名单条数 |
| 编排普适性 | `flow_node` 支持的结构类型数（顺序/并行/条件/循环/子流程/人工） |
| 模型完备性 | 有效期内可执行的字段规则数 ÷ 已声明规则数 |
| 互操作与度量 | 对外 OpenAPI 端点数、行业格式导出数、指标口径条数 |

### 期 1 · 关联与时间（1.5 周）

**这一期解决两个「没有」：没有外部任务的身份，没有设备自己的时间。**

#### T1.1 关联层表

```sql
create table task_correlation (
  id                    bigint      not null,
  tenant_id             bigint      not null,
  source_system         varchar(32) not null  comment 'LIMS / MES / PLATFORM',
  external_task_no      varchar(64) not null,
  external_revision     int         not null default 1,
  platform_execution_id bigint      null,
  match_status          varchar(16) not null comment 'PENDING/MATCHED/UNMATCHED/REVOKED',
  idempotent_key        varchar(128) not null,
  raw_payload           json        null,
  first_seen_at         datetime    not null,
  matched_at            datetime    null,
  unique key uk_corr (tenant_id, source_system, external_task_no, external_revision),
  unique key uk_corr_idem (tenant_id, idempotent_key)
);
```

三条设计要点：
- **`UNMATCHED` 是合法状态**，不是异常。外部任务先到、样本未到，先落记录，等样本登记后自动匹配。
- **`external_revision`** 是外部系统的修订号。同一单号的不同修订是两条记录，不是覆盖。
- `raw_payload` 存原文。对账出争议时，原文是唯一能自证的东西。

#### T1.2–T1.3 接口与收敛

| 编号 | 工作项 | 验收 |
|---|---|---|
| T1.2 | `TaskCorrelationApi`：`ingest` / `revoke` / `abort` / `query` | 单测覆盖四种 `match_status` 迁移 |
| T1.3 | `flow_execution.business_key` 降级为兼容字段，新逻辑只认 `task_correlation` | 全仓 grep，业务代码不再直接写 `businessKey` |

#### T1.4–T1.6 时间权威

| 编号 | 工作项 | 验收 |
|---|---|---|
| T1.4 | `device_data_raw` 增加 `device_time datetime`、`clock_offset_ms int`、`time_quality varchar(16)` | 迁移脚本可重复执行，`DIRECT/OFFSET_CORRECTED/INFERRED` 三态都有测试 |
| T1.5 | 新表 `device_calibration`：设备、校准时间、结果、有效期、`clock_offset_ms` | 校准过期后 `resolveBusinessTime` 自动降级为 `INFERRED` |
| T1.6 | 时间换算函数 `resolveBusinessTime(raw)`，偏移取**快照**不取当前值 | 单测：改校准记录后，历史 raw 的换算结果不变 |

**期 1 出口**：
1. 给一个外部单号，能反查到 `flow_execution`，并列出该执行下全部 `device_command`
2. 给一条 `device_data_raw`，能同时输出「设备时间 / 换算后时间 / 时间质量」

### 期 2 · 资源统一（2.5 周）

**这一期不拆调度器，只把「资源」变成同一类东西。**

| 编号 | 工作项 | 验收 |
|---|---|---|
| T2.1 | `Resource` 抽象：`resource_type` + `resource_id` + `capability` + `capacity` + `attributes` | 接口方法数 ≤ 8，不出现 `Device`/`Slot` 字样 |
| T2.2 | 两个只读适配器：`SlotResourceAdapter`、`DeviceResourceAdapter`（**不改原表**） | 适配器只做映射，无业务判断 |
| T2.3 | `resource_lease` 表：`resource_key`、`holder_module/type/id`、`fencing_token`、`acquired_at`、`expires_at`、`released_at` | 过期租约可被安全回收，`fencing_token` 单调递增 |
| T2.4 | `ResourceApi`：`acquire` / `renew` / `release` / `query` | 并发测试：两个任务抢同一设备，只有一个拿到租约 |
| T2.5 | `refreshSlotOccupancy` 不再覆盖 `LOCKED`/`CHECKING`，锁语义交给租约 | 有租约时槽位不会被刷新改成 `OCCUPIED` |

**期 2 出口**：
- 新增一种资源（比如「通道」）只需实现一个适配器类 + 一行注册，`ResourceApi` 与租约逻辑零改动
- 并发抢用测试通过，无重复授予

**判定失败信号**：适配器里出现 `if (type == DEVICE)`。一旦出现，说明抽象没做对，停手重审，
宁可晚两周也不要留一个「设备专用调度器」。

### 期 3 · 证据层（3 周）

| 编号 | 工作项 | 验收 |
|---|---|---|
| T3.1 | `audit_log`：`entity`、`entity_id`、`field`、`old_value`、`new_value`、`actor`、`actor_type`、`at`、`trace_id` | 受控字段白名单外的字段不写；白名单配置化 |
| T3.2 | `signature`：绑定 `entity + content_hash + signer + intent + signed_at` | 改任一字后验签失败 |
| T3.3 | `data_retention_policy` + 归档任务，`action` 只允许 `ARCHIVE`/`NOTIFY` | 代码中不存在按策略物理删除的路径 |
| T3.4 | 业务代码**不可写**审计：审计 Mapper 包内私有，只由 AOP / outbox 写 | 在其他 Service 里注入审计 Mapper，启动即失败 |

**期 3 出口**（这是整份方案最硬的验收）：

> 随机挑一次已完成的实验，审计员**只读系统输出**，能回答完这七问：
> 1. 谁在什么时候启动的，依据哪一版方法定义（含 checksum）
> 2. 每一步的输入是什么（`input_snapshot`）
> 3. 设备命令何时下发、何时被设备接受、何时完成
> 4. 原始数据的哈希与接收时间、设备时间、时间质量
> 5. 结论用的是哪一版规则（`rule_code + rule_version`）
> 6. 期间哪些受控字段被谁改过，改前改后是什么
> 7. 最终结果有没有被签署，谁签的

**T3.4 的做法**：把审计写入收敛到一个 `AuditWriter`，Mapper 设为包内可见（package-private），
其他模块无法注入。比"靠代码评审约束"可靠。

### 期 4 · 对外契约（2.5 周）

| 编号 | 工作项 | 验收 |
|---|---|---|
| T4.1 | 集成接口 `/open-api/v1/**`：API Key + `Idempotency-Key` 头 | 同一幂等键重复调用返回同一结果，不产生第二条记录 |
| T4.2 | 事件：`task.created` / `task.completed` / `device.data.received`，用 **outbox 表 + 轮询**，不引 MQ | outbox 积压可观测，重投不重复消费 |
| T4.3 | 证据导出 `/evidence/export/{executionId}`：JSON（机器）+ PDF 摘要（人） | 导出的 JSON 能被另一个系统独立解析，无需平台代码 |
| T4.4 | `schema_version`：`device_measurement` 与 `device_analysis_result` 各加一列 | 旧数据按旧版本解释，可并存 |

**期 4 出口**：
> 找一个人，只给他 OpenAPI 文档和一份示例，不给他源码，
> 他能在一天内写出「任务下发 → 轮询结果 → 下载证据」的完整集成。

## 四、依赖与并行

```
期0 ──┬─→ 期1 ──┬─→ 期3
      │          │
      └─→ 期2 ──┘（期2 只需期0，可与期1 并行）
```

| 人力 | 分工 | 总工期 |
|---|---|---|
| 1 人 | 严格串行 0→1→2→3→4 | 约 10 周 |
| 2 人 | A：期0 + 期1；B：期2；期3 两人合做；期4 由 A 收尾 | 约 6.5 周 |
| 3 人 | 再加 C 独立做 T1.4–T1.6（设备时间与校准），期4 拆成契约与导出两条 | 约 5 周 |

**硬依赖只有三条**：
- 期 3 依赖期 1（审计要能关联到外部单号，否则审计记录无法回答「哪张单」）
- 期 4 依赖期 2（对外事件要能说清资源占用）
- 期 2 与期 1 之间**无依赖**，可完全并行

## 五、范围控制：这一轮明确不做

| 不做 | 理由 |
|---|---|
| 拆微服务 | 单进程 Spring Boot 是正确的，问题不在部署形态 |
| 引消息队列（Kafka/RocketMQ） | outbox + 轮询足够；MQ 是规模问题，不是架构问题 |
| 做调度求解器 | 先用 FIFO + 优先级，等有真实争用数据再优化；没有数据的求解器都是猜 |
| 增强多租户隔离 | 现有 `tenant_id` 机制够用 |
| AI 流程生成 | 证据链未通之前，生成的流程也无法验证，做了也没人敢用 |

## 六、风险与回退

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 客户不肯加 `source_system` | LIMS 团队说「我们只有一个系统」 | 期 1 照建表，字段填常量，为将来留口，不为此争论 |
| 老设备不给时间戳 | 协议里没有时间字段 | 降级 `time_quality=INFERRED`，如实标注，不阻塞 |
| 资源抽象做成设备专用 | 适配器出现类型判断分支 | 停手重审，宁可延期 |
| 审计拖慢写入 | P99 上升超过 20% | 改异步 outbox，不动业务同步路径 |
| 关联层被当成业务表用 | 有人往 `task_correlation` 加业务字段 | 立即叫停，它只做映射 |

## 七、每期结束的固定动作

1. 跑 `script/arch-score.sh`，记录六维分数（**只允许升，降了要解释**）
2. 更新 `10-中枢能力划分与权威事实.md` 的「现状」列
3. 本期没解决、但发现的新问题，写进 `TODO.md` 的 I 区（守卫缺口）
4. 期 1、3、4 结束时各做一次「外部人验收」：找一个没参与的人按出口判据走一遍

---

## 八、与业务交付的关系

这套方案是**平台能力**，不是某个客户的功能。

- 客户功能需求照常走原排期，不受本方案阻塞
- 但每新增一张业务表，必须同时满足：有 `tenant_id`、有审计覆盖、有时间语义、
  若对应外部对象则有 `source_system + 外部号`
- 这条约束建议写进代码评审清单，否则平台能力会被业务需求一点点侵蚀
