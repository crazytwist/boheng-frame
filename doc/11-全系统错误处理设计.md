# 全系统错误处理设计

> 状态：待评审
> 参考：`/Users/yinan/workspace/megarobo/qinghua`
> 目标：统一 HTTP、业务、设备、流程、运输、异步任务的错误语义，同时保持现有 `CommonResult` 与前端兼容。

## 1. 结论

从清华项目源码可确认的做法是：业务层抛出外部 starter 提供的 `BizException`，接口层统一返回 `BaseApiResp(code, msg, data)`；控制器不重复包装错误。其全局异常处理器位于 `com.librax:librax-lab-boot-starter:0.2.9.9-SNAPSHOT` 依赖中，当前源码仓库和本机 Maven 缓存没有该依赖的实际 jar，因此不能把其隐藏实现（HTTP 状态、校验错误结构等）直接当作契约复制。

清华项目另外值得借鉴的是设备错误的领域处理：错误 key、错误上报、人工处理，以及“跳过/重试”等动作。这个模型应与 HTTP 异常分开。

boheng 当前已经具备同样的基础能力，而且更适合继续演进：

- `ErrorCode`：错误码与默认消息分离；
- `ServiceException`：业务异常；
- `GlobalExceptionHandler`：统一转换 Spring MVC 异常；
- `CommonResult`：统一接口返回；
- 各模块 `ErrorCodeConstants`：模块级错误码。

因此不建议引入第二套 `BizException/BaseApiResp`。目标方案是**保留现有协议，补齐错误分类、错误上下文、统一日志和设备运行时故障模型**。

## 2. 错误分层

| 层级 | 典型来源 | 是否返回给调用方 | 处理方式 |
| --- | --- | --- | --- |
| 请求错误 | 参数缺失、格式错误、校验失败 | 是 | `400` + `CommonResult` |
| 认证授权错误 | 未登录、无权限、租户不可访问 | 是 | `401/403` + `CommonResult` |
| 业务错误 | 资源不存在、状态不允许、重复操作 | 是 | 模块错误码 + 可读消息 |
| 并发/幂等错误 | 锁冲突、重复提交、版本冲突 | 是 | `423/409/900`，标记可重试 |
| 外部依赖错误 | 设备 HTTP、数据库、消息队列、第三方接口 | 部分 | 对外隐藏内部细节，返回稳定错误码 |
| 系统错误 | 未捕获异常、配置错误、框架错误 | 否 | `500`，记录完整堆栈并返回 traceId |
| 设备/流程运行故障 | 设备报警、流程节点失败、运输交接失败 | 不等同 HTTP 错误 | 写入事件/报警中心，驱动状态机和处置流程 |

关键原则：**HTTP 请求失败和业务运行故障不是同一个模型**。清华项目的设备错误上报、处理、查询应映射为报警实体，而不是简单抛出 HTTP 异常。

## 3. 对外响应协议

### 3.1 兼容现有格式

成功响应保持：

```json
{"code":0,"msg":"","data":{}}
```

错误响应保持 `code/msg/data`，在 `data` 中逐步增加结构化错误信息，不破坏现有前端读取 `msg` 的逻辑：

```json
{
  "code": 1_006_000_012,
  "msg": "路线 AGV-A01 当前不可用",
  "data": {
    "traceId": "01J...",
    "errorType": "BUSINESS",
    "retryable": false,
    "details": null
  }
}
```

### 3.2 参数校验错误

```json
{
  "code": 400,
  "msg": "请求参数不正确",
  "data": {
    "traceId": "01J...",
    "errorType": "VALIDATION",
    "retryable": false,
    "details": [
      {"field":"routeCode","message":"路线编码不能为空"}
    ]
  }
}
```

### 3.3 字段定义

- `code`：稳定的机器可判断错误码；
- `msg`：当前语言的用户可读摘要；
- `data.traceId`：请求关联 ID，前端报错和日志检索使用；
- `data.errorType`：`VALIDATION/BUSINESS/AUTH/CONFLICT/DEPENDENCY/SYSTEM`；
- `data.retryable`：调用方是否可以重试；
- `data.details`：字段错误、外部依赖状态或业务上下文，禁止放堆栈和密钥。

第一阶段可以只补充 `traceId` 和 `errorType`，避免一次性改动所有前端接口。

## 4. 异常类型

### 4.1 业务异常：继续使用 `ServiceException`

业务代码统一使用错误码：

```java
throw exception(TRANSPORT_ROUTE_NOT_FOUND, routeCode);
```

禁止在业务层直接抛出带用户文案的 `RuntimeException`、`IllegalStateException` 或拼接 SQL/设备响应作为错误码。

### 4.2 系统异常：保留原始 cause

`ServerException` 用于明确的系统级可控异常；未知异常由全局处理器兜底。异常必须支持 cause，便于定位根因：

```java
throw new ServerException(INTERNAL_SERVER_ERROR, cause);
```

不要把数据库异常、HTTP 客户端异常直接暴露给前端。

### 4.3 外部依赖异常

设备、WMS、Flow、MQ 等边界先转换成模块错误码，例如：

- `DEVICE_HTTP_FAILED`：设备调用失败；
- `FLOW_NODE_EXECUTION_FAILED`：流程节点执行失败；
- `TRANSPORT_HANDOVER_FAILED`：运输交接失败；
- `DEPENDENCY_TIMEOUT`：依赖超时。

错误消息可以保留安全的摘要（HTTP 状态、设备编码、超时毫秒数），原始响应只写日志或事件表。

## 5. 错误码规范

### 5.1 全局错误码

继续使用 `0-999`：

- `0`：成功；
- `400/401/403/404/405`：请求、认证、资源和方法错误；
- `409/423`：冲突、锁定；
- `429`：限流；
- `500/501/502`：系统、未实现、配置错误；
- `900+`：平台级特殊错误。

建议补充 `409 CONFLICT`，把版本冲突、幂等键冲突、状态竞争从普通 `400` 中区分出来。

### 5.2 模块错误码

沿用十位编码：`1-系统-模块-错误`。每个模块维护自己的 `ErrorCodeConstants`，禁止跨模块复用业务错误码。

建议预留：

- `001` infra；
- `002` system；
- `003` flow；
- `004` device；
- `005` wms；
- `006` transport；
- `007` message/alarm。

同一错误码一旦发布不得复用；文案调整不改变 code。

## 6. 全局异常处理链

处理优先级固定为：

1. `ServiceException`：返回业务错误码；
2. `AccessDeniedException` / 认证异常：返回 `403/401`；
3. 参数校验异常：聚合字段错误，返回 `400`；
4. 外部依赖异常：转换为稳定的依赖错误码；
5. 数据库约束/锁异常：转换为冲突或锁定错误；
6. 未知 `Throwable`：记录完整日志，返回 `500 + traceId`。

同一套转换逻辑同时服务：

- Spring MVC Controller；
- Filter/Security Filter；
- 异步任务入口；
- WebSocket/设备回调入口（无法返回普通 HTTP 时写事件和日志）。

全局处理器必须保证：错误日志失败不能影响错误响应，避免在异常处理里再次抛异常。

## 7. 日志与 trace

每个请求生成或透传 `traceId`，响应头和错误体都返回该值。日志至少包含：

- `traceId`、租户、用户、应用名；
- 请求方法、URL、模块；
- 错误码、异常类型、根因；
- 业务主键（设备编码、流程执行号、运输单号）；
- 是否可重试。

日志分级：

- `WARN`：可预期业务错误、参数错误、锁冲突；
- `ERROR`：未知异常、依赖故障、数据损坏；
- 设备原始报警不直接刷应用错误日志，进入事件/报警流水。

禁止记录密码、token、完整请求体中的敏感字段和设备密钥。

## 8. 设备、Flow、Transport 的运行时故障

参考清华项目的错误上报/处理接口，但抽象为系统级报警中心：

```text
设备回调 / Flow 节点失败 / Transport 交接失败
                 ↓
          event_log（原始事件，只增）
                 ↓
          alarm_record（聚合、状态机）
                 ↓
  页面确认/重试/跳过/终止 + 站内信/WebSocket
```

报警记录至少包含：

- `sourceType`：`DEVICE/FLOW/TRANSPORT/SYSTEM`；
- `sourceCode`：设备编码、执行号或运输单号；
- `errorCode`、等级、原始消息；
- `status`：`ACTIVE/ACKED/RECOVERED/CLOSED`；
- 首次/最近发生时间和发生次数；
- 处置人、处置动作、处置备注；
- `traceId`、原始 payload 引用。

`alarm_record` 不替代 HTTP 错误响应：HTTP 回调仍返回接收结果，运行故障通过报警状态机异步处理。

## 9. 前端处理约定

前端继续按 `code` 判断，不按中文 `msg` 判断业务分支：

- `401`：刷新 token 或跳转登录；
- `403`：提示无权限；
- `409/423/429`：提示并根据 `retryable` 决定是否重试；
- `500`：提示“系统异常”，展示 traceId；
- 业务码：展示 `msg`，必要时依据 code 打开对应详情页；
- `data.details`：表单错误回填到字段。

国际化以后以错误码为 key，`msg` 作为后端降级文案，不把中文消息作为协议契约。

## 10. 落地顺序

### P0：不破坏现有接口

1. 增加 `traceId` 上下文和响应头；
2. `GlobalExceptionHandler` 增加统一错误类型和 traceId；
3. 完善 `CommonResult` 的错误 data 扩展；
4. 补 `409 CONFLICT` 和依赖错误码；
5. 统一 Service/Controller 禁止直接抛裸 `RuntimeException`。

### P1：模块边界收敛

1. Device/Flow/Transport/WMS 的外部调用统一转换错误码；
2. 建立各模块错误码目录和重复码检查；
3. 为关键业务错误补单元测试和接口契约测试；
4. 统一异步任务的错误记录和重试策略。

### P2：报警中心

1. 落地 `event_log`、`alarm_record`、`alarm_action`；
2. 接入设备主动报警、Flow 节点失败、Transport 交接失败；
3. 增加确认、重试、跳过、终止和恢复状态机；
4. 通过站内信/WebSocket/外部 webhook 投递通知。

## 11. 验收标准

- 任意 HTTP 错误都返回合法 `CommonResult`，不泄漏堆栈；
- 任意错误可用 `traceId` 在日志中定位；
- 业务错误由错误码判断，不依赖中文文案；
- 参数错误能返回字段级 details；
- 设备/流程/运输运行故障不会被误当成普通 500；
- 前端对 401、403、409、423、429、500 的行为明确；
- 错误处理器自身失败不会覆盖原始异常；
- 现有 `code/msg/data` 调用方无需一次性改造。
